# Design

## Context

Мотивация — см. `proposal.md` («Why»), требования — `specs/mcp-integration/spec.md`.

Что из текущего состояния кода определяет подход:

- Бот — `python-telegram-bot` v20+, обработчики асинхронные, запуск `python src/main.py`
  (пакета/установки нет, `src/` оказывается в `sys.path` как корень импорта).
- Единственный внешний SDK сейчас — `openai`, и он СИНХРОННЫЙ: вызовы блокируют
  event loop, а параллельность там, где она нужна, сделана через `ThreadPoolExecutor`
  (`research/temperature.py`, `research/models.py`, `agents/compare_command.py`).
  Официальный Python SDK MCP, наоборот, асинхронный — это первое место в проекте, где
  внешний вызов можно просто `await`-ить.
- Разделение «механика отдельно, Telegram отдельно» уже принято в проекте дважды:
  `providers/*` против `main.py` и `agents/agent.py` против `agents/agent_command.py`.
- Технические/диагностические команды прячутся флагом `RESEARCH` (`RESEARCH_ENABLED`
  в `config.py`): не регистрируются в `main.py` и не упоминаются в `/help`.
- Все переменные окружения читаются через `python-dotenv`, и `load_dotenv()`
  вызывается ровно в одном месте — `config.py`.
- Тесты (`tests/`) покрывают только чистые функции — без сети, Telegram и моков
  клиентов (`tests/test_task_state.py`).

Новое ограничение, которого в проекте раньше не было: работа требует стороннего
процесса на хосте (`npx`), то есть появляется класс сбоев «внешняя программа не
запустилась/зависла», не сводимый к исключениям OpenAI SDK.

## Goals / Non-Goals

**Goals:**

- Асинхронное подключение к stdio-серверу MCP через официальный SDK без блокировки
  event loop бота.
- Слой MCP, не знающий ни про Telegram, ни про LLM, — пригодный к переиспользованию,
  когда дело дойдёт до вызова инструментов.
- Все сбои внешнего процесса превращаются в сообщение на русском, а не в падение
  обработчика.
- Форматирование списка инструментов — чистая функция, покрываемая тестами без сети.

**Non-Goals (дополнительно к не-целям из `proposal.md`):**

- Долгоживущая сессия/пул соединений и кэш списка инструментов между вызовами.
- Абстракция «несколько MCP-серверов» и реестр серверов.
- Отдельный флаг доступа под MCP: используется существующий `RESEARCH`.

## Decisions

### 1. Пакет называется `mcp_integration`, а не `mcp`

Бот запускается как `python src/main.py`, поэтому `src/` — корень импорта. Пакет
`src/mcp/` ЗАТЕНИЛ БЫ сам SDK: `import mcp` внутри проекта разрешился бы в локальный
пакет, и SDK стал бы недоступен. Альтернатива «оставить `mcp` и импортировать SDK
хитростями» отвергнута как источник неочевидных поломок. Имя `mcp_integration`
однозначно и не конфликтует.

### 2. Транспорт stdio и официальный SDK, соединение — на один запрос

Используется `mcp.client.stdio.stdio_client(StdioServerParameters(...))` вместе с
`mcp.ClientSession`: асинхронные контекстные менеджеры, вход в которые запускает
дочерний процесс и выполняет `initialize()`, а выход — гарантированно завершает
процесс. Весь цикл «запустить → рукопожатие → `list_tools()` → закрыть» живёт внутри
одного `async with` на каждый вызов команды.

Альтернатива — держать сессию живой между вызовами (кэш по аналогии с `_agents` в
`agents/agent_command.py`) — отвергнута: требует следить за живостью процесса,
перезапускать упавший сервер и чистить процессы при остановке бота, а выигрыш
(экономия старта `npx`) нужен только при частом использовании, которого у
диагностической команды нет. Цена решения зафиксирована в требовании «процесс не
удерживается между запросами» — вернуться к пулу можно, не меняя спеку наружу.

### 3. Тайм-аут — общей обёрткой вокруг всего блока, а не на отдельный запрос

`asyncio.timeout(MCP_TIMEOUT_SECONDS)` (Python 3.10+; в окружении 3.12) оборачивает
весь `async with`, потому что зависнуть может любая из трёх стадий: запуск `npx`
(включая скачивание пакета при первом запуске), рукопожатие, ответ `list_tools`.
Отмена по тайм-ауту раскручивает контекстные менеджеры, а те завершают дочерний
процесс — отдельного кода убийства процесса не требуется. Альтернатива (тайм-аут
только на `list_tools`) не покрывает самый вероятный случай — залипание на старте.

### 4. Слой MCP возвращает данные, а не текст для Telegram

`mcp_integration/client.py` предоставляет одну асинхронную функцию, возвращающую
простой результат (имя/версия сервера + список инструментов как dataclass-объекты
`name`/`description`/`required_params`), и НЕ ловит исключения «на всякий случай» —
как `Agent.ask()`, который отдаёт исключения SDK наверх.

Перевод исключений в русский текст и нарезка сообщений — в
`mcp_integration/tools_command.py`, тем же паттерном «перехватить конкретный класс
ошибок, назвать его по-человечески», что `handle_message` в `main.py`. Общий
`research/_shared.api_error_to_message` НЕ переиспользуется: он про исключения
OpenAI SDK, здесь классы ошибок другие (`FileNotFoundError` от отсутствующего `npx`,
`TimeoutError`, ошибки протокола MCP).

### 5. Конфигурация — в `config.py`, команда и аргументы раздельно

Три переменные: `MCP_SERVER_COMMAND` (по умолчанию `npx`), `MCP_SERVER_ARGS` (по
умолчанию `-y @modelcontextprotocol/server-everything`) и `MCP_TIMEOUT_SECONDS` (по
умолчанию 60, с запасом на первое скачивание пакета).

- В `config.py`, а не в `mcp_integration/client.py`: правило проекта — в
  `providers/*_client.py` живут ПРОВАЙДЕР-специфичные переменные, всё остальное общее
  — в `config.py`. MCP-сервер не является LLM-провайдером, выбора между несколькими
  реализациями нет, и `load_dotenv()` всё равно вызывается только в `config.py`.
- Команда и аргументы РАЗДЕЛЬНО (аргументы разбираются `shlex.split`), а не одной
  строкой в шелле: `StdioServerParameters` запускает процесс без оболочки, поэтому
  подстановки и инъекции через `.env` не возникает. Альтернатива «одна строка +
  `shell=True`» отвергнута именно поэтому.
- Переменные читает оператор через `.env`; пользователю сервер не подменить — команда
  игнорирует любые аргументы сообщения (требование спеки).

### 6. Команда `/mcp_tools` — обычный `CommandHandler` под `RESEARCH_ENABLED`

Диалога нет: ни ввода вопроса, ни кнопок, ни состояния — значит, `ConversationHandler`
(как в `research/*`) избыточен, достаточно одного `CommandHandler`, как у
`/agent_history`. Регистрация в `main.py` — внутри существующего блока
`if RESEARCH_ENABLED`, строка в `/help` — в блоке с `/research_*`, чтобы не заводить
второй флаг видимости (правило CLAUDE.md про новые исследовательские команды).

Перед началом работы обработчик отправляет `ChatAction.TYPING` и короткое сообщение
«подключаюсь к MCP-серверу…», потому что первый запуск `npx` может занять десятки
секунд, и молчание бота выглядело бы как зависание.

### 7. Вывод — простым текстом, без `parse_mode`

Описания инструментов приходят от стороннего сервера и могут содержать `<`, `&`,
незакрытые теги и Markdown-разметку. С `ParseMode.HTML` (как в `/help`) Telegram
отверг бы такое сообщение целиком. Поэтому результат отправляется без `parse_mode`, а
нарезается по `TELEGRAM_MESSAGE_LIMIT` тем же приёмом, что в `handle_message`.
Описание каждого инструмента усекается до разумной длины — сервер `server-everything`
отдаёт около десятка инструментов, но потолка на длину описания протокол не задаёт.

### 8. Тестируется форматирование, а не соединение

Функция «список инструментов → текст» — чистая, ей в `tests/` место по тому же
принципу, что и `tests/test_task_state.py`: тесты на пустой список, на инструмент без
описания, на обязательные параметры из `inputSchema`, на усечение. Моки сессии MCP и
проверки самого соединения не пишутся — это интеграция с внешним процессом, её
проверяет ручной прогон `/mcp_tools` (и он же зафиксирован отдельной задачей).

## Risks / Trade-offs

- **Первый вызов `npx -y` скачивает пакет и может не уложиться в тайм-аут** →
  тайм-аут по умолчанию 60 с; в README и `.env.example` указывается, что сервер стоит
  «прогреть» заранее (`npx -y @modelcontextprotocol/server-everything --help`), и что
  `MCP_TIMEOUT_SECONDS` можно увеличить.
- **Требование Node.js/`npx` на хосте бота** — раньше рантайм зависел только от
  Python → отсутствие `npx` не ломает бот: команда отвечает понятной ошибкой,
  остальное работает; требование фиксируется в README и `.env.example`.
- **Конфликт версий зависимостей**: `mcp`, `openai` и `python-telegram-bot` тянут
  `httpx`/`anyio`/`pydantic` → отдельная задача — проверить, что
  `pip install -r requirements.txt` разрешается в чистом окружении, и при
  необходимости поправить границы версий, а не подпирать конфликт в коде.
- **Каждый вызов платит за старт процесса** (сознательный размен из решения 2) →
  приемлемо для диагностической команды; при переходе к вызову инструментов из
  агентов решение пересматривается.
- **Долгий вызов держит обработчик** — при массовых нажатиях наплодится много
  процессов `npx` → команда под `RESEARCH`, то есть на проде может быть выключена;
  ограничение частоты в этот change не входит и отмечено как возможное продолжение.
- **Сторонний сервер может вернуть очень длинный список** → усечение описаний и
  нарезка сообщений; полный дамп в чат не выводится.

## Migration Plan

Изменение аддитивное: новый пакет, новая команда, новые переменные окружения со
значениями по умолчанию. Существующее поведение бота не меняется — ни один
существующий обработчик, ни `handle_message`, ни файлы памяти агентов не затрагиваются.

- Развёртывание: `pip install -r requirements.txt` (появляется `mcp`), установка
  Node.js/`npx` на хосте, перезапуск процесса. Переменные MCP можно не задавать —
  значения по умолчанию рабочие.
- Откат: `RESEARCH=false` скрывает команду немедленно без выката кода; полный откат —
  снятие коммита, никаких миграций данных и файлов состояния не требуется.

## Open Questions

- Точная нижняя граница версии `mcp` в `requirements.txt` фиксируется при реализации
  по фактически установленной версии из PyPI (в стиле существующих строк
  `openai>=1.30.0,<2`). На спеку, подход и разбивку задач это не влияет.
