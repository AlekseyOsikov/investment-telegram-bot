# Design

## Context

См. `proposal.md` — «Why». В боте сейчас нет кода, работающего с эмбеддингами,
FAISS или каким-либо корпусом документов; `data/source/pdf/` (55 файлов) и
`data/source/txt/` (6 файлов) уже существуют с реальным содержимым. Имена файлов
следуют формату `<Title>(<author>, <date>).ext`, где `author`/`date` не
обязательны. PDF — это экспорт слайдов (InDesign) в один столбец, с заголовком
документа, повторяющимся как «шапка» на каждой странице, и без доступных через
простое извлечение текста данных о размере шрифта; txt-файлы — это проза с
отдельными короткими самостоятельными строками, похожими на заголовки.
`pdftotext -layout` (poppler) воспроизводит порядок чтения на реальных файлах
приемлемо и вставляет form-feed между страницами. На этой машине уже запущен
локальный сервер Ollama с загруженной моделью `bge-m3`, доступный по адресу
`http://localhost:11434`; его эндпоинт `/v1/embeddings` OpenAI-совместим. У API
DeepSeek эндпоинта эмбеддингов нет.

Весь `data/` уже в `.gitignore` (`/data/`), поэтому новому каталогу
`data/rag_index/` отдельная запись в gitignore не нужна.

## Goals / Non-Goals

**Goals:**
- Детерминированный, повторно запускаемый CLI, превращающий
  `data/source/{pdf,txt}` в два независимо опрашиваемых индекса (чанкинг по
  фиксированному размеру vs. структурный).
- Сделать обе стратегии доступными для изучения и сравнения из бота, не требуя
  при этом наличия Ollama или построенного индекса для запуска бота или работы
  любой другой команды.
- Переиспользовать существующие механизмы проекта (SDK `openai`, перевод ошибок
  из `research/_shared.py`, паттерн включения по RESEARCH из `research/*`), а не
  вводить новые соглашения.

**Non-Goals:**
- Встраивание поиска по документам в ответы `/agent` или `/smart_agent` — это
  изменение только строит индекс и даёт его изучить, оно не меняет, что отвечает
  какой-либо агент.
- Инкрементальная/частичная переиндексация — корпус небольшой (~60 файлов);
  каждый запуск CLI пересобирает обе стратегии с нуля.
- Поддержка в этом изменении какого-либо бэкенда эмбеддингов, кроме
  совместимого с Ollama локального эндпоинта (например, размещённого в облаке
  API эмбеддингов Kimi) — можно рассмотреть позже, т.к. клиент изолирован в
  одном модуле.
- Улучшение качества поиска (переранжирование, гибридный поиск, дедупликация) —
  `/research_chunking_compare` — это прямой топ-k поиск по FAISS для сравнения
  стратегий, а не полноценный ретривер для продакшена.

## Decisions

### Эмбеддинги: локальный Ollama (`bge-m3`) через новый `providers/embeddings_client.py`
`/v1/embeddings` у Ollama OpenAI-совместим, поэтому существующий SDK `openai`
обращается к нему так же, как `providers/deepseek_client.py`/`kimi_client.py`
обращаются к своим провайдерам — просто с `base_url="http://localhost:11434/v1"`
и плейсхолдер-ключом API (Ollama его игнорирует). Это не добавляет ни одной новой
тяжёлой зависимости.
- **Альтернатива — облачный API эмбеддингов Kimi**: тоже OpenAI-совместим и
  переиспользовал бы существующий паттерн `kimi_client`, но требует
  `KIMI_API_KEY` даже при `MAIN_CLIENT=deepseek`, стоит денег за каждый чанк и
  требует сети на каждый из ~60 файлов. Отклонено по явному предпочтению
  пользователя использовать локальную модель.
- **Альтернатива — локальный `sentence-transformers`**: полностью offline, без
  зависимости от сервера, но добавляет `torch` + `sentence-transformers` в
  `requirements.txt` (установка на многие сотни мегабайт), когда эквивалентная
  модель уже работает локально через Ollama. Отклонено как избыточное.
- Конфигурация: `EMBEDDINGS_BASE_URL` (по умолчанию `http://localhost:11434/v1`),
  `EMBEDDINGS_MODEL` (по умолчанию `bge-m3`). Как и `MCP_MOEX_DIR`, недоступность
  эндпоинта не должна ронять бота при старте — от него зависят только запуск CLI
  и две новые команды RESEARCH, и они сами обрабатывают сбой на каждый вызов с
  переведённым сообщением об ошибке.
- **Клиент собран с `httpx.Client(trust_env=False)`, игнорирующим прокси из
  окружения.** Воспроизведена и подтверждена (логами Docker-контейнера Ollama: ни
  одного соответствующего запроса в них не было) причина повторяющегося `502` —
  бот запускается с `ALL_PROXY`, настроенным для DeepSeek/Kimi (внешние API,
  которым прокси действительно нужен), без `NO_PROXY`, исключающего localhost; без
  этого исключения запросы к `EMBEDDINGS_BASE_URL` (всегда локальный по дизайну)
  уходили через тот же прокси, который не умеет проксировать обратно на loopback
  этой же машины и отвечал `502` вместо реальной ошибки соединения — что выглядело
  как нестабильность самой Ollama и не лечилось никаким числом повторов, пока не
  нашлась истинная причина. `trust_env=False` — не одна из НЕСКОЛЬКИХ альтернатив,
  а единственный вариант, не зависящий от того, как настроено `NO_PROXY` в
  окружении конкретного оператора: Ollama в этом проекте всегда локальный сервис
  (см. `EMBEDDINGS_BASE_URL` выше), проксировать обращения к нему не нужно
  никогда — в отличие от `providers/deepseek_client.py`/`kimi_client.py`, которые
  проксируются обычным образом и не меняются.
- **Автоматические повторы с нарастающей паузой в `embed_texts()`** (по образцу
  `Agent._update_facts()`/`SmartAgent._check_invariants()`, но не ОДИН повтор, а
  несколько): воспроизведено на практике, что Ollama выгружает модель из памяти
  после простоя и первый запрос после этого иногда завершается ошибкой сервера (в
  т.ч. `502` — внутренний `ollama serve` не достучался до ещё не поднявшегося
  процесса `ollama runner`), а не просто задержкой. Единственного повтора с
  фиксированной паузой оказалось недостаточно на практике — воспроизведён случай,
  когда `502` держался дольше ~7 секунд суммарного времени (включая собственные
  повторы SDK `openai` поверх каждой попытки), поэтому пауз три, с нарастанием
  (2/4/6 с) — если и это не помогло, исходное исключение поднимается как есть, тем
  же путём, что и раньше. Компромисс: команда интерактивная, поэтому конечное
  число попыток, а не бесконечный повтор.

### Извлечение текста из PDF: вызов `pdftotext` (poppler), а не pip-библиотека
Проверено на реальных файлах этого репозитория: `pdftotext -layout` достаточно
хорошо воспроизводит порядок чтения и вставляет form-feed (`\f`) между
страницами, который структурная стратегия использует напрямую как границу
страницы. Это соответствует уже принятому в проекте паттерну — вызывать внешние
бинарники (`uv`, `npx`), а не добавлять возможность как pip-зависимость.
- **Альтернатива — `pypdf`/`pdfplumber`/`pymupdf`**: нет зависимости от внешнего
  бинарника, но метаданные о размере шрифта (нужные для настоящего обнаружения
  заголовков) либо недоступны (`pypdf`), либо потребовали бы `pymupdf` — гораздо
  более тяжёлую зависимость — ради преимущества, которое здесь всё равно не
  применимо (см. ниже). Отклонено по явному предпочтению пользователя, а также
  потому что это не улучшило бы структурный чанкинг именно на этих файлах.

### Исходные файлы — данные только для чтения
Пайплайн разбирает `title`/`author`/`date` из имени файла в метаданные чанка и
никогда не переименовывает и не переписывает файлы в `data/source/`. Отклонено
буквальное прочтение исходной просьбы «переименовать в `<Title>.ext`»: команда
индексации, незаметно массово переименовывающая архив документов пользователя —
это трудно обратимый побочный эффект, несоразмерный тому, что реально нужно для
индексации. Разбор метаданных даёт тот же практический результат (чистый `title`
в метаданных каждого чанка) без этого эффекта.

### Структурный чанкинг: эвристика заголовков + откат по страницам PDF, а не «один чанк на файл»
С учётом реального корпуса (см. Context) настоящее обнаружение заголовков
надёжно работает только для txt-файлов. Дизайн считает страницу PDF (разделённую
form-feed) структурной единицей первого уровня — это уже осмысленная граница
«раздела» в этих слайд-подобных документах — и дополнительно сканирует каждую
страницу (и каждый txt-файл) на строки-заголовки (короткая самостоятельная
строка без завершающего `.`/`!`/`?`/`:`, за которой следует абзац), чтобы разбить
дальше там, где они найдены. Единица без обнаруженного заголовка выдаётся как
один чанк целиком, так что текст никогда не теряется — меняется только
гранулярность.
- **Альтернатива — один чанк на файл, без обнаружения заголовков**: полностью
  надёжно, эвристике негде ошибиться, но теряет реальную внутридокументную
  структуру, которая есть в txt-файлах (а именно ради неё и затевалось сравнение
  с чанкингом по фиксированному размеру). Отклонено по явному предпочтению
  пользователя в пользу более богатой, пусть и неидеальной, эвристики.
- Ложные срабатывания/пропуски эвристики (например, строка списка,
  выглядящая как заголовок) лишь сдвигают границу чанка; они не могут привести к
  потере текста, т.к. каждая строка всё равно попадает ровно в один чанк.

### Тип индекса FAISS: плоский, точный поиск (`IndexFlatIP` по L2-нормализованным векторам)
При таком масштабе корпуса (~60 файлов, вероятно низкие тысячи чанков суммарно
по обеим стратегиям) приближённый индекс (IVF, HNSW) добавил бы сложность
настройки без измеримой пользы. Точный поиск по косинусной близости прост для
понимания и соответствует тому, что нужно `/research_chunking_compare`
(небольшие топ-k запросы, а не обслуживание с высокой нагрузкой).

### Схема SQLite на стратегию
Один `meta.sqlite3` на стратегию, одна таблица `chunks`:
`chunk_id` (TEXT, уникален в пределах стратегии), `source` (исходное имя файла),
`title`, `author` (может отсутствовать), `date` (может отсутствовать),
`strategy`, `chunk_index` (позиция внутри своего исходного документа), `text`
(содержимое чанка), `faiss_row_id` (INTEGER, индекс строки в FAISS-индексе этой
стратегии). `research/chunking_stats.py` считает
`COUNT`/`AVG(LENGTH(text))`/`MIN`/`MAX` прямо из этой таблицы для каждой
стратегии — отдельного кэша статистики нет.

### Структура кода
- Новый пакет верхнего уровня `rag/`: `rag/filenames.py` (разбор метаданных),
  `rag/extraction.py` (PDF через subprocess `pdftotext`, txt — обычное чтение,
  общая очистка пустых строк/абзацев), `rag/chunking.py` (обе стратегии за общим
  интерфейсом), `rag/index_store.py` (чтение/запись FAISS + SQLite по каждой
  стратегии), `rag/cli.py` (точка входа, `python -m rag.cli`, подключена к
  `make index`).
- Команды бота лежат в `research/chunking_stats.py` и
  `research/chunking_compare.py` — не в `rag/` — потому что они обращены к
  Telegram, включаются флагом RESEARCH и переиспользуют
  `research/_shared.py`: `api_error_to_message`/`build_cancel_handler`. Вызов
  Ollama через SDK `openai` поднимает те же типы исключений, которые
  `research/_shared.py` уже умеет переводить, — отдельный путь обработки ошибок
  не нужен. Обе команды импортируют `rag.index_store`/
  `providers.embeddings_client` для самого поиска.
- `/research_chunking_compare` — `ConversationHandler` с единственным состоянием
  `WAITING_QUERY`, которое зацикливается (на каждый запрос — ответ, затем
  ожидание следующего) до `/cancel`, используя `build_cancel_handler` — та же
  форма, что и цикл вопросов `/agent`, поскольку сравнение нескольких запросов в
  одной сессии — ожидаемый сценарий использования, в отличие от одноразовых
  мастеров `/research_constraints`/`/research_temperature`.
- `/research_chunking_stats` — обычный `CommandHandler` (без диалога, без
  аргументов) — он только читает уже сохранённые файлы SQLite.

### Поведение CLI: полная пересборка, без инкрементальности
Каждый запуск `python -m rag.cli` обрабатывает все файлы, находящиеся сейчас в
`data/source/{pdf,txt}`, и полностью переписывает файлы индекса обеих стратегий
с нуля (запись во временный путь, затем замена — так что сбой посреди работы не
может оставить наполовину записанный индекс — это и есть сценарий спеки «не
сохраняет частично построенный индекс»). При таком размере корпуса и бесплатном
локальном бэкенде эмбеддингов стоимость полной пересборки низкая, и это
избавляет от логики обнаружения изменений, которую исходная просьба не
предполагала.

## Risks / Trade-offs

- **Ollama/`bge-m3` недоступны на какой-то другой машине, где запускается этот
  бот** → Смягчение: обрабатывается ровно как `MCP_MOEX_DIR` — при загрузке
  конфигурации только предупреждение, CLI при реальном запуске завершается с
  понятным сообщением при недоступности, а обе команды бота ловят тот же сбой
  на каждый вызов и отвечают по-русски, не падая и не блокируя старт бота.
- **Эвристика заголовков ошибается на списках или коротких самостоятельных
  цитатах** → Смягчение: ошибки только меняют гранулярность/границы чанков,
  никогда не теряют текст (откат гарантирует полное покрытие); приемлемо для
  инструмента сравнения, чья цель — как раз показать эти различия, а не скрыть
  их.
- **Артефакты порядка чтения `pdftotext` на какой-то раскладке PDF, не входящей
  в текущий корпус** → Смягчение: проверено на реальных файлах этого
  репозитория; файл с сильно другой раскладкой в будущем ухудшит качество
  чанков, но не сломает индексацию — принято как то, что проверено «на
  имеющихся реальных файлах».
- **Рассинхронизация индекса FAISS и метаданных SQLite** (предполагается общий
  порядок строк) → Смягчение: оба файла пишутся вместе в рамках одного запуска
  CLI на стратегию, через единый шаг «запись во временный путь, затем замена»,
  а `chunk_id`/`faiss_row_id` записываются вместе, так что поиску никогда не
  нужно полагаться на порядок после перезапуска.
- **Рост стоимости полной пересборки по мере роста корпуса** → Принято на
  текущем этапе (Non-Goal: инкрементальная индексация); пересмотреть, если
  корпус вырастет настолько, что полная пересборка станет медленной.

## Migration Plan

Изменение полностью аддитивное — ни одна существующая команда, настройка или
сохранённые данные чатов не меняются. Выкладка: смёржить изменение, поставить
`faiss-cpu` через `pip install -r requirements.txt`, убедиться, что Ollama
запущен и `bge-m3` загружена, один раз выполнить `make index`, чтобы получить
`data/rag_index/`, оставить `RESEARCH=true` (уже значение по умолчанию), чтобы
обе новые команды зарегистрировались. Откат — удалить новые файлы/команды и
`data/rag_index/` — никакой схемы или состояния где-либо ещё разворачивать не
нужно.

## Open Questions

- Точные значения по умолчанию для длины/перекрытия чанка фиксированного
  размера и top-k команды сравнения — это настройка уровня реализации, а не
  поведение уровня спеки; предлагаемые значения по умолчанию заданы в
  `tasks.md`/`.env.example` и могут быть донастроены позже через переменные
  окружения без изменения спеки или этого design.md.
