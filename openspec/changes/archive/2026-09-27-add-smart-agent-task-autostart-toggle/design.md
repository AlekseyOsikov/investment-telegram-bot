# Design

## Context

Мотивация: `proposal.md`; требования: `specs/smart-agent-task-automation/spec.md`.

Что уже есть (проверено по коду `src/agents/smart_agent.py`/`src/agents/smart_agent_command.py`):

- `SmartAgent._enabled_layers` — общий на весь чат словарь `{имя: bool}`, шесть ключей
  (`ALL_LAYERS`), персистится в JSON вместе с профилями (`enabled_layers` верхнего
  уровня, не внутри профиля). При загрузке (`_load_state`) неизвестные ключи из файла
  ОТБРАСЫВАЮТСЯ фильтром `if layer in ALL_LAYERS` — новый ключ обязан попасть в
  `ALL_LAYERS`, иначе сохранённое значение будет молча теряться при каждой перезагрузке.
  Отсутствующий ключ читается как «включён» (дефолт из `_default_enabled_layers()`,
  наложенный ДО обновления сохранёнными значениями) — так уже устроена миграция `tools`,
  без отдельного кода на новый ключ.
- `update_task_state()` — единственное место, где вызывается `_maybe_start_task()`, ровно
  один раз (`if task is None or task_state.is_done(task): return self._maybe_start_task(profile)`).
  Проверка слоя `working` стоит ДО этого, отдельной строкой в начале метода.
- Ручные мутаторы (`start_task`, `set_task_data`, `pause_task`, `resume_task`,
  `set_task_stage`, `finish_task`) не читают `_enabled_layers` вообще — они и сегодня не
  зависят от `working`, поэтому для них в этом изменении ничего не меняется.
- `/smart_agent_toggle` (`smart_agent_command.py`): `LAYER_ALIASES` (ввод пользователя →
  канонический ключ), `LAYER_LABELS` (подпись для ответа и `/smart_agent_show`),
  `LAYER_TOGGLE_HINT` (строка подсказки формата). Тело команды — общий путь
  (`new_value = not agent.get_enabled_layers()[layer]`, `set_layer_enabled`, базовый
  текст ответа), затем `if layer == LAYER_X: text += ...` для двух слоёв, которым нужна
  дополнительная оговорка (`invariants`, `tools`) — тот же шаблон подходит для нового
  флага.
- `/smart_agent_show`: каждая строка статуса написана вручную (не циклом по
  `ALL_LAYERS`), рядом со строкой `2️⃣ Рабочая (…)`.

## Goals / Non-Goals

**Goals:**
- Флаг переключается тем же механизмом, что и остальные шесть пунктов
  (`enabled_layers`/`set_layer_enabled`/`/smart_agent_toggle`), без нового формата
  хранения и без отдельной команды.
- Выключение действует ТОЧЕЧНО: только `_maybe_start_task()`. Всё остальное поведение
  автомата, включая автопродвижение уже идущей задачи, не меняется ни на бит.
- Явно разойтись с термином «слой контекста» там, где это важно для читателя кода:
  флаг — поведенческая настройка автомата, а не участник сборки контекста.

**Non-Goals:**
- Отключение автопродвижения уже идущей задачи (то есть всего технического вызова
  `update_task_state` целиком) — это отдельная, более широкая функциональность,
  обсуждённая и намеренно отклонённая в пользу точечного варианта (см. обсуждение
  перед этим изменением).
- Любые изменения `/smart_agent_task_*`, слоя `working`, конечного автомата (этапы,
  гейты, инварианты) — они не переносятся в спеки этим изменением (см. proposal.md).
- Изменения `AGENT_TASK_START_SYSTEM_PROMPT`/детектора намерения самого по себе — флаг
  лишь решает, вызывать ли его.

## Decisions

### 1. Флаг живёт в `enabled_layers`, а не в отдельной структуре

Три варианта: (а) новый ключ в том же словаре `enabled_layers`/`ALL_LAYERS`; (б) отдельное
поле верхнего уровня в файле памяти (`data["task_autostart"]`, вне `enabled_layers`);
(в) поле внутри самого объекта задачи (`profile["working"]["autostart_enabled"]`).

Выбран (а). Он единственный, где вся инфраструктура (загрузка с фильтром по белому
списку, дефолт при отсутствии ключа, сохранение, `/smart_agent_toggle` как общий
механизм переключения) уже написана и не требует нового кода хранения — остаётся
только описать в докстринге, что не каждый ключ этого словаря участвует в сборке
контекста. Вариант (б) потребовал бы отдельной ветки загрузки/сохранения ради одного
булева значения. Вариант (в) был бы per-profile, а флаг по требованию — общий на чат
(как остальные шесть), и переживал бы удаление/создание профилей менее предсказуемо
(что при отсутствии активного профиля, при создании нового профиля и т.д. — лишние
вопросы там, где в (а) их нет: словарь верхнего уровня существует независимо от
профилей).

Имя ключа: `task_autostart` (константа `LAYER_TASK_AUTOSTART` в `smart_agent.py`, ради
единообразия с `LAYER_WORKING` и остальными, хотя это не слой контекста — комментарий
рядом с `ALL_LAYERS` явно это оговаривает, по аналогии с тем, что комментарий там уже
объясняет отличие `tools` от первых пяти).

### 2. Точка проверки — начало `_maybe_start_task()`, не место вызова

Проверка `if not self._enabled_layers[LAYER_TASK_AUTOSTART]: return None` ставится
ПЕРВОЙ строкой `_maybe_start_task()`, а не условием вокруг единственного вызова в
`update_task_state()`. Разница поведенческая: `_maybe_start_task` вызывается только из
одного места сегодня, но если это изменится, проверка должна остаться внутри функции,
которая и называется «может быть, начать задачу» — так имя функции и её условие входа
не расходятся. `update_task_state()` при этом не меняется вообще: он по-прежнему просто
делегирует решение в `_maybe_start_task`.

### 3. Порядок проверок в `update_task_state()`

`working` остаётся внешним гейтом (если слой выключен, метод выходит раньше, не доходя
до вопроса «есть задача или нет» — как и сегодня). Новый флаг проверяется ГЛУБЖЕ, только
на ветке «задачи нет» — если задача уже идёт, флаг ни на что не влияет (см. Goals).
Итоговый порядок в `update_task_state()`: `active_profile` и `working` → есть ли задача
→ (если нет) `_maybe_start_task()`, который сам проверяет свой флаг → (если есть) пауза →
разбор состояния. Флаг НЕ проверяется в общем начале метода, чтобы не создать искушение
позже сделать его влияющим на что-то ещё.

### 4. Текст `/smart_agent_toggle` и алиас

Канонический ключ `task_autostart`, короткий алиас для ввода — `autostart` (по образцу
`inv` → `invariants`, короткая форма для Telegram). `LAYER_LABELS["task_autostart"]` —
«Автостарт задач (детектор)», чтобы отличаться от подписи слоя «Рабочая» и не звучать
как синоним `working`. Ответ команды получает третью ветку `if layer ==
LAYER_TASK_AUTOSTART`, симметричную `invariants`/`tools`, с явной оговоркой (обе
стороны — включение и выключение), что: (1) это не влияет на слой контекста рабочей
задачи; (2) уже идущая задача продолжает двигаться сама; (3) ручные команды
`/smart_agent_task_*` работают как обычно. Формулировка, а не только факт, важна: без неё
пользователь, включивший флаг обратно, не поймёт, что старая задача всё это время
продолжала жить.

`LAYER_TOGGLE_HINT` расширяется до
`<profile|invariants|short|working|long|tools|autostart>`; текст помощи и докстринг
команды в `smart_agent_command.py` (и в CLAUDE.md) получают уточнение «шесть слоёв
контекста плюс этот флаг» вместо «слой» в общей формулировке — иначе документация
описывала бы флаг как седьмой «слой», хотя requirement явно говорит, что это не слой.

### 5. Строка в `/smart_agent_show`

Добавляется РЯДОМ со строкой `2️⃣ Рабочая (…)`, а не вместо нее и не общим циклом:
`🔁 Автостарт задач: включён/выключен.` — короткая, без цифр (в отличие от «Рабочая»,
где есть краткое содержание задачи). Место выбрано соседним с рабочим слоем, т.к.
семантически связано именно с ним, но не сливается с его строкой статуса — тот
показывает состояние СЛОЯ (включён/выключен в контексте), а не флага автомата, и
смешивать два разных «включён/выключен» в одной строке было бы двусмысленно.

## Risks / Trade-offs

- [Название `task_autostart` внутри `ALL_LAYERS` может читаться как «седьмой слой
  контекста»] → комментарий над `ALL_LAYERS` в коде и формулировка в CLAUDE.md/README
  явно называют его флагом автомата, а не слоем; сам текст ответа команды тоже прямо
  проговаривает границу (см. решение 4).
- [Пользователь выключает флаг, ожидая что это остановит и уже идущую задачу] →
  закрывается формулировкой ответа команды (решение 4) и требованием спеки; тестами не
  покрывается (класс `SmartAgent` тестами не покрыт вовсе), поэтому текст — единственная
  защита, и его нельзя упрощать при доработке.
- [Класс `SmartAgent` не покрыт юнит-тестами] — существующее ограничение проекта (импорт
  `config.py` требует окружения бота, см. CLAUDE.md); проверка ручная, как и остального
  автомата задачи (`tasks.md`).
