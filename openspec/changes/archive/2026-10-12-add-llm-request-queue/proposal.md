# Proposal

## Why

Бот работает с локальной моделью через Ollama, у которой один слот генерации
(`OLLAMA_NUM_PARALLEL=1`, CPU). Сейчас запросы обрабатываются строго по одному, но неявно и
вредно: `handle_message` вызывает синхронный клиент прямо в async-хендлере и замораживает весь
цикл событий на время генерации (до `REQUEST_TIMEOUT_SECONDS`); остальные пользователи не
получают ни статуса, ни оценки ожидания, а повторная отправка лишь множит запросы. Лимитов на
пользователя и на длину очереди нет, а фоновые research-прогоны делят единственный слот с
пользователями и могут сорваться по таймауту (и исказить собственные замеры).

Нужно, чтобы несколько пользователей работали одновременно предсказуемо: бот честно говорит,
сколько ждать, даёт отказаться от ожидания и не позволяет одному пользователю или research-прогону
занять сервер.

## What Changes

- Единая очередь LLM-задач в процессе бота: хендлеры только ставят задачу и сразу возвращаются;
  задачи ждут слот общего шлюза с приоритетами, число одновременных — `LLM_MAX_CONCURRENCY`
  (по умолчанию 1).
- Пользователь, чей вопрос встал в очередь, получает сообщение с оценкой ожидания в виде
  диапазона «примерно X–Y мин» (скользящее среднее времени выполнения по классам задач; верхняя
  граница — по предельному времени запроса). Оценка — на момент постановки, не обещание.
- Новые команды пользователя: `/queue` (нумерованный список своих вопросов с позицией и оценкой)
  и `/queue_cancel [номер]` (без номера снимает все свои вопросы, с номером из `/queue` — один;
  ожидающий снимается с очереди, выполняемый прерывается). `/cancel` НЕ занимается: он остаётся выходом из
  режимов (`/agent`, `/smart_agent`, `/research_*`). Выход из режима по `/cancel` снимает и
  ожидающий вопрос этого чата.
- Настройки оператора в `.env`: `LLM_MAX_CONCURRENCY`, `LLM_MAX_PENDING_PER_USER` (по умолчанию
  1; порядок вопросов одного чата сохраняется), `LLM_QUEUE_MAX` (глубина; сверх неё — немедленный
  отказ «занято»), `LLM_QUEUE_TTL_SECONDS` (вопрос, прождавший дольше, снимается с уведомлением).
- Приоритеты: интерактивные задачи (основной поток, `/agent`, `/smart_agent`, `/agent_compare`)
  выше research-прогонов. Research-прогон (`/research_rag_compare`, `/research_rag_models`)
  берёт слот на один вопрос и пропускает пользователей между вопросами.
- Отмена: из очереди — немедленно; выполняемый вопрос основного потока прерывается отменой
  асинхронного вызова (соединение закрывается, Ollama прекращает генерацию); у `/smart_agent`
  выполняемый `ask()` не прерывается, результат отбрасывается, а слот освобождается по его
  завершении.
- Основной поток переходит на асинхронный клиент, чтобы цикл событий не блокировался.
- Очередь живёт только в памяти: тексты вопросов на диск не пишутся; при перезапуске бота очередь
  теряется (пользователям — повторить вопрос).

Не входит (non-goals): `OLLAMA_NUM_PARALLEL` > 1 — отдельное решение после замера (суммарные ток/с
при 1 и 2; на CPU и MoE-модели выигрыш ожидается умеренным); рантайм-смена модели/провайдера;
сохранение очереди между перезапусками; индивидуальные оценки времени по длине промпта; платные
тарифы/квоты по суммам.

## Capabilities

### New Capabilities
- `llm-request-queue`: очередь LLM-задач — постановка, параллелизм, лимиты (на пользователя,
  глубина, TTL), оценка ожидания, `/queue` и `/queue_cancel`, приоритеты интерактива над
  research, отмена, поведение при отказе «занято».

### Modified Capabilities
- `main-llm-provider`: основной поток и функции основного провайдера обслуживаются через очередь;
  пользователь видит статус ожидания; цикл событий не блокируется вызовом провайдера.
- `rag-answer-comparison`: прогон берёт слот очереди на вопрос с низким приоритетом; отчёт
  отмечает, что в ходе прогона обрабатывались запросы пользователей (формулировку уточнить в
  design).
- `rag-models-comparison`: то же для сравнения моделей; ожидание слота не засчитывается в бюджет
  вопроса и в замер времени.

## Impact

- Код: `src/main.py` (`handle_message`, регистрация `/queue`, `/queue_cancel`, `/help`), новый
  модуль очереди (например, `src/llm_queue/`), `src/config.py` и `.env.example` (4 переменные,
  проверка в `_validate_config()`), `src/agents/*_command.py` (постановка задач вместо прямого
  `ask()`), `src/research/rag_compare.py` и `src/research/rag_models.py` (слот на вопрос),
  `README.md` и `CLAUDE.md` (команды, конфигурация, правила).
- Затронутая гарантия: потокобезопасность `SmartAgent.ask()` сейчас держится на последовательной
  обработке апдейтов (см. докстринг в `smart_agent.py`); новая схема сохраняет её за счёт
  `LLM_MAX_CONCURRENCY=1` и лимита один активный вопрос на чат. При значении > 1 нужна проверка
  (по лимиту на чат инвариант сохраняется).
- Тесты: чистые правила очереди (порядок, приоритеты, лимиты, TTL, оценка) покрываются тестами
  без сети, по принципу проекта; интеграция с Telegram и Ollama проверяется вручную.
- Домен: пользовательский текст в очереди хранится только в памяти; новых данных наружу не
  уходит; `/queue_cancel` — действие над собственным вопросом, а не админ-команда; промпты и
  дисклеймеры не меняются.
