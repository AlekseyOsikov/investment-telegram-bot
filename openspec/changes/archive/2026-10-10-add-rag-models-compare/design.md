# Design

## Context

Мотивация — в `proposal.md`. Состояние кода, от которого отталкивается решение:

- `rag_compare.py` строит ответ свежим изолированным `SmartAgent` (`_answer_mode`), но клиент и
  модель берёт глобально: `_fast_client = main_client.with_options(max_retries=0)` и `MAIN_MODEL`;
  судья (`_judge_call`) тоже вызывает `_fast_client`/`MAIN_MODEL` с
  `disable_thinking_extra_body(MAIN_CLIENT)`.
- `SmartAgent.ask()` ищет материалы САМ (`_search_for_question` → `_retrieve_materials`), то есть
  эмбеддинг вопроса считается на каждую попытку; кэша эмбеддингов нет. Публичный
  `search_materials(text, rewrite, history)` уже возвращает `(Materials, SearchInfo)` без вызова
  модели (его использует сравнение режимов поиска); `Materials` — неизменяемый `dataclass`.
- `SmartAgent.__init__` уже принимает `client=`, `model=`, `rewrite_backend=`; ответ
  (`AgentAnswer`) содержит `context_tokens`, `response_tokens` (суммы по всем вызовам ответа) и
  `llm_calls`. `_chat` основного ответа не передаёт `extra_body` — «thinking» не отключается ни у
  одной модели.
- `ModeResult` уже несёт `elapsed`, токены, `llm_calls`, цитаты, `abstained`, вердикты;
  `Question`, `parse_questions`/`load_questions`, `Verdict`, `parse_judge_response`,
  `call_with_deadline`, `split_text`, `question_failed`-подобная логика — чистый
  `rag_compare_eval.py`.
- Отчёты `/research_rag_compare` — `<UTC>.json` в `RAG_COMPARE_REPORT_DIR`; «последний»
  определяется регулярным выражением `^\d{8}T\d{6}Z\.json$`.
- Kimi отвечает 429 на два одновременных запроса одного аккаунта (`/research_models`).
- Провайдеры: `deepseek_client`, `kimi_client` (`KIMI_MODEL_K3`, `DEEPSEEK_MODEL_FLASH`),
  `ollama_client` (общий `OLLAMA_BASE_URL`).

## Goals / Non-Goals

**Goals:**
- Сравнить N моделей (ожидаемо две) на 3–5 вопросах с RAG: качество, скорость в токенах в секунду,
  стабильность; сохранить все ответы всех повторов.
- Переиспользовать правила оценки и отчёты `rag_compare`, не копируя их; поведение
  `/research_rag_compare` не меняется.

**Non-Goals:**
- Рантайм-выбор модели пользователем чата (пары и судья — только `.env`).
- Сравнение режимов поиска и «без RAG» для каждой модели (это `/research_rag_compare`).
- Стоимость в долларах, нативные метрики Ollama (`eval_duration`), стриминг и время до первого
  токена — вне объёма; метрика скорости одна и одинакова для всех провайдеров.
- Многоходовые вопросы, инструменты рыночных данных, переписывание вопроса.
- Вывод «победителя»: сводка даёт цифры и размер выборки, выводы делает читающий.

## Decisions

### 1. Отдельная команда и модуль, общий каркас оценки

Новые `rag_models.py` (LLM, фоновый прогон, Telegram) и `rag_models_eval.py` (чистые правила:
разбор настроек, выбор вопросов, метрики, агрегаты, формат отчёта и текстов), по образцу пары
`rag_compare.py`/`rag_compare_eval.py`. Из `rag_compare_eval.py` импортируются `Question`,
`load_questions`, `Verdict`, `ModeResult`, разбор ответов судьи, `call_with_deadline`,
`split_text`.

Альтернативы: уровень `models` в `RAG_COMPARE_LEVEL` — отвергнут: уровни взаимоисключающие и
привязаны к «без RAG / с RAG», модуль и так велик, а отчёт другой структуры (повторы, модели).

### 2. Обобщение `rag_compare`: клиент и модель параметром

Вводится небольшой тип `LlmBackend(client, model, provider)` (рядом с `RewriteBackend` по
духу). `_answer_mode`, `_judge_call`, `judge`, `judge_citations` получают необязательный
параметр `backend`; по умолчанию — `main_client`/`MAIN_MODEL`/`MAIN_CLIENT`, то есть поведение
`/research_rag_compare` не меняется. `extra_body` судьи строится по провайдеру бэкенда:
`disable_thinking_extra_body(provider)` (для `ollama` — `None`, как сейчас).
Клиент бэкенда оборачивается `with_options(max_retries=0)` (быстрый отказ, как `_fast_client`).

Альтернатива: дублировать `judge` в новом модуле — отвергнута: правила оценки разошлись бы, а
спека требует «те же правила».

### 3. Настройки оператора и их проверка

`config.py`:
- `RAG_MODELS_COMPARE` — список пар через запятую, `провайдер:модель`; разбор по ПЕРВОМУ двоеточию
  (в имени локальной модели бывают двоеточия: `ollama:gpt-oss:20b`). Пусто по умолчанию.
- `RAG_MODELS_JUDGE` — одна пара, например `kimi:kimi-k3`; пусто по умолчанию.
- `RAG_MODELS_QUESTIONS` (по умолчанию 4, диапазон 1–5; вопрос вне корпуса добавляется сверх
  числа), `RAG_MODELS_REPEATS` (по умолчанию 3, ≥ 1).

Чистая функция разбора и валидации (`rag_models_eval.parse_model_specs`): допустимые провайдеры,
`ollama` требует явной модели, у облачных пустая модель = умолчание провайдера
(`DEEPSEEK_MODEL_FLASH` / `KIMI_MODEL_K3`), не менее двух моделей, дубликаты запрещены. Ошибка
значения настройки — сообщение в чат при запуске команды (как у `RAG_COMPARE_LEVEL`), а не падение
бота при старте; исключение — числовые настройки, которые проверяет `_validate_config()` по
образцу соседних `RAG_COMPARE_*` (бот не должен стартовать с мусором в числе, но и не должен
требовать эту фичу). Ключи облачных провайдеров проверяются при запуске команды, а не при старте
бота.

Модель в настройках — это настройка оператора (как `REWRITE_MODEL`), а не рантайм-выбор
пользователя, поэтому правило «нет рантайм-смены модели» из `CLAUDE.md` не нарушается; в
документации это сказано явно.

### 4. Условия опыта и порядок обращений

Для каждой попытки — свежий `SmartAgent` во временном каталоге (материалы — общие на вопрос,
решение 11): `client`/`model` пары,
`rewrite_backend=None` (переписывание выключено независимо от `REWRITE_PROVIDER`),
`mcp_*_dir=""`, `cbr_enabled=False`, слой `rag` включён. Остальные параметры — рабочие, как в
`_answer_mode`; в отчёт пишутся те же `settings`.

Поиск материалов для вопроса выполняется один раз до попыток и передаётся в каждую (решение 11);
в самом `ask()` поиска в этом режиме нет.

Порядок: внешний цикл по вопросам, внутри — повторы, внутри повтора — по моделям (чередование).
Это снижает смещение из-за дрейфа нагрузки и тепла машины; цена — локальная модель будет
«переключаться» с эмбеддингами (`bge-m3`), что и есть рабочий режим. Холодный старт: первое
обращение к каждой модели в прогоне помечается `cold=true`; прогрев не делается — холодный старт
и есть измеряемая величина.

Судья вызывается после ответа, строго последовательно (лимит Kimi в один запрос), в том же
фоновом потоке вопроса, под тем же бюджетом времени, что и в `rag_compare`. Бюджет вопроса =
`RAG_COMPARE_QUESTION_TIMEOUT_SECONDS` × число моделей × повторы / 2 (в `rag_compare` базовые 120 с
рассчитаны на 2 ответа); отдельная настройка не вводится — используются существующие
`RAG_COMPARE_QUESTION_TIMEOUT_SECONDS` и `RAG_COMPARE_MAX_CONSECUTIVE_FAILURES`.

### 5. Метрика скорости

`tokens_per_second = completion_tokens / elapsed` по `ModeResult` обращения, где
`completion_tokens` — `AgentAnswer.response_tokens` (сумма по всем вызовам ответа),
`elapsed` — время `agent.ask`, в которое при общем поиске (решение 11) поиск не входит: ask
получает готовые материалы, поэтому измеряется только генерация (все вызовы модели в ответе).
Недостаток признан: включает повтор за цитатами (одинаково для всех моделей, виден через
`llm_calls`). Время поиска пишется отдельным полем вопроса. `None` при отсутствии токенов у
провайдера — исключается из агрегатов.

Агрегаты скорости по модели: медиана, минимум, максимум по всем обращениям кроме холодного;
холодное — отдельным полем.

Открытый момент, который СНИМАЕТСЯ первой задачей реализации (живой вызов, не гипотеза): входят ли
токены рассуждений gpt-oss и deepseek в `completion_tokens` (`usage.completion_tokens` у
OpenAI-совместимых API обычно включает их, у Ollama `/v1` — как отдаёт сервер). Результат
записывается в документацию команды; если для одной из моделей токены рассуждений не входят,
сводка помечает это и сравнение скорости называется приблизительным.

**Результат живой проверки (2026-10-09, задачи 1.1–1.2).** `usage` присутствует у обоих
провайдеров, токены рассуждений входят в `completion_tokens` у обоих:
- `ollama:gpt-oss:20b` через `/v1`: `completion_tokens=314` при ~970 символах `reasoning` и ~320
  символах ответа (то есть токены рассуждений посчитаны); `completion_tokens_details` — `null`
  (раздельного учёта нет); `qwen3:30b-a3b` — то же (809 токенов при 2139 символах `reasoning` и
  387 ответа), `usage` есть. Пометка «скорость неизвестна» понадобится только при отсутствии
  `usage`, на проверенных моделях он есть.
- `deepseek-v4-flash`: `completion_tokens=350`, из них `reasoning_tokens=241`
  (`completion_tokens_details`) — входят.
- Через `SmartAgent.ask(materials=…)` с общим поиском: gpt-oss — 326 и 857 токенов за 62 и 68 с
  (5,3 и 12,6 токена/с; второй ответ — с повтором за цитатами, `llm_calls=2`), deepseek — 555 и 665
  токенов за 3,6 и 3,8 с (153 и 176 токена/с). Поиск (один эмбеддинг) — 3,2 с и в `elapsed` не входит.
Вывод: токены в секунду сопоставимы между провайдерами в том смысле, что оба считают токены
рассуждений; сводка всё равно содержит пометку, что токены рассуждений входят в метрику (разная
токенизация моделей — другой источник несопоставимости, он назван там же).

### 6. Метрики качества и стабильности

Качество — вердикт на ответ: `coverage` (доля найденных фактов), `contradicts`, вердикт судьи
цитат, доля проверенных цитат, `abstained` для вопроса вне корпуса; правила — из
`rag_compare_eval` (в том числе исключение из средних ответов, не оценённых судьёй). Агрегат на
модель: среднее покрытие по оценённым ответам, число противоречий, доля ответов с проверенными
цитатами, доля «цитаты не подтверждены», зачёт отказа.

Стабильность: доля успешных обращений (ответ получен), причины сбоев, разброс скорости, разброс
покрытия по повторам для каждого вопроса (min/max), доля неоценённых судьёй. «Успешное» обращение
— ответ получен; сбой судьи считается отдельно.

### 7. Отчёт

JSON `kind="models"` в `RAG_COMPARE_REPORT_DIR`, имя `<UTC>_models.json` (не совпадает с шаблоном
`^\d{8}T\d{6}Z\.json$`, поэтому существующие команды его не видят; для нового чтения — отдельная
функция «последний отчёт моделей» по шаблону `_models.json`). Запись через временный файл +
`os.replace`, как `save_report`.

Структура: `settings` (модели, судья, число вопросов и повторов, настройки поиска, версия формата,
пометка «переписывание выключено»), `models` (ключ, провайдер, модель, подпись), `status`,
`stop_reason`, `planned`, `questions[]` — по каждому вопросу `search` (источники найденных
фрагментов, `search_seconds`, причина сбоя поиска, если был) и `attempts[model_key][repeat]` с
полями `ModeResult.to_dict()` + `tokens_per_second`, `cold`, `judge_error`. Тексты цитируемых
фрагментов в отчёт не пишутся (как сейчас). Объём: 5 вопросов × 3 повтора × 2 модели ≈ 30 ответов
— сотни килобайт.

Чтение: сводка и детали вопроса — разные форматеры; детали выводят повторы рядом по моделям,
длинный вывод делится `split_text` по лимиту Telegram. Отчёт без `kind="models"` или без нужных
полей — `ReportError`/сообщение, не исключение.

### 8. Остановка и единственный прогон

Прогон — фоновая `asyncio`-задача, как в `rag_compare.py`; рабочий поток вопроса принимает
`cancel_event`. Флаг «прогон идёт» ОБЩИЙ с `/research_rag_compare` (оба нагружают Ollama и судью,
Kimi допускает один запрос; общий флаг проще раздельных): флаг и прогресс выносятся в небольшой
общий кусок (функции `is_run_in_progress()`/занять/освободить в `rag_compare.py`, которые
вызывает и `rag_models.py`). Автоостановка — `RAG_COMPARE_MAX_CONSECUTIVE_FAILURES` вопросов
подряд, где ВСЕ обращения завершились сбоем (сбой одной модели — не повод прерывать вторую,
поэтому условие мягче, чем `question_failed`).

### 9. Приватность и доменные правила

Новый поток данных наружу: вопросы, ответы и тексты цитируемых фрагментов — модели-судье; ответы
облачной модели пары строит облачный провайдер (как при `MAIN_CLIENT=deepseek`). Это решение
оператора, оно записано в сводке отчёта и в `CLAUDE.md`. Ответы строит обычный `SmartAgent`:
`SYSTEM_PROMPT`, дисклеймер и правила слоя `rag` не меняются. Новые команды не принимают
свободный текст пользователя, который уходил бы в LLM: набор вопросов — файл оператора.

«Полностью локальный режим» (`MAIN_CLIENT=ollama`, локальные `EMBEDDINGS_BASE_URL`/
`OLLAMA_BASE_URL`, `REWRITE_PROVIDER` пуст или `ollama`) документируется в README/`CLAUDE.md` как
свойство рабочего режима; облачный судья сравнения к нему не относится.

### 10. Специфика Ollama

Параметры `num_ctx`/`keep_alive` через OpenAI-совместимый `/v1` не передаются — задаются
оператором на стороне Ollama (`OLLAMA_CONTEXT_LENGTH`, `OLLAMA_KEEP_ALIVE`,
`OLLAMA_MAX_LOADED_MODELS=2`, чтобы `bge-m3` и чат-модель не вытесняли друг друга; значения
рекомендуются в `.env.example`). Отдельный контейнер Ollama для эмбеддингов НЕ требуется: при двух
моделях такого размера память не ограничивает, а общий поиск (решение 11) сводит число
эмбеддингов к одному на вопрос. Если оператор всё же разнесёт серверы, это уже поддержано
раздельными `EMBEDDINGS_BASE_URL` и `OLLAMA_BASE_URL` без изменений кода. В отчёт
пишутся `prompt_tokens`: значение, упирающееся в потолок контекста, — признак молчаливого усечения
промпта; документация предупреждает об этом. Бот эти параметры не меняет.

### 11. Общий поиск на вопрос

Поиск (эмбеддинг вопроса, кандидаты, второй этап отбора) выполняется ОДИН раз на вопрос
изолированным агентом через существующий `search_materials(question, rewrite=None, history=[])`;
`rewrite_backend=None` — переписывания нет. Полученные `Materials` (неизменяемые) передаются всем
попыткам вопроса — каждой модели и каждому повтору.

`SmartAgent.ask()` получает необязательный параметр `materials: Materials | None = None`: при
переданных материалах `_search_for_question` не вызывается, а блок фрагментов запоминается как
обычно (`_last_rag_block`); весь остальной путь ответа (режим «не знаю», цитаты, повтор за
цитатами, `AgentAnswer`) не меняется. Без параметра поведение прежнее — `/smart_agent`
и `/research_rag_compare` не затрагиваются. Правка небольшая и ограничена одним ветвлением в
начале `ask()`.

Что это даёт: (1) эмбеддингов на прогон по числу вопросов (≈5), а не ≈30; (2) модели получают
БАЙТ-в-БАЙТ одинаковые фрагменты — разница в ответах объясняется генерацией, а не поиском;
(3) `elapsed` и токены в секунду измеряют только генерацию; (4) сбой поиска обнаруживается один
раз на вопрос и не превращается в серию ложных «сбоев моделей» — вопрос исключается из
сравнения с причиной (`rag_context.FAILURE_WARNING` в `Materials.warning`, как в
`/research_rag_compare`).

Время поиска (`search_seconds`) и источники найденных фрагментов пишутся в отчёт на уровне
вопроса, поэтому читающий видит, что обе модели получили одно и то же.

Альтернативы: оставить поиск внутри `ask()` и кэшировать эмбеддинг — отвергнуто: кэш скрыл бы
время поиска только частично и не гарантировал бы одинаковые фрагменты после отбора; отдельный
контейнер/сервер эмбеддингов — решает конкуренцию за память, а не повторы, и здесь не нужен (см.
решение 10).

## Risks / Trade-offs

- [Малая выборка (3–5 вопросов × 3 повтора) даёт шумные цифры] → в сводке всегда указаны число
  вопросов и повторов, разброс по повторам показан, «победитель» не объявляется.
- [Судья kimi-k3 — не нейтрален и не воспроизводим дословно] → оценка вслепую, `temperature=0`,
  сырые ответы всех повторов хранятся и читаются командой отчёта; судья вторично оценивает
  цитаты по фрагментам.
- [Токены рассуждений по-разному учитываются провайдерами → искажение токенов в секунду] →
  проверка живым вызовом в первой задаче, пометка в сводке, документация.
- [Локальная модель и `bge-m3` вытесняют друг друга из памяти → холодные старты искажают
  скорость] → холодное обращение отдельно, чередование моделей, рекомендации по
  `OLLAMA_KEEP_ALIVE` и `OLLAMA_MAX_LOADED_MODELS`.
- [Скорость включает повтор за цитатами и сеть до облака] → поиск в скорость не входит (решение
  11), но повтор за цитатами и сетевая задержка входят: метрика «время ответа модели», а не
  «чистая генерация»; `llm_calls` показывает повторы.
- [Общий поиск не воспроизводит рабочий путь буквально — в нём эмбеддинг считается внутри
  `ask()`] → поиск использует те же настройки и тот же `search_materials`, что и
  сравнение режимов поиска; различие касается только места вызова. Задержка поиска в рабочем
  режиме видна в отдельном поле отчёта.
- [Правка `SmartAgent.ask()` затрагивает основной модуль агента] → параметр необязательный,
  одно ветвление; проверка вручную `/smart_agent` с RAG и `/research_rag_compare` после правки.
- [Прогон занимает минуты, блокирует Kimi/Ollama] → единственный прогон на бот, остановка
  командой, пределы времени по часам.
- [Рефакторинг `rag_compare` ломает существующую команду] → параметр с умолчанием, существующие
  тесты чистых функций проходят без изменений, ручной прогон `/research_rag_compare` на
  небольшом наборе.
- [Облачный судья получает фрагменты корпуса] → решение оператора, отражено в сводке и
  документации; фрагменты не пишутся в отчёт.
