# Design

## Context

`MAIN_CLIENT` (`config.py`) сейчас принимает `deepseek|kimi`; `providers/main_client.py` выбирает
`deepseek_client` или `kimi_client` тернарным выражением. От `MAIN_CLIENT` зависят: дефолт
`MAIN_MODEL`, `MAIN_CLIENT_LABEL`, `MAIN_API_KEY_ENV_VAR`, проверка допустимости в
`_validate_config()` и обязательность ключа в `deepseek_client.py`/`kimi_client.py`. Все
потребители (`main.py`, `Agent`, `SmartAgent`, research-режимы) используют общий `main_client`
(OpenAI SDK), поэтому достаточно подменить клиента. `providers/ollama_client.py` уже даёт
OpenAI-совместимый клиент к Ollama (`OLLAMA_BASE_URL`, `trust_env=False`, без ключа) для
переписывания вопроса. Мотивация — см. proposal.md.

## Goals / Non-Goals

**Goals:**
- `MAIN_CLIENT=ollama` + `MAIN_MODEL=<локальная модель>` запускает бота целиком без облачных ключей.
- Минимум нового кода: переиспользовать `ollama_client` и существующую структуру конфигурации.

**Non-Goals:**
- Рантайм-смена провайдера/модели пользователем (запрещено CLAUDE.md).
- Fallback «облако ↔ локально» на лету, несколько моделей одновременно.
- Включение Ollama в `/research_models` (он сравнивает облачные пары и не зависит от `MAIN_CLIENT`).
- Калибровка и проверка качества конкретных локальных моделей; выбор модели — за оператором.

## Decisions

1. **Третье значение `ollama` в `MAIN_CLIENT`**, а не отдельная переменная. Соответствует просьбе
   («MAIN_CLIENT, MAIN_MODEL») и текущему паттерну. Альтернатива — `MAIN_BASE_URL` для любого
   OpenAI-совместимого сервера: шире, но размывает проверки ключей и подписи; отложено.

2. **Клиент — существующий `ollama_client`**, `main_client = ollama_client` в
   `providers/main_client.py`. Общий `OLLAMA_BASE_URL` для основного потока и переписывания: один
   локальный сервер, отдельный адрес не нужен. Альтернатива — второй клиент с `MAIN_BASE_URL`: лишняя
   настройка без запроса.

3. **`MAIN_MODEL` обязателен для `ollama`** (дефолта нет): имена локальных моделей зависят от
   установленных у оператора, неверный дефолт давал бы ошибку 404 только при первом вопросе.
   Проверка — в `_validate_config()` (`sys.exit(1)`, как остальные). Альтернатива — дефолт вроде
   `qwen3` : отвергнута как скрытая зависимость от того, что модель скачана.

4. **Ключи.** `deepseek_client.py`/`kimi_client.py` уже падают только при `MAIN_CLIENT == своё
   значение`; при `ollama` оба идут по ветке предупреждения. Текст предупреждения («основной поток
   работает через Kimi») неверен для `ollama` — сделать его нейтральным.

5. **Подписи.** `MAIN_CLIENT_LABEL`/`MAIN_API_KEY_ENV_VAR` строятся словарями по `MAIN_CLIENT`
   вместо тернарников; для `ollama` — `"Ollama"` и `OLLAMA_BASE_URL`. Тексты ошибок в
   `main.py`/`research/_shared.py` остаются раздельными по типам исключений; для `ollama`
   добавляется отдельная формулировка `APIConnectionError` («запущен ли Ollama и загружена ли
   модель»), `AuthenticationError` для Ollama практически невозможна и остаётся общей.
   Альтернатива — хранить тексты подсказок в словаре провайдера: пока достаточно условия.

6. **Параметры, специфичные для облака, не уходят в Ollama.** Сейчас только `extra_body=
   {"thinking": ...}` в переписывании (уже условное по `provider`). Основной поток и `Agent`/
   `SmartAgent` таких параметров не шлют (проверить при реализации grep'ом). `response_format=
   json_object` Ollama поддерживает через OpenAI-совместимый эндпоинт; при невалидном JSON
   работают существующие откаты автопамяти.

7. **Tool calling (`tools` у `/smart_agent`)** зависит от модели: часть моделей Ollama не
   поддерживает инструменты и вернёт ошибку статуса. Новой логики не добавляем — используется
   существующая обработка сбоя слоя; оператор выбирает модель с поддержкой tools или отключает
   слой. Это фиксируется в документации, не в коде.

8. **Приватность и безопасность.** Выбор провайдера остаётся настройкой оператора; новых
   пользовательских команд и каналов данных нет. При локальном адресе данные не покидают машину;
   при удалённом `OLLAMA_BASE_URL` уходят на него — решение оператора, отмечается в CLAUDE.md
   рядом с описанием каналов данных.

## Risks / Trade-offs

- [Локальные модели слабее, чаще нарушают формат/нужны «осторожные формулировки»] →
  `SYSTEM_PROMPT` и дисклеймер не меняются; в README рекомендовать проверить ответы на
  типовых вопросах; ответственность выбора модели — оператор.
- [Долгая генерация на CPU → тайм-ауты Telegram-UX] → `ChatAction.TYPING` уже есть; таймаут SDK по
  умолчанию (600 с) достаточен; при необходимости отдельная настройка — вне scope.
- [Контекст локальной модели мал (`num_ctx` Ollama по умолчанию), длинные промпты `SmartAgent`
  усекаются молча] → описать в `.env.example`/README необходимость увеличить `num_ctx`/
  `OLLAMA_CONTEXT_LENGTH` на стороне Ollama.
- [Пороги RAG откалиброваны под эмбеддинги, не под модель ответа] → смена основной модели их не
  затрагивает.
- [Загрузка модели при первом вопросе — долгий ответ] → `OLLAMA_KEEP_ALIVE` на стороне Ollama (уже
  упомянуто в `.env.example`).

## Migration Plan

Обратно совместимо: существующие `.env` с `deepseek`/`kimi` работают без изменений. Включение —
добавить `MAIN_CLIENT=ollama`, `MAIN_MODEL=<модель>` и перезапустить. Откат — вернуть прежние значения.
