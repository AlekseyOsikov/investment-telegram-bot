# Design

## Context

Мотивация и состав — `proposal.md`; требования — `specs/`. Что есть в коде сейчас:

- Основной поток (`main.py: handle_message`) и `/agent`, `/agent_compare` (`agent_command.py`,
  `compare_command.py`) вызывают синхронный OpenAI-клиент ПРЯМО в async-хендлере: цикл событий
  заморожен на время генерации. `/smart_agent` вызывает `SmartAgent.ask` через `asyncio.to_thread`,
  но хендлер всё равно ждёт результат, а PTB обрабатывает обновления последовательно.
- Потокобезопасность `SmartAgent` держится именно на последовательности апдейтов (докстринг
  `SmartAgent.ask`).
- Research-прогоны (`rag_compare.py`, `rag_models.py`) — фоновые `asyncio`-задачи; каждый вопрос
  набора — один вызов `asyncio.to_thread(evaluate_question, ...)`. Бюджет вопроса измеряется
  часами внутри `evaluate_question`. Это естественная граница слота.
- Короткие research-сценарии (`constraints`, `reasoning`, `temperature`, `models`) выполняют
  запрос синхронно в хендлере через `run_scenario` (`research/_shared.py`).
- Ollama в Docker: `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_QUEUE=512`; запросы сверх параллелизма
  встают во внутреннюю FIFO Ollama; CPU, 16 потоков.
- Исключения SDK переводятся в сообщения по месту (`try/except` в хендлерах), с `MAIN_CLIENT_LABEL`.

## Goals / Non-Goals

**Goals:**
- Несколько пользователей работают одновременно без заморозки бота; ожидание видно и управляемо.
- Один слот модели — всегда занят ровно одной задачей (при `LLM_MAX_CONCURRENCY=1`): никаких
  скрытых очередей внутри Ollama и искажения замеров исследований.
- Инвариант потокобезопасности `SmartAgent` не слабеет.

**Non-Goals:**
- Не менять `OLLAMA_NUM_PARALLEL` и не оценивать выигрыш от него (отдельный замер).
- Не вводить `concurrent_updates` и блокировки на чат внутри `SmartAgent`.
- Не сохранять очередь и не делать оценку по длине промпта.
- Не менять промпты, `SYSTEM_PROMPT`, дисклеймеры и состав данных, уходящих провайдерам.

## Decisions

### 1. Шлюз с приоритетами и асинхронные задачи, а не отдельный worker-цикл

Новый пакет `src/llm_queue/`:
- `rules.py` — ЧИСТЫЕ правила (тесты без сети): порядок и позиция (приоритет, затем FIFO),
  скользящая статистика времени, оценка диапазона, формат текста оценки, проверка лимитов.
- `gate.py` — `LlmGate(concurrency)`: асинхронный шлюз слотов с приоритетной очередью ожидающих
  (`acquire(priority, chat_id, kind)` → контекстный менеджер), реестр задач по чатам, метрики.
- `commands.py` — `/queue`, `/queue_cancel`, `build_queue_handlers()` для `main.py`.

Задача пользователя — отдельная `asyncio`-задача, которая ждёт слот, выполняет работу и
отправляет ответ. Альтернатива «единственный worker, разбирающий очередь корутин» отвергнута:
шаги исследований и задачи хендлеров всё равно нужны под одним ограничителем, а шлюз с
`acquire()` даёт это одним механизмом, и отмена ожидания/выполнения — обычная отмена задачи.

### 2. Хендлеры ставят задачу и сразу возвращаются (без `concurrent_updates`)

`handle_message`, `agent_receive_question`, `agent_compare_receive_question`,
`smart_agent_receive_question` проверяют ввод (длина, активный профиль и т. п. — как сейчас),
вызывают `gate.submit(...)` и возвращают то же состояние диалога. Блок «вызов LLM → перевод
ошибок → отправка ответа» переносится в корутину задачи без изменения текстов. Так:
- PTB остаётся последовательным, `/queue` и `/queue_cancel` обрабатываются сразу;
- `SmartAgent.ask` по-прежнему вызывается не более чем из одного места одновременно для чата;
- ConversationHandler не зависит от порядка завершения долгих хендлеров.

Альтернатива: `concurrent_updates=True` + `await queue.run(...)` в хендлере. Отвергнута: меняет
гарантии PTB для ВСЕХ обработчиков (диалоги, анкеты), требует блокировок на чат в `SmartAgent`.

### 3. Один активный вопрос на чат — замок чата и лимит

Реестр `{chat_id: [job]}` (список в порядке отправки; его индекс + 1 — номер вопроса, который
показывает `/queue` и принимает `/queue_cancel <n>`; номера нигде не хранятся и пересчитываются
при каждом обращении, поэтому чужие вопросы по номеру недостижимы). `/queue_cancel` без аргумента
снимает все задачи чата, с номером — одну; нечисловой или несуществующий номер ничего не
отменяет и возвращает подсказку. Список в `/queue` содержит начало текста вопроса (несколько
слов) только из памяти очереди. `LLM_MAX_PENDING_PER_USER` (по умолчанию 1) проверяется до
постановки.
Внутри задачи ПЕРЕД слотом берётся `asyncio.Lock` чата: порядок вопросов чата сохраняется и при
`LLM_MAX_CONCURRENCY > 1` одна и та же память агента не используется из двух потоков.

### 4. Слот освобождается по факту завершения работы

Отмена `asyncio`-задачи не останавливает поток из `asyncio.to_thread`. Поэтому:
- асинхронный клиент (основной поток): отмена прерывает `await`, соединение закрывается, Ollama
  прекращает генерацию — слот освобождается сразу;
- поток (`SmartAgent.ask`, `Agent.ask`, шаги исследования): задача, получив отмену, НЕ освобождает
  слот; освобождение вешается на завершение будущего потока (`add_done_callback`). Иначе новая
  задача запустилась бы параллельно доживающему потоку, нарушив `LLM_MAX_CONCURRENCY`.

### 5. Кооперативная отмена вопросов агентов с памятью

Прервать `ask()` посреди LLM-вызова нельзя, но недопустимо, чтобы отменённый вопрос потом
записался в память пользователя (память видима и управляема самим пользователем). Поэтому
`SmartAgent.ask` и `Agent.ask` получают необязательный `should_cancel: Callable[[], bool]`:
проверяется перед каждым LLM-вызовом, перед следующей итерацией цикла инструментов и ПЕРЕД
записью пары в память/историю; при `True` бросается `AskCancelled` (исключение проекта), состояние
не меняется. После начала записи отмена не действует; задача сообщает пользователю, что обмен уже
сохранён. Технические вызовы после ответа (автомат задачи) тоже проверяют флаг до начала.

### 6. Асинхронный клиент для основного потока

В `providers/main_client.py` добавляется `async_main_client` (`AsyncOpenAI`, тот же выбор
провайдера и те же параметры, `httpx.AsyncClient(trust_env=False)` для Ollama — как у синхронного
клиента). Им пользуется только `handle_message`. Остальное (`SmartAgent`, `Agent`, research)
остаётся на синхронном клиенте в потоках: переписывать их на async не нужно и не входит в
изменение. `/agent` и `/agent_compare` переводятся на `asyncio.to_thread` (они сейчас блокируют
цикл).

### 7. Оценка времени

`rules.py` хранит по виду задачи (`main`, `agent`, `compare`, `smart_agent`, `research`) окно
последних 20 длительностей выполнения (с момента получения слота до завершения, включая
неуспешные). Оценка ответа для позиции `p` при параллелизме `K`: `ceil(p / K)` задач впереди
плюс своя. Нижняя граница — медиана окна, верхняя — 90-й процентиль; при менее чем 3 измерениях
нижняя граница не показывается, верхняя — `REQUEST_TIMEOUT_SECONDS`. Для впереди стоящих задач
другого вида берётся статистика их вида (впереди `smart_agent` и свой `main` складываются
по-разному). Результат округляется вверх до минуты и подаётся как «примерно X–Y мин» с оговоркой.
Позиция и оценка вычисляются в момент постановки и по `/queue`; сообщение не редактируется.

### 8. Приоритеты и исследования

Два приоритета: `INTERACTIVE` (0) и `RESEARCH` (1); внутри — FIFO. Исследование берёт слот на
один вопрос набора: `async with gate.slot(RESEARCH): await asyncio.to_thread(evaluate_question…)`
(п. 4 — освобождение по завершению потока, если прогон остановлен). Бюджет вопроса отсчитывается
внутри `evaluate_question` и стартует после получения слота; время ожидания и число вопросов
пользователей, обработанных за прогон (счётчики шлюза «с начала прогона»), записываются в отчёт
отдельными полями (старые отчёты читаются как раньше). Короткие research-сценарии
(`constraints`/`reasoning`/`temperature`/`models`) выполняются как задачи вида `research` с
приоритетом `RESEARCH`; для них `run_scenario` вызывается в потоке под слотом.

Голодание: при постоянной нагрузке пользователей исследование идёт только в промежутках.
Это принято (исследования запускает оператор, когда бот свободен); «старение» приоритета не
вводится.

### 9. Ограничения глубины и срока

`LLM_QUEUE_MAX` — число ожидающих (не считая выполняемых) задач вида «интерактив»; исследования
не входят (их не больше одного прогона). `LLM_QUEUE_TTL_SECONDS` — ожидание слота через
`asyncio.wait_for(acquire, ttl)` только для интерактивных задач; при истечении — уведомление.

### 10. Параллелизм согласуется с сервером модели

`LLM_MAX_CONCURRENCY` документируется рядом с `OLLAMA_NUM_PARALLEL`; бот серверу значение не
передаёт и не проверяет. Рассинхронизация (бот > сервер) лишь переносит очередь внутрь Ollama и
делает оценку неверной.

### 11. Выход из режима

`_exit_agent_mode`, `_exit_smart_agent_mode`, `_exit_compare_mode` и `/cancel`-fallback вызывают
`gate.cancel_chat(chat_id, reason="exit")` до выхода: те же правила, что у `/queue_cancel`.

## Risks / Trade-offs

- [Отменённый поток доживает до конца LLM-вызова и занимает слот] → слот освобождается по
  завершению; для `/smart_agent` отмена кооперативна между вызовами; пользователю сообщается
  «вопрос снят, слот освободится по завершении текущего вызова» (формулировка в `tasks.md`).
- [Оценка неточна: время ответа `/smart_agent` зависит от числа вызовов и рассуждений] →
  диапазон по процентилям и по видам задач, оговорка «примерно»; без данных — верхняя граница по
  таймауту.
- [Очередь теряется при перезапуске] → принято (stateless), пользователь повторяет вопрос.
- [Голодание исследований при постоянной нагрузке] → принято; оператор запускает прогон в тихое
  время; число и время ожидания видны в отчёте.
- [Рефакторинг хендлеров: перенос `try/except` в корутину задачи может изменить тексты или
  состояния диалога] → механический перенос без изменения строк; проверка вручную по списку
  сценариев в `tasks.md`; тексты ошибок не трогаются.
- [`/agent_compare` отправляет три параллельных запроса под одним слотом] → при
  `NUM_PARALLEL=1` Ollama выполнит их по очереди; длительность задачи учитывается в статистике
  вида `compare`.
- [Параллелизм > 1 без замера на CPU может ухудшить скорость каждого запроса] → по умолчанию 1;
  изменение — решение оператора после замера, вне этого изменения.

## Migration Plan

1. Добавить пакет `llm_queue/`, настройки и `async_main_client` (поведение бота не меняется).
2. Перевести основной поток, затем `/agent`, `/agent_compare`, `/smart_agent`, затем research.
3. Включить `/queue` и `/queue_cancel`, обновить `/help`, README, CLAUDE.md, `.env.example`.
4. Откат — возврат к предыдущему коммиту; данных на диске новое изменение не создаёт, миграций нет.

Значения по умолчанию (`LLM_MAX_CONCURRENCY=1`, `LLM_MAX_PENDING_PER_USER=1`) сохраняют прежнюю
последовательность обработки, но без заморозки цикла событий.
