# Design

## Context

Мотивация и состав изменения — `proposal.md`, требования — дельта-спеки. Исходное состояние:

- `SmartAgent._retrieve_materials()` (`agents/smart_agent.py`): `embed_texts([вопрос], budget)` →
  `index_store.search(strategy, dir, vector, RAG_TOP_K)` → `rag_context.filter_by_score(found,
  RAG_MIN_SCORE)`. Порог режет те же K чанков, что вернул поиск.
- Параметры поиска у `SmartAgent` приходят через конструктор (`rag_top_k`, `rag_min_score`, …) —
  это позволяет `/research_rag_compare` собирать агентов с разными настройками без правки
  `config.py`.
- Провайдеры: `deepseek_client.py`/`kimi_client.py` (клиенты `OpenAI`), `main_client.py`
  (выбор по `MAIN_CLIENT`), `embeddings_client.py` (Ollama-эмбеддинги, не связан с
  `MAIN_CLIENT`). Правило проекта: ключ выбранного провайдера обязателен, невыбранного —
  опционален.
- Оборудование оператора: в локальном Ollama есть `qwen2.5:7b`, `llama3.1:8b`,
  `rscr/vikhr_llama3.1_8b`, `OxW/Vikhr-Nemo-12B-Instruct-R`, `llama3.2:1b` и эмбеддинги
  (`bge-m3`, `nomic-embed-text`). Сервер отдаёт OpenAI-совместимый `/v1`.
- Контрольный набор (`data/rag_eval/questions.json`, 10 вопросов с `facts` и `sources`) и
  отчёты `/research_rag_compare` лежат в `data/` и не коммитятся.

## Goals / Non-Goals

**Goals:**
- Отбор «шире → уже» на рабочем пути без новых вызовов моделей и сети.
- Необязательный rewrite через провайдера на выбор оператора (`ollama`/`deepseek`/`kimi`),
  выключенный по умолчанию, с безопасным откатом.
- Измеримость: каждый шаг отбора и rewrite можно включать по отдельности, сравнение режимов
  дешёвыми метриками поиска и (опционально) оценкой ответов.

**Non-Goals:**
- Cross-encoder и LLM-реранкер (оставлены как возможное продолжение, если эвристик
  окажется мало; отдельное решение — тяжёлая зависимость или вызов LLM на каждый вопрос).
- Multi-query, HyDE, гибридный (BM25) поиск; изменение чанкинга и формата индекса.
- Пользовательские команды для rewrite/отбора и рантайм-смена моделей.
- Переписывание вопросов вне слоя `rag` у `/smart_agent`.

## Decisions

### 1. Второй этап — чистый модуль без обращений наружу

Правила отбора — функции в `agents/rag_context.py` (рядом с `filter_by_score`, тесты —
`tests/test_rag_context.py`): `select_chunks(candidates, settings) -> Selection`. Вход —
кандидаты в порядке убывания близости, выход — отобранные чанки и счётчики отброшенных по
причинам (порог, относительный порог, короткий, дубликат, предел на документ) — для отчёта и
`/smart_agent_show`. Шаги применяются в фиксированном порядке:

```
кандидаты (N, по убыванию score)
  1. score >= RAG_MIN_SCORE
  2. score >= top1 - RAG_RELATIVE_MARGIN          (top1 — лучший ПОСЛЕ шага 1)
  3. len(text) >= RAG_MIN_CHUNK_CHARS
  4. дедупликация (нормализованный текст)
  5. не более RAG_MAX_PER_DOC на документ (title)
  6. первые RAG_TOP_K
```

Нейтральные значения отключают шаг: `RAG_RELATIVE_MARGIN=1` (>= любой разницы близости
косинуса), `RAG_MIN_CHUNK_CHARS=0`, `RAG_MAX_PER_DOC` = `RAG_TOP_K`. При `RAG_CANDIDATES =
RAG_TOP_K` и нейтральных шагах результат совпадает с прежним — это режим «как до изменения»
и тест на совместимость.

Альтернативы: реранкер-модель (дорого и тяжёлая зависимость, см. Non-Goals); одна «умная»
формула со взвешенной суммой признаков (нечитаема, её нельзя калибровать по шагам).
`top1` берётся после порога, чтобы относительный порог не зависел от кандидатов, уже
отсеянных абсолютным.

Значения по умолчанию подбираются калибровкой (задача 7), а не из головы: предварительно
`RAG_CANDIDATES=10`, `RAG_TOP_K=3`, `RAG_RELATIVE_MARGIN=0.08`, `RAG_MIN_CHUNK_CHARS=120`,
`RAG_MAX_PER_DOC=2`. Если после калибровки выигрыша нет, шаг остаётся в коде с нейтральным
значением по умолчанию — выбор за измерением.

`RAG_MIN_CHUNK_CHARS` опирается на известную слабость структурного чанкинга: на PDF-слайдах
эвристика заголовков даёт мелкие чанки (`src/rag/CLAUDE.md`), которые часто имеют высокую
близость к вопросу благодаря терминам, но не содержат ответа.

### 2. Rewrite — отдельный модуль и отдельный клиент

- `providers/ollama_client.py`: `OpenAI(api_key="ollama", base_url=OLLAMA_BASE_URL)` —
  локальный Ollama не проверяет ключ, но конструктор SDK требует непустой. `OLLAMA_BASE_URL`
  по умолчанию `http://localhost:11434/v1`; независим от `EMBEDDINGS_BASE_URL` (как
  `MAIN_CLIENT` не связан с эмбеддингами: оператор может держать чат и эмбеддинги на разных
  серверах).
- `providers/rewrite_client.py` (по образцу `main_client.py`): по `REWRITE_PROVIDER` отдаёт
  `(client, model)` или `None`, если провайдер не задан либо у `deepseek`/`kimi` нет ключа.
  Не в `config.py` — тот же довод про цикл импорта. Значения по умолчанию модели: для
  `deepseek`/`kimi` — `DEEPSEEK_MODEL_FLASH` / `KIMI_MODEL_K2_6` (быстрые), не `MAIN_MODEL`:
  rewrite должен быть дешёвым и не зависеть от провайдера основного потока.
- Правила — чистый модуль `agents/rag_rewrite.py`: промпт, сборка сообщений (system + user с
  вопросом), нормализация ответа (обрезка пробелов и кавычек, одна строка, предел длины,
  отбраковка пустого и явных «отказов» вида «Извините…»). Тесты — чистые функции.
- Вызов — `SmartAgent._rewrite_query(text) -> str | None` в `ask()` до эмбеддинга;
  таймаут — `REWRITE_TIMEOUT_SECONDS` (по умолчанию 8 с, отдельно от бюджета эмбеддинга 5 с),
  без автоповторов (клиент с `max_retries=0` для вызова), `max_tokens` небольшой.
  `temperature=0` для воспроизводимости сравнения.

**Промпт rewrite.** Просит: сохранить смысл, вернуть ОДНУ строку — поисковый запрос на русском
по инвестиционной теме, раскрыть аббревиатуры и разговорные обороты терминами, не отвечать на
вопрос, не добавлять сведений, которых нет в вопросе, не выдавать рекомендаций. Вопрос
подаётся как данные (разделитель), чтобы встроенные в него инструкции не выполнялись. В
промпте нет слов, ослабляющих `SYSTEM_PROMPT`, и он не описывает сам корпус (чтобы не
содержать названий документов — правило проекта).

Альтернативы: rewrite как часть уже существующего служебного вызова (смешивает
ответственность, ломает «материалы только основному ответу»); rewrite только в research (отвергнуто
решением владельца — рабочий путь).

### 3. Поиск по переписанному запросу, исходный — запасной

Основной вариант — искать только по переписанному запросу, при сбое — по исходному. Режим
объединения кандидатов по двум эмбеддингам (исходный + переписанный, слияние по лучшей оценке)
— защита от плохого rewrite у слабой модели, стоит ещё одного эмбеддинга (десятки миллисекунд
у локального `bge-m3`). Решение не принимается заранее: переменная
`REWRITE_SEARCH_MODE` (`rewritten` по умолчанию | `both`) попадает в сравнение режимов (см. 6),
и по метрикам выбирается значение по умолчанию. Оценка близости при слиянии — наибольшая из
двух, в строке источников показывается она же (исходная оценка поиска, а не производная —
требование спеки).

### 4. Порог и калибровка

Rewrite меняет распределение близостей (переписанный запрос ближе к терминам корпуса), поэтому
`RAG_MIN_SCORE` калибруется заново: `scripts/rag_calibrate.py` получает флаг `--rewrite`
(использует тот же `rag_rewrite` и клиент) и печатает близость top-1 без и с rewrite по
группам A/B/C. Порог определяется по группе C (не по теме) при включённом rewrite. Результаты
пишутся в раздел «Калибровка» этого `design.md` при приёмке — как в
`add-smart-agent-rag`.

### 5. Конфигурация и проверка при запуске

Новые переменные (`config.py`, документируются в `.env.example`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `RAG_CANDIDATES` | 10 | число кандидатов поиска, >= `RAG_TOP_K` |
| `RAG_RELATIVE_MARGIN` | 0.08 | относительный порог; 1 — выключен |
| `RAG_MIN_CHUNK_CHARS` | 120 | минимальная длина чанка; 0 — выключен |
| `RAG_MAX_PER_DOC` | 2 | предел чанков документа; >= `RAG_TOP_K` — выключен |
| `REWRITE_PROVIDER` | пусто | `ollama`/`deepseek`/`kimi`; пусто — rewrite выключен |
| `REWRITE_MODEL` | по провайдеру | для `ollama` обязательна |
| `REWRITE_TIMEOUT_SECONDS` | 8 | предел ожидания вызова |
| `REWRITE_SEARCH_MODE` | `rewritten` | `rewritten` или `both` (решение 3) |
| `RAG_COMPARE_MODES` | все доступные | режимы прогона `/research_rag_compare` (решение 6) |
| `OLLAMA_BASE_URL` | `http://localhost:11434/v1` | адрес чат-сервера Ollama |

`_validate_config()` проверяет диапазоны, `RAG_CANDIDATES >= RAG_TOP_K`, допустимость
`REWRITE_PROVIDER`/`REWRITE_SEARCH_MODE` и модель для `ollama` — как существующие проверки
`RAG_*`. Отсутствие ключа `deepseek`/`kimi` для rewrite — предупреждение при запуске, не
`sys.exit` (rewrite — вспомогательная необязательная функция: отсутствие ключа не должно останавливать
бот, который без неё полностью работоспособен). Старые `.env` работают без правок: rewrite
выключен, а шаги отбора при значениях по умолчанию действуют сразу (см. План миграции).

### 6. Сравнение режимов

`rag_compare` уже собирает `SmartAgent` с настройками из конструктора, поэтому режим —
это набор параметров, а не ветка в агенте:

```
mode              candidates  steps(2-й этап)   rewrite
baseline          = TOP_K     только порог      нет        (как до изменения)
filter            RAG_CAND    все шаги          нет
rewrite           = TOP_K     только порог      да
rewrite+filter    RAG_CAND    все шаги          да         (рабочий)
off               слой rag выключен                         (уже есть)
```

Два уровня прогона (оператор выбирает настройкой/аргументом команды):

- **Поиск без LLM-ответов**: для каждого вопроса и режима — поиск (с rewrite, если режим
  его требует) и метрики: попадание в ожидаемый источник, позиция, число чанков, доля чанков
  не из ожидаемых источников. Секунды на режим; чистые функции метрик — в
  `research/rag_compare_eval.py` (там уже есть сопоставление источников по префиксу заголовка
  и покрытие индекса). Модель ответа и оценщик не вызываются.
- **С оценкой ответов**: как нынешний прогон, но по режимам; оценщик вслепую.

Кэш: rewrite результат на вопрос не зависит от режима отбора, поэтому в прогоне
переписывается один раз на вопрос и переиспользуется (и фиксируется в отчёте — воспроизводимо
и дешевле).

Отчёты — тот же каталог `RAG_COMPARE_REPORT_DIR`, тот же формат с добавлением поля
`modes`; `/research_rag_compare_report` показывает его же. Конкретные команды/аргументы
выбора режимов — в задачах: режимы задаёт оператор настройкой `RAG_COMPARE_MODES`, уровень
прогона («только поиск» / «с оценкой ответов») — тоже настройкой, пользовательских параметров
в чате нет.

Спека `rag-answer-comparison` и код `/research_rag_compare` уже в `main`; дельта этого
изменения не перекрывает их, а добавляет `rag-retrieval-comparison`.

### 7. Видимость

Строка источников под ответом остаётся прежней (документ, фрагмент, исходная близость) —
пользователь видит те же факты. `/smart_agent_show` дополняется: поисковый текст (с пометкой
«без переписывания» / «переписывание не удалось: причина»), число кандидатов и отобранных,
счётчики отброшенных по шагам. Данные — в памяти агента (как `_last_rag_block`), на диск не
пишутся (требование «материалы не попадают в память» сохраняется).

### 8. Границы данных и безопасность

- Rewrite-провайдеру — только вопрос и неизменный служебный промпт (не память, не профиль, не
  инварианты, не чанки). Для `deepseek`/`kimi` вопрос уходит облаку на шаг раньше основного
  ответа — новый канал данных, решение оператора; фиксируется в `/CLAUDE.md` рядом с оговоркой
  об эмбеддингах, в `.env.example` — рекомендация `ollama` для вопросов, не покидающих машину.
- Это не рантайм-смена провайдера/модели/промпта: выбор в `.env`, перезапуск, пользователь не
  управляет; промпт rewrite — константа в коде. Серверам и моделям выбора пользователя нет.
- Результат rewrite — только поисковый запрос; в основной ответ, память и источники идёт
  исходный вопрос. Промпт-инъекция внутри вопроса может повлиять лишь на поисковый запрос
  (нормализация ограничивает длину и формат), но не на ответ и не на `SYSTEM_PROMPT`.
- Дисклеймеры и осторожные формулировки не затрагиваются: rewrite не формирует ответ
  пользователю, правила материалов и `SYSTEM_PROMPT` остаются прежними.
- Не добавляются: сбор данных пользователя, новые хранилища, команды.

### 9. Сбои

Любой сбой rewrite (недоступный сервер, таймаут, исключение SDK, пустой/недопустимый ответ)
→ поиск по исходному вопросу, причина — в `_last_rewrite_failure` для `/smart_agent_show`,
в `SmartAgentAnswer.warnings` НЕ попадает (пользователю не нужно знать про необязательную
оптимизацию). Следующий вопрос пробует снова. Сбой поиска остаётся прежним (предупреждение).
Для `ollama` холодный старт модели (загрузка в память на десятки секунд) укладывается в
таймаут редко — первый вопрос после простоя идёт без rewrite; прогрев — на усмотрение
оператора (`OLLAMA_KEEP_ALIVE`, документируется).

## Risks / Trade-offs

- [Латентность: +1 вызов LLM на вопрос] → rewrite выключен по умолчанию; отдельный таймаут и
  откат; локальный `qwen2.5:7b` на GPU — единицы секунд; облачные быстрые модели — порядка
  секунды.
- [Слабая модель переписывает хуже исходного] → режим `both` (решение 3), метрики сравнения до
  включения на рабочем пути, `llama3.2:1b` не рекомендуется (документируется).
- [Вытеснение моделей в памяти Ollama (эмбеддинги ↔ чат)] → документировать
  `OLLAMA_MAX_LOADED_MODELS`/`KEEP_ALIVE`; измерять в сравнении (время rewrite в отчёте).
- [Эвристики переобучены на 10 вопросах] → шаги независимо отключаются; значения — по
  калибровке на расширенном наборе (`calibration_queries.txt` групп A/B/C плюс контрольные
  вопросы); набор вопросов стоит расширять до сравнения.
- [Порог перестаёт быть откалиброванным] → обязательная перекалибровка с rewrite (задача 7);
  в `CLAUDE.md` уже зафиксировано, что порог привязан к связке модель+стратегия — добавляется
  «и rewrite».
- [Новый канал данных к облаку при `deepseek`/`kimi`] → явная настройка оператора, выкл. по
  умолчанию, документирование; `ollama` как локальный вариант.

## Migration Plan

1. Для существующих `.env`: rewrite выключен (нет `REWRITE_PROVIDER`), `RAG_CANDIDATES` по
   умолчанию больше `RAG_TOP_K`, поэтому шаги отбора действуют сразу. Чтобы сохранить прежнее
   поведение, оператор задаёт `RAG_CANDIDATES=<RAG_TOP_K>` и нейтральные шаги — это же режим
   `baseline` сравнения.
2. Порядок включения: прогнать `/research_rag_compare` в режиме метрик поиска → выбрать
   значения → перекалибровать `RAG_MIN_SCORE` → включить `REWRITE_PROVIDER`.
3. Откат: убрать `REWRITE_PROVIDER` и вернуть нейтральные значения шагов в `.env`,
   перезапустить; индекс и память не затрагиваются (формат не менялся).

## Open Questions

- Значения по умолчанию шагов отбора и `REWRITE_SEARCH_MODE` — по результатам сравнения
  (задача 7); эти значения не меняют спек (диапазоны и семантика зафиксированы).
- Нужно ли расширять контрольный набор до сравнения (10 вопросов дают шумные различия) —
  решает владелец набора; метрики поиска позволяют использовать и расширенный набор без
  дополнительных ответов моделей.
