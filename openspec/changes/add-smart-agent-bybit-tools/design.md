# Design

## Context

Слой `tools` `/smart_agent` сегодня жёстко предполагает ровно один MCP-сервер
(`mcp-moex`, каталог `MCP_MOEX_DIR`). Механика в `mcp_integration/market_session.py`
(`build_server_params`, `MarketTools`, `open_market_tools`) и правила/тексты в
`agents/market_tools.py` (сообщение слоя, статусы, предупреждения) написаны для
единственной сессии на вопрос. `agents/smart_agent.py` хранит один каталог
(`self._mcp_moex_dir`), один статус (`self._tools_status`) и вызывает
`open_market_tools(self._mcp_moex_dir, ...)` один раз.

Новый локальный сервер `mcp-bybit` (`/media/alexey/DATA/Projects/Python/mcp-bybit/`)
устроен по тому же принципу: stdio-транспорт, скрипт `mcp-bybit` из `pyproject.toml`
(`uv run --directory <каталог> mcp-bybit`), инструменты read-only
(`ToolAnnotations(read_only_hint=True, ...)`) — `search_symbols`, `get_current_price`,
`get_price_history`, и три аналитических с `open_world_hint=False` —
`compute_price_metrics`, `compare_with_benchmark`, `compare_securities`. У сервера нет
режима расписания и нет пишущих инструментов. Пять из шести имён инструментов
совпадают с именами MOEX буквально (`get_current_price`, `get_price_history`,
`compute_price_metrics`, `compare_with_benchmark`, `compare_securities`); различается
только поиск (`search_symbols` у Bybit против `search_securities` у MOEX). Без
разведения по источнику модель не могла бы вызвать «инструмент Bybit», а не
одноимённый инструмент MOEX — оба выглядели бы одной функцией в списке `tools`
OpenAI-совместимого API.

См. proposal.md про мотивацию и разграничение с price-watch (у Bybit нет
`--watch-db`, поэтому `/watch*` не расширяется).

## Goals / Non-Goals

**Goals:**
- Дать основному ответу `/smart_agent` доступ к спотовым данным Bybit наравне с
  данными Московской биржи, при этом каждый источник включается/выключается
  оператором независимо через свою переменную окружения.
- Убрать из механики и текстов слоя жёсткое предположение «один сервер»: заменить его
  на «один или несколько независимо настроенных read-only источников», без
  ограничения по количеству в коде (хотя на практике их сейчас два).
- Сохранить все существующие гарантии MOEX (ссылки на историю, правила цепочки
  анализа, границы данных, видимость вызовов, недоступность не блокирует ответ) без
  регресса, и распространить их на Bybit.
- Частичная доступность: недоступность одного источника не должна отбирать
  инструменты у другого.

**Non-Goals:**
- Никакого доступа к приватным/торговым эндпоинтам Bybit — сервер их не публикует, и
  добавлять их не планируется (домен: read-only рыночные данные, см. CLAUDE.md
  «Правила предметной области»).
- Никакого расписания/опроса цен для Bybit (`/watch*` остаётся только MOEX) — сервер
  `mcp-bybit` не поддерживает `--watch-db`.
- Никакого отдельного переключателя слоя на каждый источник — `/smart_agent_toggle
  tools` остаётся ОДНОЙ командой на весь слой, как и раньше; per-source toggle не
  запрашивался и добавил бы поверхность управления без выигрыша, соразмерного задаче.
- Никакого обобщения на «произвольное число источников через плагины/конфиг-файл» —
  два источника (MOEX, Bybit) описываются явно в коде, как сейчас описан один; когда
  появится третий, тот же принцип применяется точечно, а не через раннюю абстракцию.
- Не переносится в этот слой ничто из `/mcp_tools` (генерик-диагностика) и
  `price_watch/` — они не затрагиваются.

## Decisions

### 1. Префикс источника в имени инструмента, а не отдельный параметр

Модели передаются инструменты с именами `moex__<имя>` и `bybit__<имя>` (например,
`moex__get_current_price`, `bybit__get_current_price`). При вызове система по префиксу
до `__` определяет источник, отрезает префикс и передаёт серверу этого источника
исходное имя инструмента без изменений.

Альтернативы:
- **Один общий набор инструментов с параметром `source`.** Отклонено: пришлось бы
  добавлять параметр `source` в схему КАЖДОГО инструмента и в каждый вызов сервера
  (которому этот параметр не нужен и не знаком), усложняя схему без выигрыша — префикс
  в имени не требует менять схему параметров вообще.
- **Показывать модели только инструменты ОДНОГО источника за раз (мод переключения).**
  Отклонено: цель изменения — дать доступ к обоим сразу в одном вопросе (акция + монета
  в одном диалоге), а не заставлять пользователя переключаться.
- **Разные имена без префикса, вручную согласованные (`moex_price`, `bybit_quote`).**
  Отклонено: требует переименовывать по одному при каждом новом источнике/инструменте
  и не даёт единообразного правила разбора на стороне кода.

Разделитель `__` (двойное подчёркивание) выбран, потому что оригинальные имена
инструментов состоят из `snake_case` с одиночными подчёркиваниями — двойное не
пересекается с существующими именами и легко и однозначно разбирается (`split("__",
1)`).

### 2. Один процесс на источник на вопрос, открываются ПОСЛЕДОВАТЕЛЬНО в одном таске

**Обновлено по итогам реализации.** Как и раньше, сервер источника поднимается один
раз на вопрос и живёт на все вызовы этого вопроса. На вопрос может подниматься до
двух процессов — по одному на каждый настроенный и включённый источник.

Первым вариантом было открывать их КОНКУРЕНТНО (`asyncio.gather`, каждый источник —
в своём таске, все — в общем `AsyncExitStack`). Этот вариант был реализован и
**воспроизводимо ломался** на живых серверах:
`RuntimeError: Attempted to exit cancel scope in a different task than it was
entered in`. Причина — `stdio_client`/`ClientSession` (пакет `mcp`, поверх `anyio`)
держат внутренний task group, чей cancel scope обязан ЗАКРЫВАТЬСЯ В ТОМ ЖЕ ТАСКЕ, где
был открыт; `asyncio.gather` создаёт для каждой корутины СВОЙ таск, а закрытие через
общий `AsyncExitStack` происходит в таске-вызывающем — разные таски, нарушение
инварианта anyio. Альтернатива «открывать в отдельных тасках, но и закрывать в них
же» (через `asyncio.Event`, сигнализирующий, когда можно закрываться) была
рассмотрена, но добавляла синхронизационную сложность ради экономии ~0,75 с на
вопрос с двумя источниками — сочтено неоправданным для этой задачи.

**Итоговое решение**: источники открываются ПОСЛЕДОВАТЕЛЬНО, в ОДНОМ И ТОМ ЖЕ таске
(`open_multi_market_tools`, простой `for`-цикл с `AsyncExitStack.enter_async_context`
и `try/except` на каждой итерации) — открытие, все вызовы инструментов и закрытие
происходят в одном таске от начала до конца, что полностью соответствует требованию
anyio. Цена — задержка растёт линейно с числом источников (≈0,75 с на источник, то
есть ≈1,5 с на вопрос при обоих настроенных источниках, а не ≈0,75 с при
гипотетической параллели), но корректность важнее экономии доли секунды; сбой одного
источника (тайм-аут, отсутствие каталога) всё равно не мешает попытке открыть
следующий — партиальная доступность (решение 3) не зависит от того, последовательно
или параллельно шло открытие.

Если у чата настроен только один источник (как сейчас с одним MOEX), поведение и
задержка не меняются — открывается одна сессия, как и раньше.

### 3. Частичная доступность: агрегатор объединяет то, что удалось поднять

Новый агрегирующий слой в `mcp_integration/market_session.py` пытается открыть сессию
с каждым настроенным и включённым источником; неудача одного (сбой запуска, тайм-аут
рукопожатия) не мешает использовать инструменты другого. Модели передаётся
объединённый (с префиксами) список `openai_tools` из всех источников, которые удалось
поднять; для каждого источника, который поднять не удалось, вызывающий код
(`SmartAgent`) получает причину и добавляет предупреждение/правило «не выдавай цены
X по памяти», называющее именно этот источник — по аналогии с тем, как сейчас
единственный недоступный MOEX даёт `market_tools.build_unavailable_context_message()`,
но теперь текст называет источник по имени, а не одно жёстко зашитое «данные биржи».
Если НИ ОДИН источник не поднялся, поведение полностью совпадает с сегодняшним
(вопрос без инструментов и общее предупреждение о недоступности данных биржи).

Диспетчеризация вызова (`call(name, raw_arguments)`) агрегатора: по префиксу находит
нужный `MarketTools`-объект источника и делегирует вызов ему. Если модель вызвала имя
без известного префикса или с префиксом источника, который не поднялся в этом
вопросе, — ошибка текстом для модели, без обращения к какому-либо серверу (тот же
принцип, что уже действует для неизвестного имени инструмента).

### 4. Реестр ссылок на историю (`rN`) — свой у каждого источника, без изменений в схеме имени

Каждый источник продолжает вести свой собственный счётчик `r1, r2, …` внутри своего
`MarketTools`-объекта (класс не меняется в этой части). Поскольку диспетчеризация по
префиксу уже направляет вызов инструмента анализа к правильному источнику ДО
разрешения ссылок, ссылка `{"ref": "r1"}` естественным образом разрешается в реестре
ТОГО источника, чей инструмент анализа её принял — `bybit__compare_securities` видит
только `r1, r2, …`, накопленные вызовами `bybit__get_price_history`, и не видит
результатов MOEX, даже если там тоже накопился `r1`. Отдельно квалифицировать имена
ссылок (`moex_r1`/`bybit_r1`) не нужно: изоляция уже гарантирована местом, где
происходит разрешение ссылки (внутри объекта источника), а не именем.

Альтернатива (единый реестр ссылок на все источники с именами вида `moex_r1`)
отклонена как ненужное усложнение: пришлось бы передавать текущий источник в
`resolve_refs()`, хотя диспетчеризация уже даёт эту информацию бесплатно.

### 5. Конфигурация: `MCP_BYBIT_DIR` по образцу `MCP_MOEX_DIR`, общие лимиты

`config.py` получает `MCP_BYBIT_DIR` (по умолчанию пусто) и `_warn_if_bybit_dir_invalid()`
— копия `_warn_if_moex_dir_invalid()` для нового каталога, тот же принцип
предупреждения без остановки бота. `MCP_TIMEOUT_SECONDS`, `MCP_MAX_TOOL_STEPS`,
`MCP_TOOL_RESULT_MAX_CHARS` остаются ОБЩИМИ на все источники (не разводятся на
MOEX/Bybit): у обоих серверов сопоставимый профиль ответа (JSON, до нескольких сотен
свечей), а раздельные лимиты добавили бы конфигурационную поверхность без
показанной необходимости. `MCP_TOOL_RESULT_MAX_CHARS=45000` был подобран под полный
ответ `get_price_history` MOEX (300 дневных свечей, ≈42 300 символов) — при внедрении
нужно замерить типичный размер ответа `mcp-bybit` (задача в tasks.md) и убедиться, что
общий предел остаётся достаточным для штатного случая обоих источников; если нет,
поднять общий предел, а не заводить второй.

`PRICE_WATCH_ACTIVE` не меняется (остаётся `PRICE_WATCH and bool(MCP_MOEX_DIR)`) —
Bybit не участвует в `price_watch`.

### 6. Сообщение слоя и правила цепочки анализа собираются по источникам, MOEX-текст не переписывается

`agents/market_tools.py` перестаёт хардкодить один блок текста про Московскую биржу.
Вместо этого:
- общая шапка сообщения перечисляет только ДЕЙСТВИТЕЛЬНО доступные в этом вопросе
  источники (один или два) с их назначением и примером тикера/символа;
- абзац цепочки анализа собирается для каждого источника, у которого среди
  предоставленных инструментов есть хотя бы один инструмент анализа, и правила MOEX
  внутри такого абзаца остаются ТЕКСТУАЛЬНО такими же, как сегодня (проверенными на
  живом ISS, см. design.md изменения `add-smart-agent-analytics-chain`) — это
  изменение их не пересматривает;
- для Bybit пишется параллельный, но отдельный абзац: спотовый рынок торгуется
  непрерывно (нет понятия торгового дня/выходных, в отличие от MOEX), поэтому часть
  специфичных для MOEX оговорок (число дневных свечей у бумаг с выходными и т.п.) к
  Bybit не относится буквально. Точные пределы (доступные `interval`, максимальное
  число свечей на запрос у `mcp-bybit`) должны быть проверены на реальном API Bybit
  при реализации (задача в tasks.md), тем же способом, каким были выверены правила
  MOEX — не переносить формулировки MOEX по аналогии без проверки.

### 7. `/smart_agent_show` показывает статус каждого источника отдельно

`SmartAgent._tools_status`/`_tools_status_reason` (одна пара на весь слой) заменяются
на словарь по источнику: `{"moex": (status, reason), "bybit": (status, reason)}`.
`get_tools_status()` возвращает этот словарь целиком; `agents/smart_agent_command.py`
печатает по строке на каждый НАСТРОЕННЫЙ источник (источник без заданного каталога не
показывается вовсе — как и сегодня для единственного MOEX без `MCP_MOEX_DIR`).
`get_last_tool_calls()` не меняется по форме (список записей с именем, несущим
префикс, — источник уже виден в имени).

### 8. Единый переключатель слоя, без изменений в модели `enabled_layers`

`LAYER_TOOLS`/`/smart_agent_toggle tools` остаются как есть — одна настройка на весь
слой, охватывающая все источники сразу (см. Non-Goals). Добавление Bybit не требует
миграции сохранённых файлов памяти: старое значение `enabled_layers["tools"]`
продолжает означать «слой включён» для обоих источников без отдельного флага.

## Risks / Trade-offs

- **[Risk]** Открытие двух процессов на вопрос ПОСЛЕДОВАТЕЛЬНО (решение 2, обновлено
  по факту реализации) увеличивает задержку ответа линейно с числом настроенных
  источников (≈1,5 с при обоих вместо ≈0,75 с при одном), а не только число
  одновременных дочерних процессов. → **Mitigation**: процесс каждого источника
  живёт не дольше одного вопроса, как и сегодня; корректность (не ломать anyio)
  важнее задержки в доли секунды — конкурентное открытие было опробовано и
  воспроизводимо ломалось, см. решение 2. При необходимости лимитировать число
  одновременных дочерних процессов на инстанс бота (при параллельных вопросах разных
  чатов) — отдельная задача, не предмет этого изменения (текущий MOEX-профиль такого
  лимита тоже не имеет).
- **[Risk, ПРОВЕРЕНО]** Правила цепочки анализа Bybit изначально были написаны без
  эмпирической проверки реального API. Проверка на живом API (задача 7.1 tasks.md)
  ПОДТВЕРДИЛА риск: `interval="month"` (по аналогии с MOEX) сервер `mcp-bybit`
  ОТКЛОНИЛ — валидатор принимает только `15m`/`1h`/`4h`/`1d`/`1w`/`1M`. Формулировки
  абзаца Bybit (`_bybit_analytics_block`) исправлены по факту этой проверки до того,
  как код смог попасть в прод с неверными правилами.
- **[Risk]** Префикс `__` в имени инструмента — тонкая инвариант: если в будущем у
  MOEX или Bybit появится инструмент, чьё родное имя само содержит `__`, разбор по
  первому `__` может дать неверный источник. → **Mitigation**: инструменты обоих
  серверов сейчас используют одиночные подчёркивания (`snake_case`); разбор по ПЕРВОМУ
  `__` (а не последнему) корректен, пока префикс источника не содержит `__` сам —
  проверка вынесена в тест.
- **[Trade-off, ПРОВЕРЕНО]** Общие (не по-источнику) `MCP_TIMEOUT_SECONDS`/
  `MCP_MAX_TOOL_STEPS`/`MCP_TOOL_RESULT_MAX_CHARS` проще в конфигурации, но не
  позволяют дать источникам разные значения. Замер (задача 7.2 tasks.md) показал, что
  полный ответ `get_price_history` у `mcp-bybit` (300 дневных свечей) занимает ≈45 001
  символ компактного JSON — с пометкой о ссылке (≈90 символов) это БОЛЬШЕ прежнего
  общего предела 45000: с прежним значением полный ответ Bybit штатно бы обрезался.
  Предел поднят до 50000 (с запасом над обоими измеренными значениями — MOEX ≈42 300,
  Bybit ≈45 091), а не разведён на два — разница между источниками оказалась в пределах
  10%, недостаточной, чтобы оправдать вторую переменную окружения.

## Migration Plan

- Новая переменная `MCP_BYBIT_DIR` необязательна и по умолчанию пуста — без неё
  поведение бота не меняется (слой работает как сегодня, только с MOEX). Разворачивать
  можно без окна отказа: перезапуск процесса бота с добавленной переменной, как и при
  первом включении MOEX.
- Существующие файлы памяти `/smart_agent` (`AGENT_MEMORY_DIR/<chat_id>.json`) не
  требуют миграции: `enabled_layers["tools"]` читается как раньше, а статус по
  источникам — состояние в памяти процесса (`_tools_status`), не персистентное, как и
  сегодня.
- Откат — убрать/опустошить `MCP_BYBIT_DIR` и перезапустить бота: Bybit перестаёт
  предлагаться модели, MOEX продолжает работать как сегодня.
