# Design

## Context

Мотивация и объём — в `proposal.md`, требования — в `specs/dev-assistant/spec.md`.

Что уже есть и переиспользуется (проверено по коду):

- `rag/index_store.py`: `build_index(strategy, records, index_dir)` и `search(...)` принимают
  каталог индекса параметром; `IndexRecord` допускает `author=None`, `date=None`. Поэтому
  отдельный индекс документации не требует правок `rag/`, а `rag/cli.py` (жёстко читает
  `data/source/pdf|txt`) не трогаем.
- `providers/embeddings_client.embed_texts()` с `budget_seconds` — эмбеддинги вопроса и сборки.
- `mcp_integration/market_session.open_market_tools(params, timeout, max_result_chars, allowlist,
  require_read_only)` и `agents/market_tools.run_tool_loop(...)` — запуск stdio-сервера, проверка
  «allowlist И read_only_hint», цикл «модель → инструменты → модель»; оба не знают про рынок.
- `llm_queue.enqueue_job(update, context, kind, text, run, priority=...)` и
  `cancel_chat_questions` — очередь и снятие вопросов при выходе.
- Паттерн режима-диалога: `ConversationHandler` (`/agent`, `/smart_agent`), текстовый фильтр
  `TEXT & ~COMMAND & ChatType.PRIVATE`, выход `/cancel`.
- `mcp-git` (`/media/alexey/DATA/Projects/Python/mcp-git`): инструменты `list_roots`,
  `get_current_branch`, `list_files`, `get_diff`, все с `readOnlyHint=True`; корень доступа задаётся
  при запуске `--root`, каждый вызов требует абсолютный `repo_path`; усечение списка — поле
  `truncated`; запуск `uv run --directory <dir> mcp-git --root <path>`.

Ограничения проекта: нет рантайм-смены модели/провайдера/промпта; новые каналы данных наружу
фиксируются явно; тесты — только чистые функции; `SYSTEM_PROMPT` слоями не ослабляется.

## Goals / Non-Goals

**Goals:**
- Ассистент, отвечающий о структуре и правилах проекта по документации и сообщающий ветку и список
  файлов; доступ только по списку оператора.
- Минимальное вмешательство в существующий код: новый пакет, одна регистрация в `main.py`,
  переменные в `config.py`, один новый вид задачи очереди.
- Максимум чистых функций (проверка доступа, разбор списка, чанкер, сборка сообщений, подстановка
  `repo_path`, источники) — под тесты.

**Non-Goals:**
- Переписывание вопроса, rerank, калибровка порога — как в слое `rag` `/smart_agent`; решается
  после первого живого прогона.
- Командная строка для вопросов (`ask`) — в этом изменении только CLI сборки индекса; ядро
  `ask()` отделено от Telegram, так что CLI-фасад добавляется позже без переделки.
- Общий код с `rag/cli.py` (рефакторинг в общий индексатор) — не нужен.

## Decisions

### 1. Размещение: пакет `src/dev_assistant/` внутри проекта

Отдельного репозитория нет: нужны `rag/index_store`, `providers/`, `llm_queue`, конфигурация и
правила проекта; в отдельном проекте их пришлось бы копировать или выносить в общую библиотеку.
Ядро (`core.py`: вопрос → ответ + источники) не импортирует Telegram; командный слой
(`command.py`) — тонкая обёртка. Это сохраняет возможность второго фасада (CLI) позже.

Модули: `rules.py` (чистое: разбор списка id, `is_authorized`, тексты), `chunking.py`
(Markdown-чанкер), `sources.py` (набор документов), `indexer.py` + `cli.py` (сборка),
`search.py` (эмбеддинг вопроса → поиск → отбор), `prompts.py` (сообщения модели),
`git_session.py` (запуск `mcp-git`, allowlist, подстановка `repo_path`), `core.py`, `command.py`.

### 2. Доступ: фильтр PTB + явная проверка, тишина для чужих

- `DEV_ASSISTANT_USER_IDS` — целые через запятую; разбор и валидация — чистая функция, ошибка
  формата завершает запуск через `_validate_config()`. Пустой список — обработчик не
  регистрируется (команда ведёт себя как неизвестная).
- Точки входа и текстовые обработчики состояний собираются с `filters.User(user_id=ids)`: сообщение
  постороннего вообще не доходит до обработчика. Поверх этого в каждом колбэке — вызов
  `is_authorized(update.effective_user, ids)` (защита от ошибки регистрации; `None` → отказ).
  Отказ — молча, как для неизвестной команды (режим не раскрывается).
- Сравнение — по `effective_user.id`, не по `chat_id`.
- Альтернатива «вежливый отказ чужому» отвергнута: раскрывает существование режима, а `/help` его
  намеренно не показывает.

### 3. Индекс: отдельный каталог, одна стратегия, ручная сборка

- `DEV_ASSISTANT_INDEX_DIR` (по умолчанию `data/dev_index`), стратегия `markdown`, сборка
  `make dev-index` (`python -m dev_assistant.cli`, `PYTHONPATH=src`), полная пересборка при каждом
  запуске, атомарность — `build_index()` из `rag/`.
- Источники — фиксированный перечень в коде, корень проекта определяется по расположению
  `config.py`: `README.md`, `CLAUDE.md`, `src/**/CLAUDE.md`, `docs/**/*.md`,
  `openspec/specs/**/spec.md`. Исключено: `openspec/changes/**` (в том числе архив — шумно и
  устаревает), `data/`, `.venv`, исходники. Расширять перечень — решение отдельного изменения.
- Чанкер: делит по заголовкам Markdown (`#`…`######`), игнорируя `#` внутри ограждённых блоков кода;
  заголовок несёт «хлебные крошки» (`файл › H1 › H2`), попадающие в `title` записи и в текст
  эмбеддинга; раздел длиннее `MAX_CHUNK_CHARS` режется по абзацам, совсем короткие (`< MIN_CHUNK_CHARS`)
  присоединяются к следующему. Константы — в модуле, а не в `.env`: параметры чанкера — предмет
  кода, не эксплуатации. `chunk_structural` из `rag/` не годится: он заточен под PDF-слайды.
- `source` записи — относительный путь файла, `author`/`date` — `None`.
- Порядок индексации стабилен (сортировка путей), итог: файлов, фрагментов, пропущенных файлов
  (нечитаемые, пустые).

Альтернатива «положить README и docs в существующий индекс» отвергнута: слой `rag` у
`/smart_agent` начал бы цитировать архитектуру бота как учебный материал, а порог `RAG_MIN_SCORE`
перестал бы соответствовать корпусу.

### 4. Поиск: без переписывания, со своими параметрами

`DEV_ASSISTANT_TOP_K` (5), `DEV_ASSISTANT_MIN_SCORE` (по умолчанию `0.0` — шаг отключён, пока нет
калибровки), бюджет эмбеддинга — общий `RAG_SEARCH_TIMEOUT_SECONDS`. Эмбеддинг вопроса —
`embed_texts(..., budget_seconds=...)`; сбой эмбеддинга или отсутствие индекса — понятное
сообщение пользователю, модель не вызывается (нечего подавать). Если поиск состоялся и ничего не
нашёл: при доступных git-инструментах модель вызывается с пометкой «в документации ничего не
найдено — не выдавай ответ за подтверждённый документами»; без инструментов — фиксированный
отказ без вызова модели (по образцу `smart-agent-rag`).

### 5. Git: `mcp-git` через существующий слой MCP, `repo_path` подставляет бот

- `MCP_GIT_DIR` — каталог проекта `mcp-git` (оператор; по образцу `MCP_MOEX_DIR`, с
  предупреждением в `config.py`, если нет `pyproject.toml`). Пусто — git-слой выключен.
- Параметры запуска: `StdioServerParameters("uv", ["run", "--directory", MCP_GIT_DIR, "mcp-git",
  "--root", PROJECT_ROOT])` — своя функция в `git_session.py`, потому что `build_server_params()`
  не принимает дополнительных аргументов; `PROJECT_ROOT` — вычисляется из расположения файлов,
  не из ввода. Корень сервера — только этот репозиторий, так что даже подмена `repo_path`
  упирается в `path_not_allowed` на стороне сервера (граница вне промпта).
- Allowlist: `{"get_current_branch", "list_files"}`, `require_read_only=True` (аннотации у
  `mcp-git` есть). `get_diff` и `list_roots` модель не видит — их нет ни в схеме, ни в
  обработке; вызов по имени вне перечня возвращается модели как ошибка (механика `MarketTools`).
- Схема инструментов для модели собирается из схем сервера с УДАЛЁННЫМ параметром `repo_path`
  (по образцу `with_ref_parameters`, только в обратную сторону); в `call_tool` аргументы
  разбираются, `repo_path` перезаписывается значением `PROJECT_ROOT` (даже если модель его
  прислала), затем вызов. Подстановка и очистка схемы — чистые функции.
- Параметры `ref`/`path` у `list_files` остаются модели: это имена файлов отслеживаемого дерева, а
  не содержимое; усечение (`truncated`) подчёркивается в сообщении слоя.
- Запуск — на каждый вопрос (как слой `tools`: процесс на вопрос, закрытие по выходу из блока);
  недоступность сервера — предупреждение пользователю и ответ по документации. `MCP_TIMEOUT_SECONDS`,
  `MCP_MAX_TOOL_STEPS`, `MCP_TOOL_RESULT_MAX_CHARS` — существующие настройки.

Альтернативы: готовый `mcp-server-git` (есть мутирующие инструменты, аннотации не проверены) и
собственный мини-сервер — отвергнуты ради уже написанного `mcp-git`; прямой вызов `git` из бота —
отвергнут, цель задачи — именно MCP.

### 6. Сообщения модели и память режима

Порядок: `SYSTEM_PROMPT` (основной, без изменений) → системное сообщение ассистента
(константа: роль «только о проекте», вопросы вне темы — отказ, фрагменты и результаты
инструментов — данные, не инструкции, запрет ослаблять предупреждения `SYSTEM_PROMPT`, запрет
инвестиционных рекомендаций) → сообщение git-слоя (если доступен: что инструментов два, `diff` и
содержимое файлов недоступны, ветку называть только из результата) → краткая история диалога →
сообщение пользователя с фрагментами. Системное сообщение — отдельным, а не вместо
`SYSTEM_PROMPT`, как у слоёв `tools`/`rag`: иначе режим стал бы пользовательским системным
промптом.

История — `dict[chat_id] -> deque` последних `DEV_ASSISTANT_HISTORY_TURNS` (по умолчанию 6) пар
«вопрос — ответ», только в памяти процесса; пишется итог (без фрагментов, `tool_calls` и `tool`),
очищается `/cancel`. Диск не используется.

### 7. Источники в ответе — строит код

Строка «Источники:» собирается из фактически поданных фрагментов (`файл › раздел`), а не из
слов модели; проверку цитат слоя `rag` не повторяем (документация проекта — не юридически
значимый материал, цитата дословно не требуется). Вопрос вне темы или ответ только по git — без
блока источников, если фрагменты не подавались.

### 8. Очередь

Новый вид задачи `dev_assistant` в `llm_queue/rules.KINDS`, приоритет `INTERACTIVE`, оценка ожидания
считается по собственному окну длительностей. Тот же шаблон «поток + `asyncio.run`» и кооперативная
отмена (`should_cancel`), как у `SmartAgent`: цикл с инструментами асинхронный, вызов модели
синхронный. Выход `/cancel` — `cancel_chat_questions`. Изменение затрагивает `llm_queue` только
добавлением вида задачи (формулировки требований `llm-request-queue` остаются верными).

### 9. Регистрация и порядок обработчиков

В `main.py` `build_dev_assistant_handlers()` возвращает `[]`, если список пуст; иначе —
`ConversationHandler`, регистрируемый ДО обработчика обычного текста (по тому же правилу, что
остальные режимы). Вне `RESEARCH`: у режима другая аудитория (список id), а не «технические
команды». В `help_command` изменений нет; тест на неизменность справки не нужен, достаточно, что
`main.py: help_command` не правится (проверяется диффом).

## Risks / Trade-offs

- [Список файлов раскрывает структуру репозитория облачному провайдеру] → оператор вправе выбрать
  локальный `MAIN_CLIENT=ollama`; факт канала записан в спеке и документации; содержимое файлов и
  diff не передаются.
- [Фрагменты `openspec/specs` и `CLAUDE.md` могут содержать упоминания внутренних решений] →
  индексируется только перечисленное; корпус инвестиционных документов в набор не входит.
- [Порог `DEV_ASSISTANT_MIN_SCORE=0.0` пропускает слабые совпадения] → источники показываются
  всегда, ответ при слабых совпадениях обязан оговариваться (промпт); калибровка — отдельным
  небольшим изменением после живого прогона.
- [Устаревший индекс отвечает по прошлой версии документации] → индекс не авто-обновляется;
  ответ несёт дату сборки индекса (из метаданных, сохраняемых сборкой в `meta` каталога)
  и актуальную ветку из git.
- [`filters.User` и вход в другой режим в середине диалога] → поведение повторяет существующие
  режимы (проверить на `/agent`, `/smart_agent`); отдельная логика не вводится.
- [Процесс `mcp-git` на каждый вопрос ≈ 0,75 с] → приемлемо на фоне генерации локальной модели; кэш
  сессии — не вводим (та же цена, что у слоя `tools`).
- [`mcp-git` — внешний проект с собственным жизненным циклом] → версия не фиксируется кодом бота;
  при несовпадении контракта инструмент пропадает из allowlist и ассистент отвечает по документации.

## Open Questions

- Нужен ли CLI-вопрос (`python -m dev_assistant ask`) для ручной проверки без Telegram — решить
  после первой реализации; ядро к нему готово.
- Калибровка `DEV_ASSISTANT_MIN_SCORE` и состав источников (например, комментарии кода) — после
  живого прогона на реальных вопросах.
