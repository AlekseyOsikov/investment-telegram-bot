# Design

## Context

- `/watch*` (`src/price_watch/`) — пассивный сервер `mcp-moex` хранит опросы и сводки, бот держит
  часы и доставку («не менее одного раза»: сначала отправка, потом `watch_ack`). Модель в нём не
  участвует, и это сохраняется: новости идут отдельными командами.
- Локальная модель Ollama обслуживает один запрос за раз. `llm_queue` уже умеет слоты двух
  приоритетов: `INTERACTIVE` (вопросы пользователей: лимиты, TTL, `/queue`) и `RESEARCH`
  (`gate.slot(priority, kind, chat_id)`, без TTL и без показа пользователю).
- Провайдер вспомогательных вызовов выбирается отдельной настройкой оператора
  (`providers/rewrite_client.py`: `REWRITE_PROVIDER|MODEL`, ключ невыбранного провайдера не нужен).
- Внутри репозитория уже есть серверы вне `src/` (`mcp_servers/project_files/`,
  `mock_servers/support_crm/`), запускаемые через `sys.executable` без shell.
- Проверка источников с машины разработки (без ключей): MOEX ISS `sitenews` и RSS ЦБ отвечают;
  общий RSS РБК отвечает; e-disclosure.ru отвечает 403 автоматическим запросам. Это решение
  владельца проекта: первый этап на общих лентах, а неполнота подборки сообщается пользователю.

## Goals / Non-Goals

**Goals:**
- Дайджест новостей по бумагам из `/watch` с разбором «тип события + механизм», проверяемым кодом.
- Граница допустимого записана в коде (схема, перечни, запретные формулировки), а не только в
  промпте.
- Фоновая работа не мешает вопросам пользователей и переживает недоступность модели и лент.
- Чистые правила (привязка, проверка ответа модели, лимиты, тексты) покрыты тестами без сети.

**Non-Goals:**
- Направление влияния, прогноз, оценка «хорошая/плохая новость», пороги и «сигналы», советы.
- Официальное раскрытие эмитентов (источник закрыт; позже, отдельным решением).
- Пользовательский выбор источников, тихие часы, поиск по архиву новостей, своя таблица бумаг.
- Суммы, портфель, связь с брокером.

## Decisions

### 1. Отдельные команды `/news*`, `/watch*` остаётся без модели

Отдельная включаемая подписка вместо «встроить новости в сводку `/watch`»: сводка `/watch` —
шаблон сервера без LLM, и правило «модель в `/watch*` не участвует» остаётся истинным и
проверяемым. Новости нужны не всем, а фоновый текст модели в чат — новый канал, его пользователь
включает осознанно. Тикеры не вводятся второй раз: бот на каждом тике читает их из опроса чата
(`watch_status`), поэтому замена `/watch` сразу меняет дайджест, а `/watch_stop` его выключает.

Альтернативы: вшить в сводку `/watch` (ломает инвариант без модели, ломает доставку по периоду
сводки); собственный список тикеров у `/news` (два источника правды, расхождение).

### 2. Сервер новостей `mcp_servers/news/` в репозитории вне `src/`

Решает открытый вопрос из обсуждения. Сервер на FastMCP, запуск `sys.executable` с аргументами
`--db` (абсолютный путь), `--feeds` (список адресов от оператора), как `project_files`. Причины:
сбор, дедупликация, привязка и хранилище не зависят от Telegram и модели и тестируются отдельно;
внешний проект (`mcp-moex`) не наш, добавлять в него новости нельзя; пакет внутри `src/` смешал
бы сбор с логикой бота. `src/` не импортирует код сервера — только общается по MCP, как с
остальными серверами.

Разделение ответственности повторяет `/watch*`:

```
 тик бота (NewsScheduler)
   |
   | 1. watch_status(chat) --------------------> mcp-moex      тикеры чата
   | 2. news_collect() ------------------------> mcp-news      ленты -> дедуп -> привязка -> SQLite
   | 3. news_pending(tickers) -----------------> mcp-news      новости без разбора
   | 4. для каждой: слот llm_queue (низкий приоритет) -> модель -> проверка кодом
   | 5. news_save_analysis(id, разбор | "нет") ->  mcp-news
   | 6. news_ready(chat, tickers, лимит) ------> mcp-news      что отправить
   | 7. отправка в Telegram
   | 8. news_ack(chat, ids) -------------------> mcp-news      ТОЛЬКО после успешной отправки
```

Один процесс сервера на обращение (как `call_watch_tool`): ничего не держится открытым на время
отправки и работы модели.

### 3. Привязка к тикерам — таблица алиасов в данных сервера

`mcp_servers/news/data/aliases.json`: тикер → названия и формы («название эмитента», бытовые
сокращения). Совпадение — по границам слов, без регистра; тикер латиницей ищется только как
целое слово в верхнем регистре. Слишком короткие и двусмысленные алиасы либо требуют
сопутствующего слова (например «банк», «акции»), либо не включаются в таблицу. Сервер в
`news_ready` отдаёт запись вместе с тем, ПО ЧЕМУ она привязана (для журнала и оценки).

Бумага, которой нет в таблице, находится только по тикеру в тексте; `/news` в ответе честно
перечисляет такие бумаги как «покрытие ограничено». Это известное ограничение этапа 1 (риск ниже).

Альтернативы: просить модель определить компанию (выдуманные привязки, недетерминизм, нечего
тестировать); подтягивать названия с биржи (`shortname` ISS) автоматически — отложено, названия
биржи редко совпадают с тем, как пишут СМИ.

### 4. Разбор моделью: схема, проверка кодом, повтор, откат на «без разбора»

Ответ — JSON из полей `event_type`, `importance`, `summary`, `mechanism`. Перечни и длины — в
чистом модуле `news_digest/rules.py`. Проверка кодом:

1. JSON разбирается терпимо (Ollama может обернуть в текст) и валидируется по схеме;
2. `event_type`/`importance` — из перечней;
3. `summary` и `mechanism` не длиннее лимита и не содержат запретных формулировок: направление
   («позитивн*», «негативн*», «рост*/вырастет», «паден*/упадёт», «подорожа*/подешевеет»), советы
   («покупать», «продавать», «стоит», «рекомендуем»), прогноз («ожида*», «будет расти»), оценки
   «хорошая/плохая новость»; регулярные выражения по основам слов, со списком в одном месте;
4. нарушение — один повтор с указанием, что именно нарушено; после второго — запись «разбор
   недоступен» и показ заголовка, источника и ссылки.

Механизм — это описание того, ЧЕРЕЗ ЧТО тип события связан с ценой («дивидендная отсечка
уменьшает стоимость акции на размер выплаты», «ограничение по ценной бумаге влияет на условия
торгов»), а не оценка, что произойдёт в этот раз. Границу показывает таблица:

| Допустимо | Недопустимо |
|---|---|
| тип события и важность | «позитивно/негативно для акций» |
| одна фраза пересказа по тексту новости | «акция вырастет/упадёт», «ожидаем» |
| общий механизм типа события | «стоит купить/продать», пороги и «сигналы» |
| совпадение по времени с движением цены | «цена упала из-за этой новости» |

Кроме запрета в коде, системное сообщение разбора содержит ту же границу и прямо говорит, что
текст новости — данные, а не инструкции, и что оно не ослабляет основной промпт проекта (оговорку
сохранять, как у слоёв `tools`/`rag`). Модели не отдаются инструменты и не передаются сообщения
пользователей, chat_id, тикеры других чатов: на вход идёт только публичный текст одной новости
и её привязка.

Разбор кэшируется по идентификатору новости на сервере и общий для всех чатов — один и тот же
текст не разбирается дважды, и модель ничего не знает о том, кто наблюдает бумагу.

Альтернативы: свободный текст модели и фильтр после (хуже проверяется); двухпроходная схема
«классификатор + редактор» (двойная цена на локальной модели без выигрыша для этапа 1);
строгий JSON-режим провайдера как единственная защита (Ollama и облако ведут себя по-разному —
валидация нужна в любом случае, режим JSON используется как подсказка, а не как гарантия).

### 5. Очередь: слот на одну новость, низкий приоритет, свой вид

Каждая новость разбирается под отдельным `gate.slot(priority=RESEARCH, kind="news", chat_id=0)`:
вопрос пользователя вклинивается между новостями, а разбор не регистрируется как вопрос чата и
не попадает в `/queue`, лимиты и TTL (такая же механика, как у исследований). Добавляется
`KIND_NEWS` в `llm_queue/rules.py` (учёт длительностей по виду, как у остальных). Спека очереди
дополняется сценариями с разбором новостей.

Провайдер и модель разбора — `NEWS_PROVIDER` (`ollama`|`deepseek`|`kimi`, по умолчанию
`ollama`) и `NEWS_MODEL`, по образцу `REWRITE_*`; клиент собирается в `providers/news_client.py`.
Это настройка оператора, не рантайм-выбор пользователя. Пустая модель или отсутствие ключа
выбранного облачного провайдера — предупреждение в журнале, дайджест работает без разбора.

### 6. Доставка, срочность, лимиты

- Дайджест: раз в `NEWS_DIGEST_INTERVAL_HOURS`; сообщение собирается из неотправленных новостей
  чата, отсортированных по важности и времени, не более `NEWS_DIGEST_MAX_ITEMS`; остальное
  остаётся на следующий раз.
- Срочное: только `importance == "high"`, не чаще окна, ограниченного суточным лимитом.
- Суточный лимит `NEWS_MAX_MESSAGES_PER_DAY` на чат; счётчик по московским суткам хранит сервер.
- Всё по шаблону доставки `/watch*`: сначала отправка, потом `news_ack`; сбой отправки
  оставляет новости неподтверждёнными; недоступный чат (`is_chat_unreachable`) выключает
  дайджест. Пользователям о фоновых сбоях не пишем, паузы с удвоением, как у планировщика цен.
- Оговорки — фиксированные строки кода (в `news_digest/texts.py`), входят в каждое сообщение;
  тест проверяет, что дайджест, срочное сообщение и ответ `/news` их содержат.

### 7. Совпадение по времени с ценой

Берём цену из существующего read-only инструмента истории цен `mcp-moex` (тот же, что видит
`/smart_agent`), а изменение считаем чистой функцией в боте: между закрытием до публикации
новости и последним значением. Строка «в это же время цена изменилась на X% (котировки с
задержкой; это изменение цены, а не доходность)» не пишется, если данных нет, интервал слишком
короткий для имеющейся свечи или новость старше окна. Слова о причине запрещены тем же проверяемым
перечнем. Это последний слой работы: если инструмент окажется неудобным, дайджест выходит без него
(спека разрешает), и это не блокирует остальное.

### 8. Оценка качества: правила в `src/research`, прогон в `scripts/`

По образцу `dialog_eval`: `src/research/news_eval.py` (чистые правила: формат набора, проверки
ответа — те же функции, что в боте, доля совпадения типа с разметкой, текст итога) и
`scripts/news_eval.py` (чтение набора из `data/news_eval/`, обращение к настроенной модели,
отчёт). Набор — публичные заголовки и тексты новостей, вымышленные в тестах; настоящий набор и
отчёты в `data/`, не коммитятся. Скрипт ничего не применяет сам: модель и промпт остаются
решением оператора.

## Risks / Trade-offs

- [Ограниченное покрытие: нет официального раскрытия, дивиденды и отчётность приходят из
  заголовков СМИ] → оговорка в каждом сообщении и в `/news`; тип события только из текста, который
  есть; официальные данные — отдельное будущее решение.
- [Таблица алиасов покрывает не все бумаги и может давать ложные срабатывания] → ограничения на
  короткие алиасы, привязка видна в журнале и отчёте оценки, `/news` сообщает о бумагах без алиасов.
- [Локальная модель нарушает схему или даёт запретные формулировки] → проверка кодом, один
  повтор, откат на показ без разбора; оценка по набору до включения у пользователей.
- [Prompt injection в тексте новости] → текст как данные, нет инструментов, нет данных
  пользователей на входе, строгая схема вывода и проверка; худший исход — новость без разбора.
- [Фоновые разборы занимают единственный слот Ollama и задерживают вопросы] → низкий приоритет,
  слот на одну новость, потолок числа разбираемых новостей за тик, пропуск старых.
- [Лента меняет формат или блокирует автоматические запросы] → сбор по каждой ленте независим,
  тайм-ауты и лимиты размера, отчёт о недоступных лентах; обход блокировок не делаем.
- [Облачный провайдер разбора вывозит тексты новостей за пределы машины] → публичные тексты без
  данных пользователей; решение оператора, по умолчанию локальный Ollama, строка об этом в
  документации.
- [Дублирующиеся срочные сообщения при сбоях доставки «не менее одного раза»] → идентификаторы
  новостей и подтверждение после отправки; редкий повтор допустим, потеря — нет.

## Migration Plan

1. Выкладка выключенной: `NEWS_ENABLED=false` по умолчанию, поведение бота не меняется.
2. Оператор настраивает ленты, провайдера и модель разбора, собирает `aliases.json`, запускает
   `scripts/news_eval.py` на локальном наборе и только после этого включает флаг.
3. Откат: выключить флаг и перезапустить бот; файл SQLite можно удалить, он содержит только
   публичные данные и отметки дайджеста.

## Open Questions

- Точный состав стартовых лент (РБК, возможно Интерфакс) — после проверки условий использования
  оператором; не меняет схему и задачи, адреса лежат в настройке.
- Конкретная свеча и интервал для строки о цене (решение 7) — выясняется по схеме инструмента
  `get_price_history` при реализации; спека допускает отсутствие строки.
