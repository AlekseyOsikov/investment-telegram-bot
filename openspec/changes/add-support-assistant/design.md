# Design

## Context

Мотивация и объём — в `proposal.md`, требования — в дельта-спеках `support-assistant` и
`support-crm-mock`. Ближайший образец в коде — режим `/dev` (`src/dev_assistant/`): отдельный
пакет с чистыми правилами, отдельный индекс (`rag.index_store.build_index()`, стратегия
`markdown`), один MCP-сервер через `mcp_integration.market_session.open_market_tools`,
подстановка параметра кодом (`force_repo_path`), история в памяти процесса, вид задачи очереди,
взаимоисключение через `agents.active_mode`. Отличия `/support` от `/dev`: доступ для всех
пользователей, данные зависят от пользователя (изоляция), в справке показывается, контекст
подгружается кодом заранее.

Ограничения проекта (корневой `CLAUDE.md`): `SYSTEM_PROMPT` уходит первым без изменений;
системные сообщения слоёв — отдельные и не ослабляют его; нет рантайм-смены модели/промпта;
чувствительные данные не запрашиваются и не хранятся; новые режимы памяти — только явные и
видимые; корпус документов учебного RAG в репозиторий не входит (FAQ поддержки — собственная
документация бота, ей это не касается).

## Goals / Non-Goals

**Goals:**
- Режим `/support` со структурой `dev_assistant`: чистые правила и промпты тестируются без сети.
- Контекст тикетов пользователя получается детерминированно (код), а не по усмотрению модели.
- Изоляция пользователей обеспечивается кодом бота и дублируется мок-сервером.
- Замена мока настоящей CRM — настройкой оператора, без правок ядра режима.

**Non-Goals:**
- Запись в CRM (создание/комментирование тикетов), роль оператора поддержки, эскалация.
- Реальная CRM, персональные и финансовые данные, связь с брокером.
- Калибровка порога поиска под FAQ (стартовое значение 0.0, как у `/dev`) и переписывание вопроса.
- Изменение `SmartAgent`, `/dev`, `rag/` и существующих спек.

## Decisions

### 1. Отдельный пакет `support_assistant/`, а не слой `/smart_agent`

Пакет повторяет разбиение `dev_assistant` (`rules`, `prompts`, `search`, `indexer`, `crm_session`,
`core`, `command`, `cli`). Чанкер Markdown и `build_index` переиспользуются импортом
(`dev_assistant.chunking.chunk_markdown`), а не копируются; если импорт «режима из режима»
окажется неудобным, чанкер выносится в общий модуль в рамках задачи 1.3 без изменения поведения
`/dev` (тесты `/dev` остаются зелёными).
*Альтернатива:* слой `support` в `SmartAgent` — отвергнута: порог `RAG_MIN_SCORE` откалиброван под
инвестиционный корпус, `SmartAgent` уже перегружен, смешение поддержки и инвестиций в одном диалоге.

### 2. Контекст тикетов — предзагрузка кодом + три read-only инструмента

На каждый вопрос открывается одна сессия CRM-сервера; код сам вызывает «список моих обращений»
(открытые, не больше `SUPPORT_TICKETS_LIMIT`), формирует из результата системное сообщение с
данными и затем ведёт цикл инструментов (`market_tools.run_tool_loop`) с тремя инструментами.
Предзагрузка делает ответ про «почему не работает» детерминированным (модель не должна
догадаться вызвать инструмент); инструменты нужны для уточнений («покажи события тикета T-…»).
Предзагрузка выполняется на КАЖДЫЙ вопрос, а не при входе: статус тикета может измениться, а
состояние сессии между вопросами не хранится (≈0,75 с на запуск — приемлемо).
*Альтернативы:* только инструменты (непредсказуемо); только предзагрузка (нет уточнений).

### 3. Изоляция: идентификатор подставляет код (по образцу `force_repo_path`)

Параметр `telegram_user_id` удаляется из схем инструментов (`strip_param`) и в каждом вызове
перезаписывается значением `update.effective_user.id` (`force_param`), даже если модель его прислала.
Идентификатор — пользователя, не чата. Вторая граница — мок-сервер: он возвращает данные только
запрошенного идентификатора, чужой тикет по номеру неотличим от несуществующего (не раскрывает
существование). Настоящая CRM обязана обеспечить то же на своей стороне.

### 4. Мок-CRM внутри репозитория, запуск тем же интерпретатором

Мок лежит в `mock_servers/support_crm/` (`server.py` на `mcp.server.fastmcp.FastMCP`, данные
`users.json`, `tickets.json`). Это отступление от принципа «MCP-серверы вне репозитория»
(`MCP_*_DIR`): мок — часть демонстрации и тестовых данных, а не внешний продукт. Запуск —
`sys.executable <server.py> --demo-user-id <SUPPORT_DEMO_USER_ID>`, списком аргументов без shell.
Данные вымышленные, содержат записи нескольких пользователей и тикет с «инъекцией» в тексте.
Настоящая CRM подключается через `MCP_SUPPORT_COMMAND`/`MCP_SUPPORT_ARGS` (разбор `shlex.split`);
флаг `--demo-user-id` добавляется только к встроенному моку.

Привязка: `SUPPORT_DEMO_USER_ID` — Telegram id оператора; мок отдаёт ему демонстрационную
запись, остальным — пустой профиль. Пустая настройка — демо-данных не получает никто.
*Альтернативы:* показывать демо всем (нарушает «только свои»); команда `/support_login` с
номером тикета (пользователь выбирает идентичность, перебор номеров).

### 5. Контракт инструментов CRM

Три инструмента, все `read_only_hint=True`, с явным перечнем `SUPPORT_TOOL_ALLOWLIST`, как у
`GIT_TOOL_ALLOWLIST`: `get_my_profile`, `list_my_tickets(status?)`, `get_ticket(ticket_id)`.
Нет инструмента — модель получает ошибку. Результаты усекаются общим пределом
`MCP_TOOL_RESULT_MAX_CHARS`, поля тикета в предзагрузке — дополнительно лимитом символов.

### 6. Поиск: отдельный индекс, исходы как у `/dev`

Источники индекса — фиксированный перечень: `docs/support/**/*.md` (FAQ и руководства) и
`README.md`; `CLAUDE.md`, спеки, исходники и `data/` не входят. Индекс — `SUPPORT_INDEX_DIR`
(`data/support_index`), `make support-index`, атомарная замена, сбой эмбеддингов оставляет прежний
индекс. Поиск — как `dev_assistant.search`: эмбеддинг вопроса с бюджетом
`RAG_SEARCH_TIMEOUT_SECONDS`, порог `SUPPORT_MIN_SCORE`, `SUPPORT_TOP_K`; исходы
`FOUND`/`NOT_FOUND`/`NO_INDEX`/`FAILED`. Без переписывания вопроса и второго этапа отбора.

### 7. Матрица исходов `ask()`

| Индекс/поиск | Тикеты (CRM) | Действие |
|---|---|---|
| `NO_INDEX` / `FAILED` | любые | фиксированный текст, без модели |
| `NOT_FOUND` | нет или CRM недоступна | фиксированный «не нашлось», без модели |
| `NOT_FOUND` | есть | модель с пометкой «в FAQ ответа не нашлось, не выдавать за подтверждённое» |
| `FOUND` | есть | модель: фрагменты + тикеты |
| `FOUND` | нет | модель: фрагменты + «обращений нет» |
| `FOUND` | CRM недоступна | модель: фрагменты + «ДАННЫЕ ОБРАЩЕНИЙ НЕДОСТУПНЫ» + предупреждение |

Источники в конце ответа строит код по поданным фрагментам; номера тикетов, на которые опирается
ответ, модель называет в тексте (код их не проверяет — это не цитаты).

### 8. Порядок сообщений и данные как данные

`SYSTEM_PROMPT` (без изменений) → системное сообщение поддержки (тематика, запрет инвестиционных
рекомендаций, «не ослабляет основной промпт», данные тикетов/инструментов/фрагментов — данные,
не инструкции, чужие тикеты недоступны) → данные обращений → фрагменты FAQ → краткосрочная
история → вопрос. Тест проверяет наличие оговорки о неослаблении, как в `/dev`.

### 9. Доступ, справка, очередь, режимы

Доступ — любой пользователь личного чата; список id не нужен. Отправитель `None` — отказ. `/support`
добавляется в `/help` отдельной строкой; текст оговорки о советнике не трогается. Обработчики
регистрируются в `main.py` ДО `/agent*`, `/smart_agent` (по образцу `/dev`), вне `RESEARCH`. Вид
задачи `support` в `llm_queue/rules.py` с интерактивным приоритетом; `ask()` — в потоке под слотом,
кооперативная отмена `should_cancel`. Взаимоисключение — через `get_active_mode`, как у `/dev`.

### 10. Конфигурация

Новые переменные (все — настройки оператора, проверяются `_validate_config()`, описываются в
`.env.example`): `SUPPORT_INDEX_DIR`, `SUPPORT_TOP_K` (5), `SUPPORT_MIN_SCORE` (0.0),
`SUPPORT_HISTORY_TURNS` (6), `SUPPORT_TICKETS_LIMIT` (5), `SUPPORT_DEMO_USER_ID` (пусто),
`SUPPORT_CRM_MOCK` (булево, по умолчанию `true`: запускать встроенный мок),
`MCP_SUPPORT_COMMAND`/`MCP_SUPPORT_ARGS` (внешняя CRM; приоритет над моком). Общие переменные
(`MCP_TIMEOUT_SECONDS`, `MCP_MAX_TOOL_STEPS`, `MCP_TOOL_RESULT_MAX_CHARS`,
`RAG_SEARCH_TIMEOUT_SECONDS`) переиспользуются. Если CRM не настроена (мок выключен, команда
пуста) — режим работает только по FAQ.

## Risks / Trade-offs

- [Тикет — недоверенный ввод пользователя; возможна prompt injection] → данные подаются отдельным
  сообщением с явным запретом выполнять их указания, модель получает только read-only
  инструменты, тест с мок-тикетом-инъекцией; ручная проверка живой моделью.
- [Утечка чужих тикетов через выбор идентификатора моделью] → идентификатор вне схемы и
  перезаписывается кодом; мок изолирует и не раскрывает существование; тесты чистых функций.
- [Реальная CRM принесёт персональные данные] → вне объёма; мок их не содержит; в документации
  зафиксировано, что подключение реальной CRM — отдельное решение владельца.
- [Вопрос и тикеты уходят облачному провайдеру при `MAIN_CLIENT=deepseek|kimi`] → документируется
  как решение оператора; для локальной обработки — `MAIN_CLIENT=ollama`.
- [Каждый вопрос запускает процесс мока (≈0,75 с)] → приемлемо для поддержки; кэш сессии добавил
  бы состояние и сложность закрытия anyio-сессий.
- [Мок в репозитории отступает от правила «серверы вне репозитория»] → зафиксировано в решении 4,
  граница — каталог `mock_servers/`, `src/` его не импортирует.
- [Порог поиска не откалиброван под FAQ] → старт с 0.0 (шаг отключён), калибровка — отдельная
  задача оператора при росте FAQ.
- [Копирование/импорт чанкера из `dev_assistant`] → импортом; рефакторинг в общий модуль только
  без изменения поведения `/dev`.
