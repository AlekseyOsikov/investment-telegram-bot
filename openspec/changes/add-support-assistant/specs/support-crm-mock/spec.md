# Spec Delta

## Purpose

Определяет мок-сервер «CRM» для режима поддержки: MCP-сервер над JSON-файлами с вымышленными
пользователями и тикетами, дающий только чтение данных ОДНОГО пользователя, чтобы режим можно
было разрабатывать и проверять без реальной CRM и без персональных данных.

## ADDED Requirements

### Requirement: Контракт инструментов только для чтения

Мок-сервер SHALL предоставлять по протоколу MCP через стандартный ввод-вывод ровно три
инструмента: профиль пользователя, список обращений пользователя (с необязательным фильтром по
статусу) и обращение по номеру. Каждый инструмент SHALL быть помечен как только читающий. Сервер
NOT SHALL предоставлять инструментов создания, изменения или удаления данных и NOT SHALL изменять
исходные файлы.

#### Scenario: Перечень инструментов

- **WHEN** клиент запрашивает список инструментов сервера
- **THEN** сервер возвращает три инструмента, каждый с признаком «только чтение», и ни одного
  записывающего

#### Scenario: Файлы данных не меняются

- **WHEN** выполнена любая последовательность вызовов инструментов
- **THEN** исходные файлы данных остаются без изменений

### Requirement: Изоляция данных по пользователю

Каждый вызов инструмента SHALL принимать идентификатор пользователя Telegram и возвращать данные
только этого пользователя. Запрос обращения по номеру, принадлежащего другому пользователю, SHALL
давать тот же ответ «не найдено», что и запрос несуществующего номера, не раскрывая наличия
чужого обращения. Пользователь, не сопоставленный ни с одной записью, SHALL получать пустой
профиль и пустой список, а не ошибку.

#### Scenario: Чужое обращение

- **WHEN** пользователь запрашивает номер тикета, принадлежащего другому пользователю
- **THEN** ответ неотличим от ответа на несуществующий номер

#### Scenario: Список только своих

- **WHEN** в данных есть обращения нескольких пользователей и запрашивается список
- **THEN** возвращаются только обращения запрашивающего

#### Scenario: Неизвестный пользователь

- **WHEN** идентификатор не сопоставлен ни с одной записью
- **THEN** возвращаются пустой профиль и пустой список

### Requirement: Сопоставление демонстрационного пользователя

Сервер SHALL сопоставлять идентификатор Telegram с записью пользователя в данных через значение,
заданное оператором при запуске: этот идентификатор получает демонстрационную запись, прочие
идентификаторы — пустой профиль. Записи других вымышленных пользователей SHALL присутствовать в
данных, чтобы изоляцию можно было проверить. Если значение не задано, никто NOT SHALL получить
демонстрационные данные.

#### Scenario: Демонстрационный идентификатор

- **WHEN** сервер запущен с идентификатором оператора и этот идентификатор запрашивает список
- **THEN** возвращаются обращения демонстрационной записи

#### Scenario: Значение не задано

- **WHEN** сервер запущен без демонстрационного идентификатора
- **THEN** любой запрос получает пустой профиль

### Requirement: Вымышленные данные без чувствительных сведений

Данные мока SHALL быть полностью вымышленными: без реальных имён, адресов электронной почты,
номеров счетов и карт, сумм на счетах, паспортных и налоговых данных. Темы обращений SHALL
отражать реальные функции бота (рассылка сводок по расписанию, очередь запросов, недоступность
источника рыночных данных, ответ без найденных материалов). Данные SHALL содержать обращение с
текстом, похожим на инструкцию для модели, для проверки того, что тикет трактуется как данные.

#### Scenario: Состав данных

- **WHEN** проверяются файлы данных
- **THEN** в них нет персональных и финансовых сведений, а обращения относятся к функциям бота

#### Scenario: Обращение с инструкцией в тексте

- **WHEN** проверяются файлы данных
- **THEN** есть хотя бы одно обращение, текст которого пытается дать модели указание
