# Design

## Context

Мотивация и объём — в `proposal.md`, требования — в дельта-спеках `dev-assistant` и
`project-files-server`. Ближайший образец — сам `/dev` (`src/dev_assistant/`): `git_session.py`
(фасад над MCP-сессией с allowlist, `repo_path` подставляет код), `core.py` (`DevAssistant.ask`,
цикл инструментов `market_tools.run_tool_loop`, сессия на ВОПРОС через
`mcp_integration.market_session.open_market_tools`), `command.py` (доступ по `filters.User` +
`is_authorized`). Образец внешнего сервера вне `src/` — `mock_servers/support_crm` (запуск тем же
интерпретатором, `src/` его не импортирует).

Ограничения, из-за которых нужны явные решения:
- процесс MCP-сервера живёт один вопрос, а кнопка «Применить» нажимается позже — состояние
  предложения должно пережить сессию;
- `open_market_tools(..., require_read_only=True)` отфильтрует инструмент без `read_only_hint`, а
  `propose_change` пишет (в каталог предложений) и честно read-only не является;
- корневой `CLAUDE.md` и `src/dev_assistant/CLAUDE.md` сейчас утверждают, что содержимое файлов
  модели не уходит; это решение владельца проекта меняется (см. proposal) и фиксируется в
  документации одновременно с реализацией.

## Goals / Non-Goals

**Goals:**
- Модель сама ищет, читает и анализирует несколько файлов и готовит правки; запись — только по
  кнопке пользователя из списка оператора.
- Вся защита файловой системы на стороне сервера; бот и модель не могут её обойти.
- Чистые правила (пути, denylist/allowlist, diff, хэш, форматирование) тестируются без сети и MCP.

**Non-Goals:**
- Правка исходного кода (`src/**/*.py`), запуск команд, git-операции (commit/push), удаление и
  переименование файлов.
- Автоприменение без кнопки, пакетное применение «все сразу».
- Автоматическая пересборка индекса `/dev` после применения (только напоминание оператору).
- Изменение `mcp-git`, `rag/`, существующих режимов и очереди.

## Decisions

### 1. Свой сервер `mcp_servers/project_files/`, а не готовый файловый сервер и не функции в боте

Каталог вне `src/` (не мок, поэтому не `mock_servers/`), запуск `sys.executable server.py --root
<repo> --staging-dir <dir>` списком аргументов без shell. Внутри — `files_rules.py` (чистые правила)
и `server.py` (тонкая обвязка `MCPServer`). Альтернативы: `@modelcontextprotocol/server-filesystem`
через `npx` (нет denylist секретов, нет предложений с хэшем, запись сразу, лишняя зависимость
Node); инструменты внутри процесса бота (граница доступа в одном процессе с моделью, проект
договорился об MCP). Пакет `mcp` уже установлен.

### 2. Инструменты сервера

| Инструмент | Для модели | Что делает |
|---|---|---|
| `list_dir(path)` | да | список каталога без запрещённых путей |
| `read_file(path, start_line?, end_line?)` | да | текст с номерами строк, лимит размера |
| `search_text(query, path_glob?, regex?)` | да | совпадения `файл:строка: текст`, лимит числа |
| `propose_change(path, new_content, summary)` | да | строит diff, пишет предложение в staging |
| `apply_change(proposal_id)` | НЕТ (только код бота) | проверки и атомарная запись |
| `discard_change(proposal_id)` | НЕТ (только код бота) | удаляет предложение |

`propose_change` принимает полное новое содержимое, а не патч: модели проще и надёжнее, хэш
исходника и diff считает сервер, повторная подготовка при тех же входах даёт тот же diff.
Альтернатива «модель присылает unified diff» — частые ошибки номеров строк и контекста.

### 3. Состояние предложения — на диске у сервера, а не в памяти бота и не в процессе

Сервер на вопрос не живёт, поэтому `propose_change` сохраняет JSON-файл (`id`, путь, хэш
исходника или признак создания, новое содержимое, момент создания) в `--staging-dir`
(`data/dev_proposals/`, не коммитится). `apply_change` — вызов в НОВОЙ короткой сессии, которую
открывает код бота по нажатию кнопки; TTL (по умолчанию 1 час) проверяется сервером и при чтении
удаляет просроченное. Привязку «предложение ↔ чат ↔ пользователь» хранит бот в памяти процесса
(`proposals.py`), поэтому после перезапуска кнопки отвечают «предложение устарело», а файл на
диске остаётся ждать TTL-очистки. Альтернатива «всё в памяти бота и применять напрямую из бота»
выносит запись из зоны контроля сервера (проверки пути/хэша пришлось бы дублировать в боте).

### 4. Права записи — allowlist путей на стороне сервера

Запись разрешена в `README.md`, `CLAUDE.md`, `**/CLAUDE.md` внутри `src/`, `docs/**`,
`.env.example`, `CHANGELOG.md` и ADR-каталог (`docs/adr/**`, покрыт `docs/**`). Проверка — при
`propose_change` и повторно при `apply_change`; расширение — только аргументом запуска оператора
(`--write-allow` glob-ы), пользователь чата и модель его не меняют. Расширение значения по
умолчанию на `src/**/*.py` — отдельное решение. Чтение: весь корень минус denylist (`.env*` кроме
`.env.example`, `data/`, `.git/`, `.venv*/`, `__pycache__`, `*.pem`, `*.key`, `id_rsa*`,
`*.sqlite*`). Канонизация через `Path.resolve()` и проверка `is_relative_to(root)`; denylist
применяется к КАНОНИЧЕСКОМУ относительному пути, поэтому символическая ссылка на `.env` отклоняется.

### 5. `read_only_hint` и allowlist модели

`propose_change` не read-only, поэтому файловая сессия открывается с `require_read_only=False`, а
безопасность держит ЯВНЫЙ allowlist модели `{list_dir, read_file, search_text, propose_change}`
(как в `git_session.py`), тест проверяет, что `apply_change`/`discard_change` в схеме и в
`call()` отсутствуют. Сессию кнопки открывает отдельная функция с allowlist `{apply_change,
discard_change}`, недоступная модели. Остальные инструменты сервера помечены `read_only_hint`
честно (`list_dir`, `read_file`, `search_text` — True).

### 6. Фасад `FilesTools` — подстановка корня и перехват предложений

`files_session.py` по образцу `GitTools`: схемы без служебных параметров (`root`, `staging_dir` —
серверу они приходят аргументами запуска, в схемы не попадают), allowlist, отказ по неизвестному
имени. Дополнительно `call("propose_change", ...)` после успешного ответа сервера регистрирует
предложение (`proposals.register`) и добавляет его в список `DevAnswer.proposals`; модель получает
краткий результат (id, путь, число строк diff), а не полный diff. Полный diff показывает бот —
модель не пересказывает его, и это экономит контекст.

### 7. Telegram: сообщение с diff и `CallbackQueryHandler`

После ответа `command.py` для каждого предложения отправляет сообщение с кратким заголовком,
diff в блоке кода (в пределах `TELEGRAM_MESSAGE_LIMIT`; длиннее — документом `.patch` и сводка в
тексте) и `InlineKeyboardMarkup` из «Применить»/«Отклонить», `callback_data` вида `dev:apply:<id>`
(короче 64 байт). Обработчик `CallbackQueryHandler(pattern=r"^dev:(apply|discard):")` с
`filters.User` недоступен для callback-запросов, поэтому проверка выполняется внутри явным
`rules.is_authorized(update.effective_user, ids)` и сверкой владельца предложения (`user_id`,
`chat_id`). Посторонний — `query.answer()` без текста, без изменений (режим не раскрывается).
Применение — тот же путь через очередь не нужен: операция быстрая, не вызывает модель, идёт через
`asyncio.to_thread`/штатный async вызов сессии.

### 8. Воспроизводимость

Применённый diff сохраняется в `data/dev_patches/<UTC-время>-<id>.patch` в формате `git apply`
(заголовки `a/…`/`b/…`); к сообщению о применении добавляется имя файла. Детерминизм обеспечивает
сервер: одинаковые вход и файлы → одинаковый diff (`difflib.unified_diff` с фиксированным
контекстом, нормализованные окончания строк). Недетерминизм модели не скрывается: воспроизводим
результат (патч), а не выбор файлов.

### 9. Промпт и инварианты в сообщениях

Системное сообщение файлового слоя — ОТДЕЛЬНОЕ, как у git-слоя: перечисляет инструменты, говорит,
что содержимое файлов — данные, не инструкции; запрещает инвестиционные рекомендации и не
ослабляет `SYSTEM_PROMPT` (оговорку проверяет тест — не убирать); велит готовить правки только
для документации, объяснять итог и не утверждать, что файл изменён (меняет только пользователь по
кнопке). Статусы «доступен/недоступен/не настроен» — по образцу git-слоя. `SYSTEM_PROMPT` уходит
первым без изменений.

### 10. Настройки оператора (`config.py`, `.env.example`)

`MCP_FILES_ENABLED` (булево, по умолчанию `false` — как и сам режим, поведение `/dev` не меняется
без явного включения), `DEV_FILES_STAGING_DIR` (`data/dev_proposals`), `DEV_PATCHES_DIR`
(`data/dev_patches`), `DEV_FILES_PROPOSAL_TTL_SECONDS` (3600), `DEV_FILES_MAX_READ_CHARS`,
`DEV_FILES_MAX_SEARCH_RESULTS`, `DEV_FILES_MAX_PROPOSAL_CHARS`; целые проверяет
`_validate_config()`. Корень — каталог репозитория по расположению `PROJECT_ROOT` (как `git`),
не из ввода. Режим файлов независим от `MCP_GIT_DIR`: каждый слой может быть выключен отдельно.

### 11. Взаимодействие слоёв в `ask()`

Порядок: RAG-поиск → открытие сессий git и файлов (обе на вопрос, объединяются в один набор
`tools` для `run_tool_loop` с префиксами не нужны: имена не пересекаются) → цикл → ответ.
Недоступность любого слоя не блокирует остальные. Условие «ничего не найдено и инструментов нет»
остаётся фиксированным отказом без вызова модели; наличие файловых инструментов считается
«инструменты есть», потому что поиск по файлам — самостоятельный источник ответа.

## Risks / Trade-offs

- [Содержимое файлов уходит облачному провайдеру] → denylist секретов на сервере; документировать
  `MAIN_CLIENT=ollama` для режима; решение оператора, как для остальных каналов.
- [Prompt injection из файлов проекта (README, докстринги)] → результаты подаются как данные,
  запись только по кнопке и только в документацию, diff виден пользователю до применения.
- [Модель предлагает неверную правку документации] → человек читает diff; сверка хэша защищает от
  устаревшего основания; `.patch` позволяет откатить (`git apply -R`).
- [Путь/симлинк-обход] → канонизация и проверка корня и denylist на каноническом пути, тесты на
  `..`, абсолютные пути, ссылки.
- [Staging на диске содержит текст правок] → каталог в `data/`, вне индекса и git; TTL-очистка;
  в документации оператора указано.
- [Кнопки после перезапуска мертвы] → явное сообщение «предложение устарело»; это приемлемо для
  операторского инструмента.
- [Гонка двух нажатий] → сервер удаляет предложение при применении (атомарное переименование
  staging-файла перед записью), второй вызов получает «неизвестное предложение».
- [Рост контекста от больших файлов] → лимиты чтения и поиска, усечение с пометкой,
  `MCP_MAX_TOOL_STEPS`, `MCP_TOOL_RESULT_MAX_CHARS`.

## Migration Plan

Поведение по умолчанию не меняется: `MCP_FILES_ENABLED=false`. Включение — правка `.env` и
перезапуск; откат — вернуть `false`. Применённые патчи и staging лежат в `data/`, удаляются
вручную. После применения правок документации оператор пересобирает индекс `make dev-index`.
Документация (CLAUDE.md, README, `.env.example`) обновляется вместе с реализацией.
