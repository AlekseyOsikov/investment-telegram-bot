# Design

## Context

Мотивация — см. `proposal.md` («Why»), требования — `specs/smart-agent-market-tools/spec.md`
и `specs/mcp-integration/spec.md`.

Что из текущего состояния кода определяет подход:

- `SmartAgent.ask()` (`agents/smart_agent.py`) — СИНХРОННЫЙ: один вызов
  `client.chat.completions.create(...)` без инструментов, затем запись пары в
  `short_term`. Вызывается из async-обработчика `smart_agent_receive_question` прямо,
  без `to_thread`, то есть блокирует event loop на время запроса к LLM.
- Обновления в PTB обрабатываются ПОСЛЕДОВАТЕЛЬНО (`concurrent_updates` в `main.py` не
  включён), поэтому один и тот же `SmartAgent` чата не вызывается из двух мест разом.
- Официальный MCP SDK — АСИНХРОННЫЙ. `mcp_integration/client.py` уже подключается к
  серверу по stdio циклом «процесс → рукопожатие → `list_tools()` → закрыть» без
  кэша сессии; он диагностический и в этом изменении не меняется.
- Слои контекста `SmartAgent` (`profile`/`invariants`/`short_term`/`working`/
  `long_term`) — константы `LAYER_*`, `ALL_LAYERS`, общий на чат `enabled_layers`.
  `_load_state()` стартует с «все слои включены» и накладывает сохранённые значения
  только для известных слоёв — поэтому старые файлы без нового ключа читаются как
  «включён» без отдельной миграции.
- Правила и тексты вынесены из класса-владельца состояния в отдельные модули
  (`agents/task_state.py`, `agents/invariants.py`); `SmartAgent` владеет состоянием,
  диском и вызовами LLM.
- Замер на живом сервере `mcp-moex` (спайк до написания этого дизайна):
  - рукопожатие ≈ 0,75 с на запуск процесса;
  - `get_price_history` возвращает до 300 свечей — около 62 000 символов
    pretty-printed JSON, сводка в начале, в конце самые свежие свечи;
  - успешный результат имеет `structured_content`; ошибка приходит как
    `is_error=True` и русский текст, написанный для LLM («Error executing tool …:
    Бумага с тикером … не найдена … Найдите тикер через search_securities»).
- Спайк цикла tool-calls на DeepSeek (`MAIN_MODEL=deepseek-flash`): цикл работает без
  возврата `reasoning_content`; параллельные вызовы (два `tool_calls` за шаг) работают;
  цикл заканчивается за 2 шага; `thinking` отключать не нужно. `reasoning_content` на
  шагах с вызовом инструмента не приходил вовсе. Kimi не проверялся.

## Goals / Non-Goals

**Goals:**

- Дать основному ответу `/smart_agent` цикл вызова инструментов, не ломая ни один
  существующий слой памяти, инварианты и автомат задачи.
- Изолировать механику MCP (подключение, схема инструментов, вызов, сжатие результата)
  от правил и текстов агента — тем же разделением, что `client.py`/`tools_command.py`
  и `task_state.py`/`smart_agent.py`.
- Любая неудача инструмента или сервера превращается в текст модели или предупреждение
  пользователю, но не в потерянный ответ.
- Всё, что не требует сети (преобразование схем, разбор аргументов, сжатие и усечение
  результата, тексты), — чистые функции, покрытые тестами без моков MCP-сессии.

**Non-Goals (дополнительно к не-целям из `proposal.md`):**

- Перевод остальных синхронных вызовов LLM (автомат задачи, детектор старта, ревизор)
  на `to_thread`. Они по-прежнему блокируют event loop, как и до изменения.
- Отдельная переменная для команды запуска (`uv`). Захардкожена, см. решение 7.
- Проверка семантики ответа (что модель действительно назвала задержку). Это забота
  формулировки сообщения слоя, а не кода.

## Decisions

### 1. Механика MCP — отдельный модуль `mcp_integration/market_session.py`

Асинхронный контекстный менеджер `MarketToolsSession`: запускает `uv run --directory
<MCP_MOEX_DIR> mcp-moex`, делает рукопожатие и `list_tools()` под общим
`MCP_TIMEOUT_SECONDS`, оставляет только read-only инструменты и отдаёт их в формате
OpenAI (`{"type":"function","function":{name, description, parameters=input_schema}}`),
а метод `call(name, arguments_json) -> str` выполняет вызов. Исключение из-за
неудачи ИНСТРУМЕНТА (неизвестное имя, невалидный JSON аргументов, `is_error`, обрыв
обмена) наружу не выходит — метод возвращает текст ошибки (решение 4); исключением
остаётся только неудача ЗАПУСКА сервера, которую перехватывает вызывающий код и
превращает в режим «без инструментов».

Существующий `client.py` не переиспользуется и не меняется: его функция делает
целый цикл «подключиться → перечислить → закрыть» и не оставляет сессию открытой, а
здесь сессия нужна на весь вопрос. Общий код — только `StdioServerParameters` и тот же
таймаут; вынести общий базовый класс ради двух десятков строк — преждевременно.

Правила и тексты для агента — в `agents/market_tools.py` (по образцу
`agents/invariants.py`): сообщение слоя для контекста (два варианта — сервер доступен /
недоступен), строка о вызове, строка статуса, предупреждение пользователю.

### 2. Мост sync/async: `ask()` остаётся синхронным, `asyncio.run` внутри `to_thread`

Командный слой вызывает `await asyncio.to_thread(agent.ask, user_text)`; внутри `ask()`
при доступном слое `tools` выполняется `asyncio.run(self._ask_with_tools(...))` — свой
цикл событий рабочего потока, внутри него `await` MCP-вызовов и обычные синхронные
вызовы `openai` (блокируют только этот рабочий поток).

Почему так, а не `async def ask()`: `ask()` вызывается ровно из одного места, но у
него есть побочные эффекты на состояние (`short_term`, `_save_state`), тесты и
докстринги завязаны на синхронный контракт, а перевод в async потянул бы за собой
весь класс. Побочная выгода: event loop перестаёт блокироваться на время запроса к
LLM — правда, только для основного ответа.

Безопасность потоков: состояние `SmartAgent` трогает один рабочий поток на время
ответа, а обновления PTB идут последовательно — ни два вопроса подряд, ни команда
`/smart_agent_toggle` посреди ответа на тот же чат не выполняются одновременно. Если кто-то включит `concurrent_updates`, это предположение нужно
пересмотреть — оговорка идёт в докстринг `ask()`.

Ограничение: `asyncio.run()` бросит `RuntimeError`, если `ask()` вызвать в потоке с
уже работающим циклом. Единственный вызывающий — командный слой, он оборачивает
вызов в `to_thread`; это фиксируется в докстринге.

Альтернативы: (а) `async def ask()` — отвергнуто, см. выше; (б) держать отдельный
поток с постоянным циклом событий на весь процесс бота и слать в него корутины —
отвергнуто как лишняя инфраструктура без выгоды при подходе «процесс на вопрос».

### 3. Сессия — один процесс на вопрос, запуск в начале `ask()`

Процесс сервера запускается в начале ответа (схемы инструментов нужны ДО первого
обращения к модели), живёт на все вызовы этого вопроса и закрывается при выходе из
`async with`. Цена — ≈0,75 с на каждый вопрос при включённом слое, даже если
рыночные данные не нужны.

Альтернатива, рассмотренная и отложенная: запускать процесс лениво, только когда
модель уже запросила вызов, а схемы брать из кэша в памяти процесса бота. Экономит
задержку на нерыночных вопросах, но требует кэша с инвалидацией, а сбой запуска
обнаруживается уже посреди вопроса, а не в начале. Для первой версии простота
важнее; пользователю остаётся `/smart_agent_toggle tools` для вопросов без бирж. См.
«Открытые вопросы».

Если слой выключен или `MCP_MOEX_DIR` не задан — процесс не запускается и `asyncio.run`
не вызывается вовсе: путь без инструментов идёт по прежнему синхронному коду
(`_ask_plain`). Запрос к модели при этом остаётся прежним (без ключа `tools`); единственное
отличие — при выключенном слое и настроенном сервере в контексте одно короткое
системное сообщение (решения 8 и 9). Без `MCP_MOEX_DIR` поведение и стоимость
существующего чата не меняются вовсе.

### 4. Цикл вызовов

Копия списка сообщений → до `MCP_MAX_TOOL_STEPS` (по умолчанию 5) обращений к модели
с `tools=...`. Если ответ — `tool_calls`: в историю цикла добавляется сообщение
ассистента (с `tool_calls`, а `reasoning_content` — если он есть в сообщении; спайк
показал, что без него цикл работает, а возврат — страховка, которую мы не смогли
проверить, так как на шагах с вызовом он не приходил), затем на КАЖДЫЙ вызов —
сообщение `role: "tool"`. Вызовы одного шага выполняются последовательно: их обычно
один-два, а один процесс сервера с одной сессией не получает выгоды от параллельности.
Если после лимита модель всё ещё просит вызовы, делается ещё одно обращение БЕЗ
`tools`, чтобы получить финальный текст, и пользователю уходит строка о лимите.

Ошибки уровня инструмента всегда становятся содержимым сообщения `tool`:
неизвестное имя («такого инструмента нет»), инструмент без read-only-пометки (то же
сообщение, вызова сервера нет), `arguments`, не разбираемые как JSON-объект,
`is_error=True` (текст сервера как есть — он уже написан для LLM), исключение обмена
с сервером и тайм-аут вызова. Обрыв обмена дополнительно даёт предупреждение в `warnings`.

Разбор аргументов — чистая функция `parse_arguments(raw) -> dict | error`, потому что
именно здесь модель чаще всего ошибается, и это покрывается тестами без сети.

Сам цикл — функция в `agents/market_tools.py` с ВНЕДРЯЕМЫМИ вызовами `complete(messages,
with_tools)` и `call_tool(name, arguments)`: она не знает ни про OpenAI SDK, ни про MCP,
поэтому ветвления цикла (несколько вызовов за шаг, лимит, неизвестный инструмент,
ответ без вызовов) проверяются тестами на простых фейковых функциях, без сети и без
моков класса `SmartAgent`. `SmartAgent` лишь передаёт ей реальные `complete`/`call_tool`
и собирает результат.

### 5. Read-only фильтр — по аннотации сервера, строго

Инструмент попадает к модели только при `tool.annotations.read_only_hint is True`.
Отсутствие аннотации — НЕ read-only: по умолчанию в протоколе инструмент считается
потенциально изменяющим, а фильтр — защита на случай, если в `mcp-moex` когда-нибудь
добавят пишущий инструмент. `mcp-moex` помечает все три. Имя поля в MCP SDK 2.x —
snake_case (`read_only_hint`), в `requirements.txt` закреплён `mcp>=2.2,<3`.

### 6. Результат инструмента → текст для модели

Порядок: `is_error` → текст сервера как есть; иначе, если есть `structured_content`,
он сериализуется КОМПАКТНО (`separators=(",", ":")`, `ensure_ascii=False`) — без
отступов pretty-print, которые в замере давали заметную часть 62 000 символов;
иначе — склеенный текст блоков контента. Затем предел `MCP_TOOL_RESULT_MAX_CHARS`:
при превышении сохраняется НАЧАЛО (там сводка и заголовок), в конец добавляется
пометка «результат обрезан … запроси меньший период или более крупный interval».

Значение по умолчанию выбирается так, чтобы полный ответ сервера (его собственный
предел — 300 свечей) в компактном виде УМЕЩАЛСЯ: предел — предохранитель от
аномально больших результатов, а не штатная обрезка. Точное число фиксируется на этапе
реализации замером (задача 1.3): компактный ответ на 300 свечей занял ≈42 300
символов (pretty-print — ≈62 200), поэтому по умолчанию стоит 45 000. Обрезка с головы плохо
сочетается с хронологическим порядком свечей (пропадут самые свежие) — поэтому
предел не должен срабатывать штатно, а пометка направляет модель к более крупному
интервалу.

Альтернативы: сохранять голову и хвост (сложнее и портит JSON так же); знать формат
конкретного инструмента и вырезать свечи (привязка к чужому серверу, ломается при
его изменении); отдавать pretty-print как есть (в 2–3 раза больше токенов).

### 7. Настройка: `MCP_MOEX_DIR`, команда `uv` захардкожена

`MCP_MOEX_DIR` — путь (после `expanduser`); пусто/не задан → возможность неактивна.
Команда `uv` с аргументами `["run", "--directory", <dir>, "mcp-moex"]` собирается в
коде списком, без shell — тот же принцип, что у `MCP_SERVER_COMMAND`/`ARGS`
(`StdioServerParameters` не вызывает оболочку, подстановок нет). Отдельная переменная
для программы запуска не заводится: пользователь просил вынести в окружение именно
каталог, а её добавление тривиально позже.

Проверка каталога при старте (`config.py`): существует ли он и есть ли в нём
`pyproject.toml`; если нет — `logger.warning`, процесс НЕ останавливается (тот же
принцип, что у необязательного ключа неосновного провайдера). Остальная проверка
(`uv` в `PATH`) происходит на запросе: `FileNotFoundError` при запуске → режим
«без инструментов».

Дочернему процессу `stdio_client` передаёт только безопасное подмножество окружения
(`PATH`, `HOME` и т. п.) — прокси бота (`ALL_PROXY` и т. д.) он не наследует, а сам
`mcp-moex` ходит на ISS напрямую (`trust_env=False`). Если сеть хоста требует прокси
для биржи, эта схема не заработает — сознательно вне объёма.

### 8. Слой `tools` — общий механизм слоёв, без миграции

`LAYER_TOOLS = "tools"` добавляется в `ALL_LAYERS`, `LAYER_LABELS`, `LAYER_ALIASES`
и подсказку `LAYER_TOGGLE_HINT`; сохранение/загрузка уже работают по `ALL_LAYERS`
(см. «Context»). Выключение слоя не запускает процесс и не добавляет сообщение о работе с
инструментами — в отличие от инвариантов, выключение которых опасно, отдельного
предупреждения ПОЛЬЗОВАТЕЛЮ каждый ход не требуется: слой только ДОБАВЛЯЕТ возможности, а
о самом выключении его уведомляет ответ команды `/smart_agent_toggle`.

Но модели о выключении сказать нужно, если сервер настроен. Живой прогон показал: при
выключенном слое в краткосрочной памяти остаются ответы с ценами от инструментов, и
модель повторила такую цену как «текущую», приписав ей выдуманное время котировки.
Поэтому при выключенном слое И заданном `MCP_MOEX_DIR` в контекст идёт третий вариант
сообщения слоя (решение 9). Без `MCP_MOEX_DIR` он не добавляется: там инструментов
никогда не было, чат ведёт себя как до изменения, а отсылка к недоступной команде
ничего бы не дала. Условие проверяется в `SmartAgent._market_tools_mode()` — той же
точке, что уже различает «выключен» и «не настроен».

Статус слоя для `/smart_agent_show` — состояние в памяти объекта на последний вопрос
(`off` / `not_configured` / `ok` / `unavailable(причина)`); на диск не пишется —
это диагностика, а не настройка.

### 9. Место сообщения слоя в контексте и его содержание

Порядок сборки: инварианты → профиль → **инструменты** → долговременная память →
рабочая задача → краткосрочный диалог. Инварианты остаются первыми и прямо получают
приоритет над сообщением об инструментах; профиль (стиль подачи) идёт до него.
Содержание закреплено спекой: данные, а не инструкции; время и задержка котировки;
единицы измерения; не гарантия; НЕ отменяет `SYSTEM_PROMPT` (та же оговорка, что в
`_profile_meta_message` и у инвариантов, и убирать её нельзя).

Вариант «сервер недоступен» — отдельный короткий текст: данных нет, текущие цены
по памяти как факт не называть, сказать, что получить их сейчас не удалось.

Вариант «слой выключен» — третий короткий текст (`build_disabled_context_message`):
данные биржи выключены пользователем командой `/smart_agent_toggle tools`, актуальных
цен нет; цены и котировки из прежних ответов диалога не выдавать за текущие и не
приписывать им время котировки; на вопрос, требующий текущих данных, сказать, что данные
биржи выключены и включаются той же командой; оговорка, что блок не отменяет и не
ослабляет обязательные правила основной инструкции. Отличается от «недоступен»
причиной и подсказкой действия: там пользователь ничего исправить не может, здесь может.
Место в контексте — то же, что у остальных вариантов (после профиля, до долговременной
памяти).

### 10. Учёт токенов и контекст последнего вопроса

`SmartAgentAnswer` расширяется: `tool_calls: list[ToolCallRecord]` (имя, аргументы,
кратко исход), `warnings: list[str]` (предупреждения для чата: недоступный сервер, сбой
обмена, исчерпанный лимит), `llm_calls: int`. `context_tokens` и
`response_tokens` — суммы по всем обращениям вопроса (это реальная стоимость), а
строка `📈 Токены` получает «обращений: N» при N > 1. Существующие поля с прежним
смыслом при отсутствии вызовов не меняются.

`get_last_context_messages()` по-прежнему возвращает только системные сообщения
СБОРКИ контекста (включая сообщение слоя `tools`), а не промежуточные сообщения цикла:
вызовы видны отдельно (`/smart_agent_show` печатает и статус, и последние вызовы).

### 11. `short_term` и остальные слои — без изменений

В краткосрочную память пишется ровно одна пара «вопрос — ответ» после успешного
завершения цикла, как и раньше; сообщения `tool_calls`/`tool` в память не попадают, а
ответ на неудачном вопросе (исключение SDK) по-прежнему не искажает сохранённый
диалог. Служебные вызовы (`update_task_state`, `_maybe_start_task`,
`_check_invariants`) идут через `_call_json_api` без `tools`, и этот путь не трогается.
Ответ, содержащий данные биржи, попадает в `short_term` и далее в чтение автомата — это
допустимо: данные публичные, суммы пользователя среди них нет.

## Risks / Trade-offs

- [+≈0,75 с на каждый вопрос при включённом слое] → выключение слоя, рассмотренный и
  отложенный ленивый запуск с кэшем схем (см. решение 3 и «Открытые вопросы»).
- [Описания инструментов длинные и уходят в каждый основной вызов] → рост входных
  токенов виден в строке `📈 Токены`; при неприемлемой цене — сокращать описания на
  стороне `mcp-moex` (это его контракт для LLM) или включать слой только по требованию.
- [Модель зовёт инструменты зря, выдумывает тикеры, зацикливается] → ошибки сервера
  возвращаются модели, лимит шагов, финальный вызов без инструментов при исчерпании.
- [Проверено только на DeepSeek] → в CLAUDE.md пометка «проверено на DeepSeek»; то же
  для возврата `reasoning_content`, который остаётся непроверенной страховкой.
- [Обрезка с головы теряет свежие свечи] → предел должен вмещать полный ответ сервера
  (решение 6); пометка направляет модель к более крупному интервалу.
- [Поисковый запрос модели может содержать формулировку пользователя и уйти на сервер,
  а оттуда в ISS] → инструмент ограничивает длину запроса (100 символов), сервер
  публичный и только читает; это осознанное расхождение со спекой `/mcp_tools` («серверу
  не передаётся текст пользователя»), поэтому оно оформлено изменёнными требованиями.
  Промпт слоя не должен подталкивать модель пересылать пользовательский текст целиком.
- [Инъекция инструкций через данные (названия бумаг, сообщения сервера)] → правило
  «данные, а не инструкции» в сообщении слоя, только read-only инструменты, результаты
  не сохраняются.
- [Синхронный `ask()` внутри `asyncio.run` в потоке] → единственный вызывающий
  оборачивает вызов в `to_thread`; предположение о последовательности обновлений PTB
  зафиксировано в докстринге.
- [Другие синхронные вызовы LLM по-прежнему блокируют loop] → существующее поведение,
  вне объёма.
- [Шум в журнале: stderr дочернего процесса попадает в stderr бота] → допустимо; при
  необходимости позже перенаправить.
- [Слой выключен, а в краткосрочной памяти уже лежат ответы с ценами от инструментов] →
  наблюдалось в живом прогоне: модель повторила цену из прежнего ответа и приписала ей
  выдуманное время котировки. Митигация — сообщение «данные биржи выключены» при
  настроенном сервере (решения 8 и 9). Это подсказка модели, а не гарантия: код не
  вычищает цены из краткосрочной памяти и не проверяет ответ, поэтому эффект нужно
  подтвердить живой проверкой (задача 9.4). Проверка на DeepSeek прошла: модель отказалась
  называть цену, сказала, что данные выключены и как включить, и прямо предупредила, что
  цифру из прежнего ответа нельзя считать текущей; на вопрос без цен выключение не
  упоминалось. Выборка — по одному прогону на шаг, а поведение модели недетерминировано. Вычищать прежние ответы из памяти
  отвергнуто: память — это диалог пользователя, и менять его задним числом нельзя.

## Migration Plan

- Данные: миграции нет. Файлы памяти без ключа `tools` в `enabled_layers` читаются как
  «включён».
- Развёртывание: `uv` в `PATH` бота, задать `MCP_MOEX_DIR` в `.env`, перезапустить.
  Ничего не задать — бот работает как раньше.
- Откат: убрать `MCP_MOEX_DIR` из `.env` и перезапустить (слой неактивен и молчит) либо
  точечно — `/smart_agent_toggle tools` в конкретном чате. Файлы памяти при этом
  совместимы в обе стороны (`enabled_layers` с лишним ключом старым кодом отбрасывается
  как неизвестный слой).
- `requirements.txt` не меняется: `mcp` уже есть.

## Open Questions

- Нужен ли ленивый запуск с кэшем схем инструментов, если ≈0,75 с на каждый ход
  окажутся заметными на практике? Не меняет спеку — только внутренность `ask()`.
- Стоит ли перевести служебные вызовы LLM `SmartAgent` тоже на `to_thread`, раз
  основной ответ уже переведён? Существующее поведение, решается отдельно.
- Проверка цикла на Kimi (`MAIN_CLIENT=kimi`): не входит в этот change, при переходе
  на него нужен свой спайк.
