# Design

## Context

См. `proposal.md` — зачем. Что есть сейчас (проверено по коду):

- `SmartAgent.ask()` вызывает `_retrieve_materials()` на каждый вопрос; пустой результат с
  `Materials.searched=True` при выключенных `tools` даёт `should_abstain()` → фиксированный отказ
  без модели. При `searched=False` (слой выключен, индекса нет, сбой) режим «не знаю», блок
  правил про цитаты и повтор за цитатами не включаются — они завязаны на непустые `chunks`/
  `searched`.
- Пометка «в материалах ничего не нашлось» уже есть: `rag_context.NO_MATERIALS_NOTE` и
  `needs_no_materials_note()` (поиск состоялся, чанков нет, модель вызвана). Новая пометка для
  требования «источники или явная строка» не нужна.
- Автомат: `TaskStage` (frozen dataclass) в `task_state.py`, сценарии — записи `SCENARIOS`,
  этап `validation` строится общей `_validation_stage()`. Технический вызов автомата идёт ПОСЛЕ
  ответа, поэтому на вопросе видно состояние задачи после предыдущего хода.
- Раннеры без Telegram уже есть по образцу `research/rag_compare.py` (изолированный `SmartAgent`
  с `tempfile`-памятью, `mcp_*_dir=""`) и `scripts/rag_calibrate.py` (одноразовый скрипт, файлы
  запросов в `data/`); чистые функции оценки вынесены в `research/*_eval.py` и покрыты тестами.

## Goals / Non-Goals

**Goals:**
- Убрать застревание сбора вводных/приёмки из-за режима «не знаю» и давления цитат, не трогая
  поиск там, где он нужен (`execution`, `asset`).
- Получить воспроизводимый прогон длинного диалога с проверками по ходам.

**Non-Goals:**
- Распознавание «настоящего вопроса к корпусу» посреди этапа по тексту реплики (ненадёжно; для
  этого был бы мягкий режим — отдельное решение).
- Передача `goal`/`data` в переписывание вопроса; изменение гейтов, ключей и переходов автомата.
- Команда бота для раннера (раннер — оснастка оператора, `RESEARCH`-флаг не нужен).

## Decisions

**1. Признак — поле `rag_search: bool = True` на `TaskStage`.** Значение `False` у
`planning` и `validation` сценариев `portfolio`/`review`; у `asset` и `execution` — по умолчанию.
`_validation_stage()` принимает параметр, чтобы `asset` оставил поиск включённым. Альтернативы:
(а) множество «этапов без поиска» отдельной константой — размазывает свойство этапа по двум
местам, а `gate`, `sequential_keys` уже живут в записи; (б) трёхзначный режим `on|soft|off` —
вне объёма по решению владельца; (в) эвристика по тексту реплики — ненадёжна и недетерминирована.

**2. Чистая функция `task_state.search_allowed(task) -> bool`.** `None`, завершённая, приостановленная
задача → `True`; иначе — признак текущего этапа. Условия «есть активный профиль» и «слой
`working` включён» проверяет `SmartAgent` (слой выключен — состояние не участвует в контексте, и
признак его не должен «подсматривать»). Эти условия — в одном приватном методе агента, чтобы
`ask()` не разрастался.

**3. Пропуск — до `_retrieve_materials()`, результат — `Materials` с новым полем
`skipped_by_stage: bool`.** Пустой `chunks`, `searched=False` — поэтому режим «не знаю», блок
правил и повтор за цитатами не срабатывают без правок их кода. `skipped_by_stage` нужен ровно
для двух вещей: строки в служебном сообщении (`format_answer_service_lines` получает
необязательный `stage_skip_note`, как `no_materials_note`) и показа состояния
(`get_rag_status()`/`describe_search()` — «пропущен этапом задачи»). `_last_rag_search`/`_last_rag_failure`
на пропущенном ходу очищаются, как в начале `_retrieve_materials`, — иначе `/smart_agent_show`
показал бы поиск прошлого вопроса. Строка пропуска — константа в `rag_context.py` рядом с
`NO_MATERIALS_NOTE`, с тестом на неизменность текста.

**4. Раннер: чистая логика в `src/research/dialog_eval.py`, CLI — `scripts/dialog_eval.py`.**
Тот же раскол, что у `rag_compare_eval.py` и `rag_calibrate.py`: тестируется то, что без сети.
Чистое: разбор/проверка формата сценария (JSON: `name`, `task: {type, goal}`, `turns: [str]`),
проверки хода по двум снимкам (`before`, `after`) состояния задачи и признакам ответа, формат
итоговой таблицы. CLI: создаёт `SmartAgent` во временном каталоге (`mcp_*_dir=""`,
`cbr_enabled=False`), профиль и задачу (явный старт тем же вызовом, что `/smart_agent_task_start`,
чтобы цель не зависела от автодетектора), на каждую реплику — `ask()`, затем
`update_task_state()`. Отчёт — файл в `data/dialog_eval/` (в `.gitignore` уже есть `data/`;
проверить при реализации). Альтернатива «режим `/research_*`» отвергнута: нужен не оператор в
чате, а воспроизводимый пакетный прогон, а `RESEARCH` требует регистрации команды и записи в
`/help`.

**5. «Ключ не пропал» учитывает законные откаты.** `_roll_back` намеренно чистит ключи этапов
после целевого, гейт-отказ чистит `brief`/`brief_verdict`, ревизор инвариантов откатывает этап.
Поэтому проверка сверяет пропажу ключа с `task_state.transitions(task)` (причина `by`:
`rollback`, `gate_rejected`, `rejected`, `invariants`): пропажа без новой записи такого рода —
нарушение; с записью — допустимо, но «откат без записи причины» тоже нарушение.

**6. Пока задача активна, отказ «не знаю» без вызова модели не применяется — на любом этапе.**
Живой прогон раннера (два сценария по 12 реплик) показал, что одного флага этапа недостаточно: на
`execution` при выключенных `tools` отказ получали реплики, не являющиеся вопросами к корпусу
(«предложи, что поменять», «принимаю предложенные изменения»), и задача не доходила до `done`.
Поэтому `rag_context.should_abstain(materials, tools_can_participate, task_active)` не даёт отказа
при `task_active=True`: поиск состоялся без чанков → модель вызывается с
`build_no_materials_message()`, в служебном сообщении `NO_MATERIALS_NOTE` (путь, который уже есть при
доступных `tools`; `needs_no_materials_note` получает то же условие). `rag_search` и отказ —
НЕЗАВИСИМЫЕ условия: первое решает, искать ли на этапе, второе — можно ли ответить без модели;
активная задача → поиск по этапу, отказа без модели нет вообще. «Активна» — активный профиль, слой
`working` включён, задача существует, не на паузе и не `done`; признак считает один приватный метод
`SmartAgent` (общий с `_search_skipped_by_stage`), чистая функция его не вычисляет. Вне активной
задачи поведение прежнее. Альтернативы: (а) выключить поиск и на `execution` — теряются источники
там, где они нужнее всего; (б) трёхзначный режим `on|soft|off` — вне объёма, отказ отменяется
одним условием без нового режима; (в) оставить как есть — задача не завершается.

## Risks / Trade-offs

- [Реальный вопрос к корпусу посреди `planning`/`validation` отвечается без материалов и цитат]
  → осознанный компромисс (булев флаг по решению владельца); явная строка в служебном сообщении
  говорит, что поиск не выполнялся; вне этапа/после паузы поиск работает; мягкий режим — отдельное
  изменение при необходимости.
- [На активной задаче при пустом поиске модель отвечает без материалов и может говорить без опоры
  на корпус] → указание модели из `build_no_materials_message()` (не выдавать ответ за подтверждённый
  материалами) и пометка «ничего подходящего не нашлось» в служебном сообщении; вне активной
  задачи отказ прежний.
- [Раннер использует живые LLM и Ollama: стоимость и недетерминизм] → запуск вручную оператором,
  не часть `make test`; тесты — только на чистые функции; `temperature` модели прогона — как в
  боте (результаты сравнивать по свойствам, а не по тексту).
- [Задержка состояния: решение о поиске принимается по этапу ДО текущего хода, а переход
  происходит после ответа] → описано в спеке («по этапу, на котором задача стояла к моменту
  вопроса»); логика предсказуема и тестируется на состоянии.
- [Файлы сценариев и отчёты содержат тексты корпуса] → только в `data/` (не коммитятся); в тестах
  и документации — вымышленные примеры.
