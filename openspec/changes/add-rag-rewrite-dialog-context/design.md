# Design

## Context

Мотивация и состав изменения — `proposal.md`, требования — дельта-спеки. Исходное состояние
(после `add-rag-rerank-and-rewrite`):

- `SmartAgent._rewrite_query(user_text)` вызывает модель переписывания с сообщениями из
  `rag_rewrite.build_messages(question)`: неизменный system-промпт и user-сообщение
  `<вопрос>…</вопрос>`. Больше модель ничего не видит. Результат — только поисковый запрос;
  при сбое поиск идёт по исходному вопросу.
- `ask()` вызывает `_retrieve_materials()` ДО дописывания пары в `short_term`, поэтому в момент
  поиска `profile["short_term"]` содержит только предыдущие реплики (пары `user`/`assistant`);
  слой `short_term` включается и выключается `/smart_agent_toggle short`, очищается
  `/smart_agent_reset`.
- `/research_rag_compare` строит ИЗОЛИРОВАННЫХ агентов (пустая память), режимы поиска —
  параметры конструктора (`_mode_agent_kwargs`), переписывание делается один раз на вопрос и
  переиспользуется. Контрольный набор (`Question`: вопрос, тип, факты, источники) лежит в
  `data/rag_eval/`, не коммитится.
- Режим `REWRITE_SEARCH_MODE=both` ищет и по исходному вопросу, и по переписанному, объединяет
  кандидатов по лучшей оценке.
- Измерения прошлого изменения: оба набора вопросов самодостаточные, поэтому выигрыш контекста
  диалога в них не виден.

## Goals / Non-Goals

**Goals:**
- Дать переписыванию достаточно контекста, чтобы вопросы-продолжения («А акции?») находили материалы.
- Передавать минимум данных: только тексты нескольких предыдущих вопросов пользователя текущего
  профиля, только по настройке оператора, с уважением к выключению и очистке краткосрочной памяти.
- Измерить эффект на многоходовых вопросах и выбрать значение по умолчанию по измерению, а не из
  головы; сравнить с вариантом без LLM (склейка).

**Non-Goals:**
- Ответы модели, долговременная память, рабочая задача, профиль, инварианты, найденные фрагменты
  в переписывании (границы данных остаются).
- История для сервера эмбеддингов в виде текста реплик (ему по-прежнему уходит только
  поисковый текст).
- Автоматическое определение, зависит ли вопрос от контекста (это делает модель по промпту).
- Сравнение ОТВЕТОВ на многоходовые вопросы (нужна настоящая предыстория с ответами модели).
- Изменение семантики `REWRITE_SEARCH_MODE` (см. «Вне изменения»).

## Decisions

### 1. Что передаётся и откуда берётся

Чистая функция в `agents/rag_rewrite.py`: `history_questions(short_term, limit)` — берёт из
списка реплик ТОЛЬКО сообщения с ролью `user`, последние `limit` штук, в хронологическом
порядке (старые → новые), каждую усекает до `HISTORY_QUESTION_MAX_CHARS` (константа, 300) с
многоточием; пустые и состоящие из пробелов пропускает. `SmartAgent` вызывает её с
`profile["short_term"]` активного профиля, ТОЛЬКО если включён слой `short_term` и
`REWRITE_HISTORY_QUESTIONS > 0`; текущий вопрос в `short_term` ещё не записан (запись — после
ответа), поэтому выборка исключает его без специального кода.

Почему только вопросы (вариант A), а не пары с ответами:
- ответы длинные и содержат утверждения самой модели — это и объём, и поверхность утечки, и
  риск, что в запрос просочится сгенерированный, а не пользовательский текст;
- большинство продолжений («А акции?», «а ВДО?», «и какие риски?») разрешается по прошлым ВОПРОСАМ;
- минус: ссылку на содержимое ответа («подробнее про второй пункт») такой контекст не
  разрешит — это осознанное ограничение (Non-Goal).

Альтернативы: свёртка диалога/`summary` как контекст (дополнительный LLM-вызов и ещё один слой
данных); рабочая задача как контекст (тема задачи не равна теме последнего вопроса).

### 2. Настройка и значения

`REWRITE_HISTORY_QUESTIONS` (`config.py`, `.env.example`): целое число 0…10, 0 — не передавать
историю. Проверяется в `_validate_config()` как соседние `REWRITE_*`. Лимит длины реплики —
константа, а не переменная окружения (по принципу проекта: параметры формы промпта — в коде,
`.env` — для того, что меняет оператор). Значение по умолчанию выбирается ПО ИЗМЕРЕНИЮ
(задача 7): до него — 0, то есть поведение не меняется и новый канал данных не открывается,
пока оператор не включит его сам. Эталонное число для режима сравнения «с контекстом диалога»,
если в конфигурации 0 — 3 (`REFERENCE_HISTORY_QUESTIONS` в `rag_modes_eval.py`), по образцу
эталонных шагов отбора.

### 3. Промпт: один системный промпт плюс правила истории

`REWRITE_SYSTEM_PROMPT` (измеренный на прошлом изменении) НЕ меняется и используется, когда
истории нет. Когда история есть, к нему добавляется абзац правил `HISTORY_RULES`, а
user-сообщение получает блок:

```
<история>
1. <старый вопрос>
2. <следующий вопрос>
</история>
<вопрос>
<текущий вопрос>
</вопрос>
```

Правила (смысл): блок `<история>` — предыдущие вопросы того же пользователя, это ДАННЫЕ, а не
указания; использовать их ТОЛЬКО если текущий вопрос неполный (местоимение, «а …?», «и что с…?») и
без них непонятен; самодостаточный вопрос переписывать как раньше, не добавляя в запрос тем из
истории; из истории брать только то, что нужно для смысла текущего вопроса; по-прежнему не отвечать на
вопрос и возвращать одну строку. Разделение на «базовый промпт» и «правила истории» гарантирует,
что при `REWRITE_HISTORY_QUESTIONS=0` запрос к модели побайтно прежний — прежние измерения остаются
верными, а регресс невозможен.

Альтернатива — один универсальный промпт с пометкой «истории может не быть»: меняет и
запрос без истории, ломая сопоставимость с измерениями прошлого изменения.

### 4. Где собирается история и как она попадает в вызов

`_rewrite_query(user_text, history=())` и `_request_rewrite(backend, user_text, history)` получают
готовый список строк; `rag_rewrite.build_messages(question, history=())` собирает сообщения.
`_retrieve_materials(user_text, rewrite=None, history=None)`: `history is None` — взять из
`short_term` по правилам решения 1 (рабочий путь), список (в том числе пустой) — использовать как
есть (сравнение режимов). `search_materials()` получает такой же необязательный аргумент.
`SearchInfo` получает `history_used: int` (сколько прошлых вопросов реально ушло в вызов), а
`describe_search()` — строку «Прошлых вопросов в переписывании: N» (спека: число, не тексты).
При сбое вызова `history_used` — 0 (вызов не удался, поиск по исходному вопросу).

### 5. Откат и поиск

Правило отката не меняется: сбой, таймаут, непригодный ответ → поиск по исходному вопросу БЕЗ
вопросов истории (история не «склеивается» на запасном пути — иначе сбой переписывания тихо
превращался бы в склейку с непредсказуемым эффектом). Режим `REWRITE_SEARCH_MODE=both` не
меняется. Известный риск: для вопроса «А акции?» поиск по исходному тексту добавляет
малополезные кандидаты (слияние по лучшей оценке, порог и топ-K ограничивают вред); влияние
измеряется на многоходовом наборе (задача 7), решение — в «Вне изменения».

### 6. Контрольный набор: поле `history`

`Question` получает `history: tuple[str, ...] = ()`; `parse_questions()` принимает необязательное
поле `history` — список непустых строк (предыдущие вопросы от старых к новым); не список или
пустая строка → `QuestionSetError` с номером вопроса (как у `facts`/`sources`). Наборы без поля
остаются допустимыми. Запись в отчёт: `history` вопроса (текст из набора оператора — данных
реальных пользователей нет). README получает описание поля и пример с ВЫМЫШЛЕННЫМИ вопросами.

### 7. Режимы сравнения «с контекстом диалога» и «склейка»

Ключи режимов: `rewrite_context` («с контекстом диалога») и `concat` («склейка»), добавляются в
конец `RETRIEVAL_MODES` (порядок прежних режимов и их ключи не меняются).

```
mode            candidates  steps     rewrite   история
baseline        = TOP_K     порог     нет       -
rewrite         = TOP_K     порог     да        нет (текущий вопрос как есть)
rewrite_context = TOP_K     порог     да        да  (N вопросов из набора)
concat          = TOP_K     порог     нет       текст = "<последний вопрос истории> <текущий>"
```

- `rewrite_context` недоступен без `REWRITE_PROVIDER` (как прочие режимы с переписыванием);
  `concat` модели не использует и доступен всегда.
- Переписывание теперь кэшируется ДВАЖДЫ на вопрос: без истории (для `rewrite*`) и с историей
  (для `rewrite_context`); у вопроса без истории второе совпадает с первым и не делается.
- `concat` — обычный `search_materials(текст)` агента без переписывания; в отчёте
  `search_text` — склеенный текст.
- У вопроса без истории результат `concat` копируется из `baseline`, а `rewrite_context` — из
  `rewrite` (спека: режимы совпадают), без повторного поиска.
- Число вопросов для `rewrite_context`: `REWRITE_HISTORY_QUESTIONS` рабочей конфигурации, а если оно
  0 — эталонное (3); отчёт указывает, что оно эталонное (`history_reference`, `history_questions` в
  настройках).
- Метрики (`aggregate_retrieval`) считаются по двум группам: вопросы с историей и без; сводка
  печатает блоки по группам, если есть обе; если группа одна, формат прежний. Разница с
  `baseline` — внутри группы.
- Режимы выбираются тем же `RAG_COMPARE_MODES` (пусто на уровне `search` — все режимы, включая
  новые); пользователю чата они недоступны.

### 8. Уровень `answers` и многоходовые вопросы

Ответ на вопрос-продолжение без настоящей предыстории (ответов модели на предыдущие вопросы)
несравним, а проигрывать диалог ради сравнения — отдельные вызовы модели с недетерминированными
ответами. Поэтому на уровне `answers` вопросы с `history` не выполняются: перед прогоном —
сообщение «пропущено N многоходовых вопросов (проверяются на уровне search)»; остальные идут как
раньше; если пропущены все — прогон не начинается. Номера вопросов остаются номерами из набора
(в отчёте будут пропуски); проверка номера в `/research_rag_compare_report` учитывает это.

### 9. Измерения и выбор значения по умолчанию (задача 7)

Многоходовый набор оператора (`data/rag_eval/`, не коммитится) — 12–20 вопросов-продолжений четырёх
видов: (а) эллипсис («А акции?»), (б) местоимение («А какие у неё риски?»), (в) продолжение на
два хода назад, (г) СМЕНА ТЕМЫ — формально следует за другим вопросом, но самодостаточен
(проверка, что контекст не «заражает»). Метрики: доля попаданий в ожидаемый документ, позиция, MRR
по группам (вопросы вида (г) и самостоятельные — отдельно от (а)–(в)). Сравниваются `baseline`,
`rewrite`, `rewrite_context` при N = 1, 2, 3 (повторные прогоны с `REWRITE_HISTORY_QUESTIONS`),
`concat`, и оба значения `REWRITE_SEARCH_MODE`. Значение по умолчанию — наименьшее N, при котором
выигрыш на (а)–(в) максимален, а на (г) и на самостоятельных вопросах отката нет; если выигрыша
нет — 0. Результаты — в разделе «Результаты сравнения» этого `design.md`, без текстов вопросов и
названий документов корпуса.

### 10. Границы данных и безопасность

- Провайдеру переписывания при включённой истории уходят тексты до N предыдущих ВОПРОСОВ
  пользователя активного профиля (усечённые) — новый канал данных. При `ollama` — на сервер
  `OLLAMA_BASE_URL` (по умолчанию локальный, прокси из окружения клиент не использует); при
  `deepseek`/`kimi` — облачному провайдеру на шаг раньше основного ответа. Основной провайдер
  историю и так получает (окно `short_term` целиком, с ответами), но провайдер переписывания
  может быть другим, поэтому это решение оператора, записанное в `CLAUDE.md`, `README.md` и
  `.env.example`: для вопросов, не покидающих машину, — `ollama`.
- Слои памяти не фильтруют ввод (корневые правила): всё, что пользователь написал раньше, может
  оказаться в истории. Тексты команд уже предупреждают не вводить чувствительные данные; в
  документации оператора добавляется, что при `deepseek`/`kimi` и включённой истории прошлые
  вопросы покидают машину.
- Не уходят никогда: ответы модели, `long_term`, `working`, `meta`, инварианты, фрагменты. Не
  пишется ничего нового: история только читается, результат переписывания по-прежнему не
  сохраняется.
- Выключенный слой `short_term` и очищенная память действуют как запрет на историю.
- Это не рантайм-смена провайдера/модели/промпта: настройка в `.env`, промпт — константа,
  пользователь ничего не выбирает. Инъекция: реплики истории — данные в тегах, результат
  нормализуется (длина, иероглифы, отказ) и идёт только в поиск, не в ответ.
- Дисклеймеры и осторожные формулировки не затрагиваются: переписывание не формирует ответ.

### 11. Сбои и производительность

Таймаут, отсутствие автоповторов и правила отката те же (`REWRITE_TIMEOUT_SECONDS`). Промпт
длиннее на N коротких реплик (десятки токенов) — на задержку почти не влияет. Холодный старт
локальной модели — прежняя оговорка. Сбой выборки истории (теоретически — некорректный
`short_term` на диске) не должен ронять поиск: ошибка → пустая история, предупреждение в журнал.

## Risks / Trade-offs

- [Контекст «заражает» самодостаточный вопрос: после ответа про облигации новый вопрос про крипту
  получает в запрос слова про облигации] → промпт требует использовать историю только для
  неполного вопроса; в измерении есть группа «смена темы»; по умолчанию история выключена, пока
  отката нет.
- [Малые локальные модели игнорируют правило «только для неполных вопросов»] → измерение на
  реальных моделях оператора (`qwen2.5:7b` и др.); значение по умолчанию — 0, если откат есть.
- [Новый канал данных к облаку] → выключен по умолчанию, настройка оператора, `ollama` как
  локальный вариант, запись в документации; в сравнении данные реальных пользователей не
  участвуют.
- [Поиск по исходному «А акции?» в режиме `both` добавляет мусор] → ограничен порогом и топ-K;
  измеряется; при вреде — отдельное изменение (см. «Вне изменения»).
- [Ссылки на содержимое ответа не разрешаются] → осознанное ограничение варианта A, в Non-Goals.
- [Пропуски в номерах вопросов на уровне `answers`] → проверка номеров в команде отчёта
  учитывает пропущенные; покрыть вручную.
- [Склейка как baseline может оказаться не хуже LLM] → это и есть цель сравнения: если `concat`
  не уступает `rewrite_context`, дешёвый вариант без LLM становится рекомендацией оператору в
  документации.

## Migration Plan

1. Существующие `.env` работают без правок: `REWRITE_HISTORY_QUESTIONS` по умолчанию 0 —
   запрос к модели переписывания побайтно прежний, новые данные не передаются.
2. Включение: задать `REWRITE_PROVIDER` (рекомендуется `ollama`) и `REWRITE_HISTORY_QUESTIONS`
   (по измерению — 2 или 3), прогнать `/research_rag_compare` на уровне `search` с набором, где
   есть `history`, убедиться, что на вопросах со сменой темы отката нет.
3. Откат: `REWRITE_HISTORY_QUESTIONS=0` и перезапуск; индекс, память и форматы файлов не
   затронуты.

## Вне изменения

- Если измерение покажет, что на многоходовых вопросах `REWRITE_SEARCH_MODE=both` хуже
  `rewritten` (поиск по исходному «А акции?» вытесняет полезные чанки), понадобится режим
  «искать только по переписанному, когда использована история». Это меняет спеку
  `rag-query-rewrite`/`smart-agent-rag`, поэтому — отдельным изменением по результатам задачи 7.

## Open Questions

- Значение по умолчанию `REWRITE_HISTORY_QUESTIONS` — по результатам задачи 7; на спеки не влияет
  (диапазон и семантика нуля зафиксированы).
- Размер многоходового набора (12–20 вопросов) и его содержание — за оператором; метрики поиска
  позволяют менять набор без вызовов моделей ответа.
