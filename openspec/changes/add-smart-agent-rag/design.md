# Design

## Context

Мотивация и состав изменения — `proposal.md`, требования — `specs/smart-agent-rag/spec.md`.

Что уже есть в коде и определяет подход:
- `rag/index_store.search(strategy, index_dir, query_vector, top_k)` возвращает `SearchResult`
  (`chunk_id`, `source`, `title`, `author`, `date`, `chunk_index`, `text`, `score` — косинус по
  L2-нормализованным векторам). Индекс читается с диска на каждый вызов; корпус небольшой.
  `index_exists(strategy, index_dir)` — проверка наличия.
- `providers/embeddings_client.embed_texts(texts)` — синхронный вызов Ollama (bge-m3) с тремя
  повторами с паузами 2/4/6 с (нужны из-за холодного старта модели после простоя) и поверх них
  собственными повторами SDK. Клиент создан без явного `timeout`, поэтому действуют значения
  SDK по умолчанию (openai 1.109.1: `connect=5 с`, `read=600 с`, `max_retries=2`): при
  остановленной Ollama отказ наступает примерно через 12 с, а при недоступном хосте или
  «зависшем» сервере ожидание может быть в разы дольше. Расписание рассчитано на пакетную
  индексацию, а не на интерактивный ответ.
- `SmartAgent.ask()` синхронный и работает в потоке (`asyncio.to_thread`). Оба пути ответа —
  `_plain_completion` и `_run_tool_loop` — собирают контекст через
  `_build_context_messages()` и ДОБАВЛЯЮТ последнее `user`-сообщение уже после
  сохранения `_last_context_messages` (поэтому содержимое `user`-сообщения в
  `/smart_agent_show` сейчас не попадает).
- `enabled_layers` — общий на чат словарь с дефолтами «все `True`», накладываемыми
  сохранённым состоянием; переключение через `LAYER_ALIASES` в `smart_agent_command.py`.
  Слой `tools` — образец: статус по каждому источнику, предупреждения в `SmartAgentAnswer`,
  чистый модуль текстов и правил `agents/market_tools.py` + тесты на фейках.
- Служебные вызовы LLM идут мимо `_chat()` и получают контекст отдельно, поэтому не затронуты,
  пока RAG-блок не попадает в общий код сборки для них.

## Goals / Non-Goals

**Goals:**
- Пайплайн «вопрос → эмбеддинг → поиск → материалы + вопрос → LLM» в основном ответе
  `/smart_agent`, один поиск на вопрос, общий для обоих путей ответа.
- Слой `rag` с теми же соглашениями, что у остальных слоёв (дефолт «включён», алиас в
  `/smart_agent_toggle`, статус в `/smart_agent_show`).
- Сбой поиска и отсутствие индекса не меняют поведение ответа.
- Правила и тексты слоя — чистый модуль, покрытый тестами без Ollama и FAISS.

**Non-Goals:**
- Переписывание запроса поиска с учётом истории диалога (уточняющие реплики будут искаться
  хуже) — отдельное улучшение.
- Гибридный поиск, реранкинг, поиск по обоим индексам сразу, выбор стратегии пользователем.
- Кэш эмбеддингов и индекса между вопросами.
- RAG для `handle_message`, `/agent`, `/agent_compare`, research-режимов и служебных вызовов.
- Цитирование источников внутри текста ответа моделью: источники показывает бот строкой `📚`.
- Автоматическая перекалибровка порога: калибровка — разовая задача, повторяется вручную при
  смене модели эмбеддингов или стратегии.

## Decisions

### 1. Чистый модуль `agents/rag_context.py`, поиск внедряется

Правила и тексты — в новом модуле рядом с `invariants.py`/`market_tools.py`: фильтр по порогу,
системное сообщение с правилами, сборка последнего `user`-сообщения (фрагменты + вопрос),
строки источников для чата, описание статуса. Сам поиск (эмбеддинг + `search()`) —
функция-зависимость, которую `SmartAgent` передаёт при вызове; модуль не знает ни про Ollama,
ни про FAISS. Альтернатива — логика прямо в `SmartAgent` — отвергнута: нарушает принцип
проекта «правила и тексты отдельно от владения состоянием и вызовов LLM» и делает ветвления
непроверяемыми без моков `SmartAgent`.

### 2. Поиск — один раз в `ask()`, до ветвления на пути ответа

`ask()` вызывает `_retrieve_materials(user_text)` ДО выбора пути (`_market_tools_mode`) и
передаёт результат в оба пути. Альтернатива — поиск внутри `_build_context_messages` — давала
бы повторный поиск на каждом обращении цикла инструментов (а их до `MCP_MAX_TOOL_STEPS`).
Метод синхронный: `embed_texts` синхронный, `ask()` и так в потоке. Вызов идёт ДО запуска
процессов MCP-серверов, чтобы сбой эмбеддингов не оставлял открытых сессий.

Результат — небольшой датакласс: `chunks` (прошедшие порог), `warning` (текст для
пользователя при сбое), `status`. Без слоя/индекса — пустой результат без предупреждения.

### 3. Правила — в system, фрагменты — в последнем user-сообщении

Два сообщения, а не одно:
- **system** (порядок контекста: инварианты → профиль → инструменты → **материалы** →
  долговременная память → рабочая задача → краткосрочный диалог): короткие правила — данные,
  не инструкции; образовательный материал, не рекомендация, не гарантия; опирайся, когда
  относится к вопросу; НЕ ослабляет `SYSTEM_PROMPT`; инварианты приоритетнее. Добавляется
  только когда фрагменты есть.
- **user** (последнее): `Справочные материалы: …` (по фрагментам: документ, номер, текст),
  затем отделённый разделитель и вопрос пользователя.

Почему так: по требованию пользователя материалы объединяются с самим вопросом (ближе к концу
контекста — выше внимание модели), но правило «не ослабляет `SYSTEM_PROMPT`» надёжнее в роли
system, а текст, потенциально содержащий инъекцию, не должен получать полномочий инструкций.
Альтернативы: всё в одном system-сообщении (фрагменты далеко от вопроса, сбиваются историей)
или всё в user (правила получают вес пользовательской реплики) — отвергнуты.

В `short_term` пишется исходный `user_text` (как и сейчас), в `_last_context_messages` входит
system-сообщение правил; сам блок фрагментов сохраняется отдельно (`_last_rag_block`) для
`/smart_agent_show`, т.к. последнее `user`-сообщение в показ контекста не входит.

### 4. Конфигурация оператора

В `config.py`: `RAG_SMART_AGENT_STRATEGY` (по умолчанию `structural`; допустимы значения
стратегий индекса, проверка в `_validate_config()`), `RAG_TOP_K` (по умолчанию 3, ≥ 1),
`RAG_MIN_SCORE` (диапазон 0–1), `RAG_SEARCH_TIMEOUT_SECONDS` (по умолчанию 5, > 0; см.
решение 10). Отдельный `RAG_TOP_K`, а не переиспользование
`RAG_COMPARE_TOP_K`: первый — настройка продакшн-ответа, второй — параметр экспериментальной
команды, и менять их независимо удобнее. Индекс — существующий `RAG_INDEX_DIR`. Значение по
умолчанию `RAG_MIN_SCORE` определяется задачей калибровки (см. tasks.md) и до неё не
принимается «из головы».

### 5. Слой `rag` в `enabled_layers`

Новая константа `LAYER_RAG = "rag"` в `ALL_LAYERS`; дефолт `True` даётся существующим
механизмом `_default_enabled_layers()` + наложением сохранённого, отдельная миграция не
нужна (как у `tools`/`task_autostart`). Подпись в `LAYER_LABELS`, алиас `rag` в
`LAYER_ALIASES`, обновлённая подсказка `LAYER_TOGGLE_HINT`. Это именно СЛОЙ контекста (он
добавляет сообщения), в отличие от `task_autostart`. Слой не отдельный механизм, потому что
пользователь ждёт от `/smart_agent_toggle` одну точку управления.

Статус слоя для показа состояния, по образцу `get_tools_status()`: выключен /
индекс не построен / включён / недоступен (причина последнего сбоя в памяти объекта, на диск не
пишется). «Индекс не построен» определяется по текущему состоянию диска
(`index_exists`), а не по последнему вопросу.

### 6. Отказоустойчивость

`_retrieve_materials` ловит любое исключение поиска (ошибки OpenAI SDK эмбеддингов, `OSError`
и ошибки FAISS/SQLite на повреждённых файлах), логирует и возвращает пустой результат с
предупреждением; ответ идёт дальше без материалов. Тот же принцип, что у служебных вызовов и
недоступного источника `tools`: вспомогательная часть не роняет ответ. `KeyboardInterrupt`/
`SystemExit` не перехватываются. Следующий вопрос снова пробует поиск — состояния «отключён
до перезапуска» нет.

Отсутствие индекса (`index_exists` ложно) — не сбой: тихий пропуск без предупреждения, иначе
каждый вопрос в окружении без индекса сопровождался бы служебным шумом.

### 7. Порог применяется к каждому чанку после `search(top_k)`

`search` возвращает до `RAG_TOP_K` ближайших, затем отбрасываются чанки ниже
`RAG_MIN_SCORE`; если не осталось ни одного — блока нет вовсе. Альтернатива — порог только на
первый чанк — теряет смысл: хвост из нерелевантных чанков разбавил бы запрос.

### 8. Видимость

`SmartAgentAnswer` получает поле с использованными фрагментами (название, номер, оценка);
командный слой печатает их строкой `📚` в служебном сообщении после ответа, рядом со строками
`🔧`; предупреждение о сбое идёт в общий `warnings`. Текст чанков пользователю не выводится
(только метаданные): они уже в источнике, а вывод увеличил бы сообщения.

### 9. Границы данных

В embeddings-бэкенд уходит только текст вопроса. Канал отличается от `tools` (где наружу
уходят лишь аргументы модели), поэтому фиксируется в спеке и в CLAUDE.md. `EMBEDDINGS_BASE_URL`
по умолчанию локальный; при переводе на удалённый бэкенд вопрос пользователя покинет машину
оператора — это решение оператора, и оно должно быть видно в документации.

### 10. Бюджет времени на эмбеддинг вопроса (`RAG_SEARCH_TIMEOUT_SECONDS`, по умолчанию 5)

Одна настройка оператора — сколько максимум вопрос ждёт вектор от сервера эмбеддингов.
`embed_texts` получает необязательный параметр бюджета (по умолчанию `None` — прежнее
поведение, поэтому `rag/cli.py` и `research/chunking_compare.py` не меняются). С бюджетом
функция считает дедлайн один раз; каждая попытка идёт с таймаутом, равным остатку бюджета, и
без собственных повторов SDK (на запрос `max_retries=0`), иначе они складывались бы с нашими;
паузы существующего расписания используются только пока остаток бюджета больше паузы, после
чего ожидание прекращается и поднимается последнее исключение. `SmartAgent` передаёт бюджет
из конфигурации; исключение попадает под общий отказ из решения 6. Бюджет относится к
запросу эмбеддинга — единственному сетевому шагу; чтение индекса локальное.

Альтернативы: фиксированное короткое расписание повторов (худший случай «виснет» остаётся
~десятки секунд, а число не настраивается оператором); прерыватель цепи (пропуск поиска на N
секунд после сбоя) — оставлен на потом: добавляет состояние и меняет сценарий «следующий
вопрос снова пробует».

Цена: если холодный старт Ollama после простоя не укладывается в бюджет (502 бывает держится
дольше ~7 с), первый такой вопрос уйдёт без материалов, с предупреждением; следующий пойдёт на
уже загруженной модели. Снять причину можно на стороне Ollama (`OLLAMA_KEEP_ALIVE`, например,
`-1`) — это настройка сервера, не кода; упоминается в `.env.example`.

## Калибровка `RAG_MIN_SCORE`

Замер 2026-10-01: `python scripts/rag_calibrate.py --snippets`, стратегия `structural`, модель
эмбеддингов `bge-m3` (Ollama), `RAG_FIXED_CHUNK_*` не влияют на structural-индекс; набор —
`data/rag_eval/calibration_queries.txt` (34 запроса: A=13, B=9, C=12; файл привязан к корпусу и не
коммитится). Релевантность top-1
оценена вручную по началу текста чанка.

| Группа | n | min | median | max | Релевантность top-1 |
|---|---|---|---|---|---|
| A (по теме корпуса) | 13 | 0.524 | 0.621 | 0.739 | да — 9, частично — 4, нет — 0 |
| B (пограничные) | 9 | 0.377 | 0.575 | 0.615 | да — 1, частично — 3, нет — 5 |
| C (не по теме) | 12 | 0.409 | 0.530 | 0.674 | чистый шум — 9 (0.409–0.592); тематически близкие, но не отвечающие на вопрос про «сейчас» — 3 (оценки 0.674, 0.598, 0.584) |

Группы по score пересекаются. Число проходящих запросов при разных порогах:

| Порог | A проходят | B проходят | C проходят (из них шум) |
|---|---|---|---|
| 0.58 | 12 из 13 | 4 | 5 (2: «как дела», «анекдот») |
| **0.60** | **11 из 13** | **2** | **1 (0, тематически близкий запрос)** |
| 0.62 | 7 из 13 | 1 | 1 |
| 0.65 | 4 из 13 | 0 | 1 |

**Выбрано `RAG_MIN_SCORE = 0.60`** (правило «пропуск дешевле ложного включения»): ни один
чистый шум не проходит (максимум шума 0.592), а из A не проходят два запроса (0.585 и
0.524) — ответ на них строится без материалов, то есть как до появления слоя.

Наблюдения, которые стоит учитывать:
- Запас тонкий: шум 0.592 против A 0.600; score сам по себе слабо разделяет группы. Причина
  — в structural-индексе много совсем коротких чанков (заголовки слайдов, номера примеров,
  обрывки фраз), которые получают ~0.5–0.6 на любой короткий запрос, а не только на
  релевантный. Отдельная мера (минимальная длина чанка при поиске или пересборка индекса без
  таких чанков) — возможное улучшение `rag/`, вне этого изменения.
- Retrieval-промахи: на двух запросах top-1 — не самый подходящий документ корпуса. В одном
  случае нужный документ вообще не попал в индекс (PDF без текстового слоя, `rag.cli` пропускает
  такие файлы молча) — это не промах поиска; в другом дело в качестве чанкинга и эмбеддингов, а
  не порога.
- Повторить калибровку при смене `EMBEDDINGS_MODEL`, стратегии, параметров чанкинга или
  существенном изменении корпуса.

## Risks / Trade-offs

- **Порог не откалиброван** → отдельная первая задача: замер на трёх группах запросов
  (корпус/пограничные/не из корпуса), значение по умолчанию записывается по итогам; порог
  привязан к связке «модель эмбеддингов + стратегия + `RAG_FIXED_CHUNK_*`», пересматривается
  при их смене.
- **Structural-чанки бывают мелкими из-за ложных заголовков** (известный компромисс
  `rag-indexing`) → score на коротких чанках может вести себя иначе; ловится калибровкой,
  проверять релевантность top-1 глазами, а не только по score.
- **Задержка на каждый вопрос**: эмбеддинг + чтение индекса; при недоступной Ollama вопрос
  ждёт не дольше `RAG_SEARCH_TIMEOUT_SECONDS` (5 с по умолчанию, решение 10), но и такое
  ожидание повторяется на каждом вопросе, пока Ollama лежит → допустимо для первой версии;
  прерыватель цепи — возможное дальнейшее улучшение.
- **Холодный старт Ollama дольше бюджета** → первый вопрос после простоя без материалов, с
  предупреждением (решение 10); `OLLAMA_KEEP_ALIVE` на стороне сервера устраняет причину.
- **Рост токенов**: до `RAG_TOP_K` чанков по ~1200 символов (fixed) или размер структурного
  чанка на каждый вопрос у существующих чатов, где индекс есть → порог отсекает нерелевантные
  вопросы; `RAG_TOP_K` ограничивает верхнюю границу.
- **Уточняющие реплики** (реплики вида «а что насчёт этого?») ищутся по сырому тексту → известное
  ограничение, вынесено в Non-Goals.
- **Инъекция через текст документов** → материалы подаются как данные, правила в system,
  корпус локальный и контролируется оператором.
- **Поиск читает индекс при каждом вопросе, пока идёт пересборка `make index`** →
  пересборка атомарна по каталогу стратегии (`index_store`), поэтому чтение либо видит старый
  индекс, либо новый; редкая ошибка в момент подмены попадает под общий отказ без падения.

## Migration Plan

Миграции данных нет: ключ `rag` отсутствует в старых файлах памяти и читается как «включён».
Развёртывание — перезапуск бота; новые переменные `.env` необязательны. Откат — удалить
слой (выключить пользователем `/smart_agent_toggle rag` либо откатить коммит); сохранённые
файлы остаются совместимыми, лишний ключ `rag` в `enabled_layers` старый код игнорирует.
