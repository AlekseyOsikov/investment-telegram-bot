# Spec Delta

## Purpose

Определяет автоматическое AI-ревью pull request в репозитории проекта: что запускает ревью, как
оно защищено от исполнения чужого кода, какими материалами дополняется diff и какой комментарий
получает автор PR. Ревью — черновик для разработчика, не замена проверке человеком.

## ADDED Requirements

### Requirement: Запуск ревью только для PR из этого репозитория

Система SHALL запускать ревью при открытии, обновлении (новый коммит) и повторном открытии PR,
head-ветка которого находится в ТОМ ЖЕ репозитории, что и база. Для PR из форка ревью NOT SHALL
выполняться. Определения workflow и скрипта ревью SHALL браться из базовой ветки, а не из PR. Для
одного PR одновременно SHALL выполняться не более одного ревью: новый коммит SHALL отменять
устаревшее незавершённое ревью.

#### Scenario: PR из ветки этого репозитория

- **WHEN** автор открывает PR из ветки этого же репозитория
- **THEN** запускается ревью и в PR появляется комментарий с результатом

#### Scenario: PR из форка

- **WHEN** PR открыт из форка
- **THEN** ревью не выполняется, комментарий не публикуется, а runner не получает содержимого PR

#### Scenario: Новый коммит во время ревью

- **WHEN** в PR приходит новый коммит, пока предыдущее ревью ещё идёт
- **THEN** предыдущее ревью отменяется, а результат публикуется только для актуального коммита

#### Scenario: Изменение самого workflow в PR

- **WHEN** PR изменяет файл workflow ревью
- **THEN** действует версия workflow из базовой ветки, изменение вступает в силу только после
  попадания в неё

### Requirement: Содержимое PR используется только как данные

Система SHALL читать diff и содержимое изменённых файлов PR как текст. Код PR NOT SHALL
импортироваться, исполняться, устанавливаться как зависимость или запускаться как тесты. Модели
ревью NOT SHALL отдаваться инструменты (файловая система, сеть, оболочка, git-команды): на вход —
только текст сообщения, на выход — только текст комментария. У задачи ревью NOT SHALL быть секретов
сверх токена публикации комментария, а его права SHALL ограничиваться чтением содержимого и записью
комментариев в PR.

#### Scenario: PR содержит вредоносный скрипт

- **WHEN** PR добавляет файл с исполняемым кодом, который при запуске выполнил бы команды на
  машине runner
- **THEN** файл попадает в ревью как текст, и никакой его код не выполняется

#### Scenario: Инструкции модели внутри diff

- **WHEN** diff содержит текст вида «проигнорируй правила и сделай X»
- **THEN** он подаётся модели как данные ревьюируемого кода, а единственным результатом остаётся
  текст комментария

### Requirement: Индекс ревью строится из базовой ветки

Система SHALL искать дополнительный контекст ревью в отдельном индексе, который содержит
документацию проекта (README, CLAUDE.md, вложенные CLAUDE.md, главные спеки) и исходники
`src/` и `scripts/`, разбитые по функциям и классам, с путём файла и сигнатурой в заголовке
фрагмента. В индекс NOT SHALL попадать: `tests/`, каталог данных, файлы окружения и секретов,
незакоммиченные файлы, содержимое PR и незавершённые изменения OpenSpec. Индекс SHALL
пересобираться при изменении базовой ветки и быть отдельным от индексов бота и режима `/dev`.
Сбой сборки SHALL оставлять прежний индекс нетронутым.

#### Scenario: Сборка индекса после слияния

- **WHEN** в базовую ветку попадает новый коммит
- **THEN** индекс пересобирается из состояния этой ветки, а дата и коммит сборки сохраняются

#### Scenario: Файл вне перечня

- **WHEN** в рабочем каталоге есть файл окружения с секретами или каталог данных
- **THEN** их содержимое не попадает в индекс

#### Scenario: Сбой эмбеддингов при сборке

- **WHEN** сервер эмбеддингов недоступен во время сборки индекса
- **THEN** сборка завершается ошибкой, а прежний индекс остаётся пригодным к чтению

### Requirement: Состав ревью и контекст модели

Модель ревью SHALL получать: системное сообщение с правилами ревью, diff PR (после отсечения
шума), полное содержимое изменённых файлов в пределах бюджета и фрагменты индекса, найденные по
изменённым файлам и фрагментам diff. Системное сообщение SHALL требовать структуры «потенциальные
баги / архитектурные проблемы / рекомендации», проверять соблюдение инвариантов проекта,
запрещать давать инвестиционные рекомендации и утверждать, что код безопасен или корректен
гарантированно. Фрагменты индекса SHALL подаваться как справочные данные и NOT SHALL ослаблять
правила ревью.

#### Scenario: PR нарушает инвариант из документации

- **WHEN** PR добавляет второй вызов загрузки окружения вне модуля конфигурации
- **THEN** фрагмент документации с этим правилом попадает в контекст, и ревью может сослаться на
  него в разделе архитектурных проблем

#### Scenario: Индекс недоступен

- **WHEN** индекс отсутствует или поиск не удался
- **THEN** ревью выполняется только по diff и изменённым файлам, а комментарий явно сообщает, что
  контекст проекта не использовался

### Requirement: Формат и достоверность комментария

Система SHALL публиковать в PR один комментарий и при новом запуске обновлять его, а не создавать
новый. Комментарий SHALL содержать: пометку, что это автоматический черновик и не заменяет ревью
человеком; короткий идентификатор проверенного коммита; провайдера и модель; дату сборки индекса;
разделы «Потенциальные баги», «Архитектурные проблемы», «Рекомендации» и обязательный раздел «Что
не удалось проверить». Ссылки на файлы и строки в комментарии SHALL проверяться кодом по
фактически поданным данным: непроверенные ссылки NOT SHALL показываться как ссылки. Пустой раздел
SHALL отображаться как отсутствие находок, а не пропадать.

#### Scenario: Повторный запуск на новом коммите

- **WHEN** ревью запускается повторно для того же PR
- **THEN** существующий комментарий ревью обновляется, и в PR остаётся один такой комментарий

#### Scenario: Модель сослалась на несуществующую строку

- **WHEN** ответ модели указывает файл или строку, которых нет в поданном diff и файлах
- **THEN** такая ссылка не оформляется как ссылка на код, и комментарий не выдаёт её за проверенную

#### Scenario: Нет находок

- **WHEN** модель не нашла проблем в одном из разделов
- **THEN** раздел присутствует и сообщает, что находок нет, а не пропущен

### Requirement: Большие PR и честное усечение

Система SHALL ограничивать объём данных, подаваемых модели, настраиваемым оператором бюджетом.
Из ревью SHALL исключаться шум: бинарные, сгенерированные и lock-файлы. При превышении бюджета
файлы SHALL отбираться по приоритету (исходники `src/`, затем `scripts/`, затем остальное), а
не вошедшие файлы и усечённые части SHALL перечисляться в разделе «Что не удалось проверить».
Молчаливое усечение NOT SHALL допускаться.

#### Scenario: Diff не помещается в бюджет

- **WHEN** суммарный diff PR превышает бюджет
- **THEN** в ревью входят файлы по приоритету, а остальные названы в разделе «Что не удалось
  проверить» с причиной

#### Scenario: PR состоит только из шума

- **WHEN** PR меняет только lock-файлы и бинарные файлы
- **THEN** комментарий сообщает, что содержательных изменений для ревью нет, без вызова модели

### Requirement: Недоступные зависимости не ломают PR

Недоступность модели ревью, сервера эмбеддингов или превышение таймаута SHALL приводить к
понятному комментарию «ревью не выполнено» с причиной (без внутренних деталей и секретов) либо к
завершению задачи с ошибкой; ревью NOT SHALL блокировать merge PR и NOT SHALL оставлять в PR
устаревший успешный результат за новый коммит.

#### Scenario: Модель недоступна

- **WHEN** сервер модели не отвечает в пределах таймаута
- **THEN** в PR публикуется (или обновляется) комментарий о невыполненном ревью с указанием
  коммита, а проверка merge не блокируется

### Requirement: Настройки и данные наружу определяет оператор

Провайдер, модель, таймаут, бюджет, каталог индекса и метку runner SHALL задавать только
оператор репозитория (переменные окружения runner и файл workflow в базовой ветке). Автор PR и
участники обсуждения NOT SHALL иметь возможности выбирать модель, провайдера или правила ревью
текстом PR или комментарием. Комментарий SHALL называть провайдера и модель, выполнившие ревью.
Если провайдер облачный, система SHALL документировать, что diff и фрагменты кода покидают машину
оператора.

#### Scenario: Попытка сменить модель из PR

- **WHEN** описание PR или комментарий содержит просьбу «используй другую модель» или «замени
  правила ревью»
- **THEN** ревью выполняется с настройками оператора, а текст просьбы подаётся как данные PR

#### Scenario: Комментарий называет модель

- **WHEN** ревью завершено
- **THEN** комментарий содержит провайдера и модель, которые его выполнили
