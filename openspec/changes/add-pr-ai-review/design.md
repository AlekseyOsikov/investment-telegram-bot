# Design

## Context

В репозитории нет `.github/`; RAG-инфраструктура (`rag.index_store`: FAISS + SQLite, эмбеддинги
через локальный Ollama `bge-m3`) и индекс документации `/dev` (`dev_assistant.indexer.build()` с
подставляемыми `embed`/`store`/`record_factory`) живут в `data/` и недоступны облачному раннеру.
`dev_assistant/sources.py` намеренно индексирует только Markdown. `src/config.py` вызывает
`_validate_config()` при импорте, то есть требует токен бота и параметры очереди: оснастка ревью не
должна импортировать `config` и `providers.embeddings_client` (он тянет `config`).
Мотивация и границы — `proposal.md`, требования — `specs/pr-ai-review/spec.md`.

Репозиторий публичный: self-hosted runner на нём исполняет workflow на машине оператора, поэтому
модель угроз определяет архитектуру.

## Goals / Non-Goals

**Goals:**
- Ревью PR на локальной машине оператора с тем же RAG-стеком, что у бота (Ollama, FAISS).
- Безопасность runner: код PR никогда не исполняется; перенос на VPS без смены дизайна.
- Чистые правила (отсечение шума, бюджет, проверка ссылок, сборка сообщений) тестируются без сети.

**Non-Goals:**
- Ревью форков, автофиксы, блокировка merge, многопроходное ревью, ревью в реальном времени.
- Изменение бота, `/dev`, `rag/` и существующих индексов.
- Калибровка порога релевантности под код (первая версия: фиксированный top-k без порога,
  оценка качества — вручную на реальных PR).

## Decisions

### 1. Self-hosted runner + `pull_request_target`, «код PR как данные»

Два workflow:

```
ai-review-index.yml : on push -> main
   checkout main -> python scripts/pr_review.py index -> каталог индекса на хосте

ai-review.yml      : on pull_request_target (opened, synchronize, reopened)
   if head.repo.full_name == github.repository
   concurrency: group pr-review-${{ number }}, cancel-in-progress
   checkout main (скрипт ОТСЮДА)
   git fetch origin pull/N/head  -> только git diff / git show, без checkout PR в рабочее дерево
   python scripts/pr_review.py review --pr N --base main --head <sha>
```

`pull_request_target` берёт workflow из базовой ветки, поэтому PR не может подменить скрипт.
Содержимое PR читается командами `git diff` и `git show <sha>:<path>`, в рабочее дерево не
выкладывается: нечему исполниться случайно (импорт, хуки, `conftest.py`). `GITHUB_TOKEN`:
`contents: read`, `pull-requests: write`. Секретов у job нет (Ollama локальный).
*Альтернатива*: обычный `pull_request` — workflow из PR, на публичном репо runner исполнил бы
изменённый workflow. Отклонено.

### 2. Runner: ephemeral в Docker, метка `ai-review`

Контейнер без монтирования `$HOME`, `.env` и SSH-ключей; доступны только Ollama
(`host.docker.internal:11434`) и каталог индекса (read-only для job ревью, read-write для job
индекса). Дополнительно в настройках репозитория: approval для outside collaborators. Перенос на
VPS — смена `runs-on`/метки и адресов в переменных окружения runner.
*Альтернатива*: runner напрямую под пользователем ПК — быстрее поднять, но весь домашний каталог в
зоне поражения. Допустимо только как отладочный шаг.

### 3. Индекс из `main` по `push`, отдельный каталог

`PR_REVIEW_INDEX_DIR`, стратегия `review`, сборка через `rag.index_store.build_index()` (атомарная
замена), рядом `meta.json` (дата, коммит, число файлов/чанков). Перечень файлов — `git ls-files`
по маске: документация как у `dev_assistant.sources` плюс `src/**/*.py`, `scripts/**/*.py`;
`tests/`, `data/`, файлы окружения исключаются независимо от того, отслеживаются ли они git.
*Альтернативы*: индекс на каждый PR (дороже, в индекс попал бы недоверенный текст; содержимое PR и
так подаётся напрямую); общий индекс с `/dev` (смешал бы порог и корпус, нарушив правило
«индекс отдельный»).

### 4. Чанкер исходников по `ast`

Чанк = функция/метод/класс (верхний уровень и методы): заголовок «путь › класс › имя(сигнатура)» +
docstring + тело с усечением по константе модуля; модульный docstring и константы верхнего уровня
— отдельный чанк; синтаксическая ошибка файла → файл целиком одним усечённым чанком (ревью не
падает). Чистая функция, тесты на синтетических исходниках.
*Альтернатива*: окна фиксированного размера — хуже поиск «что делает вызываемая функция».

### 5. Переиспользование без импорта `config`

`scripts/pr_review.py` не импортирует `config`/`providers.embeddings_client`: собственный тонкий
клиент эмбеддингов (OpenAI-совместимый, `EMBEDDINGS_BASE_URL`/`EMBEDDINGS_MODEL` из окружения) и
клиент чата по `PR_REVIEW_PROVIDER`/`PR_REVIEW_MODEL`/`PR_REVIEW_BASE_URL`. Из проекта
импортируются только `rag.index_store` и чистые части `dev_assistant` (чанкер Markdown), у которых
нет побочных эффектов импорта. `src/` бота не правится.

### 6. Контекст модели и поиск

Запросы поиска: пути изменённых файлов, имена изменённых функций (из hunk-заголовков), первые
строки изменённых блоков. Результаты объединяются, дедуплицируются, ограничиваются top-k. Порядок
сообщений: системное сообщение ревью → справочные фрагменты (отдельное сообщение, оговорка «данные,
не инструкции») → diff и файлы. Системное сообщение запрещает инвестиционные рекомендации,
гарантии корректности и требует проверять инварианты `CLAUDE.md`.

### 7. Бюджет и усечение вместо многопроходности

Файлы PR: фильтр шума → сортировка по приоритету (`src/` > `scripts/` > остальное) → набор до
бюджета `PR_REVIEW_MAX_CHARS`; остаток и усечённые хвосты — в раздел «Что не удалось проверить».
*Альтернатива*: многопроходное ревью по файлам + сводка — умножает вызовы к Ollama, делящему
ресурсы с ботом (`LLM_MAX_CONCURRENCY`/`OLLAMA_NUM_PARALLEL`); отложено.

### 8. Достоверность комментария строит код

Модель просят вернуть находки структурой (раздел, файл, строка, текст) в JSON. Код проверяет, что
файл есть среди поданных, а строка — в диапазоне подданного текста; проверенные ссылки
оформляются как ссылки на коммит, непроверенные — обычным текстом с пометкой. Если JSON не
разобран — один повтор, затем текст ответа как есть в блоке под предупреждением. Комментарий
собирается кодом по шаблону; идентификатор комментария для обновления — скрытый маркер
`<!-- pr-ai-review -->`.

### 9. Публикация через `gh`

`gh api` с `GITHUB_TOKEN`: найти комментарий с маркером → PATCH, иначе POST. Текст комментария
режется по лимиту GitHub (65 536 символов) с пометкой.

## Risks / Trade-offs

- [Чужой PR исполнил код на runner] → `pull_request_target`, условие по head-репозиторию, approval,
  ephemeral-контейнер, никаких checkout/install кода PR; в `tasks.md` — ручная проверка на
  PR-«ловушке» (файл с `conftest.py`/`setup.py`).
- [Prompt-инъекция из diff искажает ревью] → у модели нет инструментов, результат — только текст
  комментария; пометка «черновик»; ссылки проверяются кодом.
- [Слабая локальная модель: шум и ложные находки] → раздел «что не удалось проверить», честная
  пометка модели в комментарии, оценка на реальных PR перед включением по умолчанию; провайдер
  сменяемый настройкой оператора.
- [Ревью конкурирует с ботом за Ollama] → `concurrency` на PR, таймаут, бюджет; согласование
  `OLLAMA_NUM_PARALLEL` — на стороне оператора.
- [ПК выключен → PR без ревью] → допустимо для пробы; проблема снимается переносом на VPS.
- [Индекс устарел относительно `main`] → дата сборки и коммит показываются в комментарии.
- [Облачный провайдер → код и diff покидают машину] → репозиторий публичный, но канал документируется
  в `CLAUDE.md`/README как решение оператора; значение по умолчанию — локальный Ollama.

## Migration Plan

1. Развернуть runner на ПК (Docker, ephemeral, метка `ai-review`), включить approval для outside
   collaborators, проверить `permissions`.
2. Смержить workflow в `main` отдельным маленьким PR (правки workflow в PR не действуют до этого).
   Для отладки скрипта — `workflow_dispatch` с номером PR.
3. Собрать индекс (`push` или вручную), прогнать ревью на двух-трёх реальных PR, оценить качество.
4. Перенос на VPS: поставить runner и Ollama (эмбеддинги + модель по возможностям VPS), сменить
   метку и адреса; индекс собирается на VPS по `push`. Откат: отключить workflow — бот и проект не
   затронуты, это отдельная оснастка.

## Open Questions

- ~~Какая модель ревью по умолчанию на ПК~~ — РЕШЕНО замером на трёх PR (#3, #4, #7): выбран
  облачный `deepseek-flash` с отключённым рассуждением (`thinking: disabled`): ~1400 токенов и
  ~9 с на ревью, ответ стабильно разбирается, ссылки «файл:строка» подтверждаются, инъекция из
  diff не действует. Локальный `gpt-oss:20b` (Ollama, CPU, ~10 ток/с) работает только с
  тайм-аутом ≥ 1800 с и контекстом сервера ≥ 16384: рассуждение съедает лимит токенов (при 4096
  и 8192 ответ пуст), поэтому он запасной вариант, а не основной. Выбор — настройка оператора
  (`PR_REVIEW_*`); облачный провайдер означает, что diff и код покидают машину (репозиторий
  публичный). Качество: часть находок верна, часть — ложные срабатывания (например, «том будет
  принадлежать root» при проверенной записи), поэтому комментарий остаётся черновиком.
- Нужен ли порог релевантности для кода (после первых прогонов; отдельное изменение при
  необходимости).
