# Design

## Context

Мотивация и объём: `proposal.md`, требования: `specs/price-watch/spec.md` и дельты `specs/smart-agent-market-tools/spec.md`, `specs/mcp-integration/spec.md`.

Серверная часть реализована в репозитории `mcp-moex` (изменение `add-price-watch-scheduler`), контракт ниже сверен с её кодом (`models.py`, `server.py`), а не только с её `design.md`.

Что важно в текущем устройстве бота:

- Бот — один долгоживущий процесс (`run_polling`), обновления обрабатываются последовательно (`concurrent_updates` не включён). Он же единственный, кто может писать в Telegram.
- Сервер `mcp-moex` запускается подпроцессом по stdio (`uv run --directory <MCP_MOEX_DIR> mcp-moex`) и не живёт между обращениями: `mcp_integration/market_session.py` держит процесс на один вопрос smart-агента, `mcp_integration/client.py` на один вызов `/mcp_tools`. Планировщик внутри сервера невозможен, часы у бота.
- Слой `tools` smart-агента отдаёт модели инструменты с пометкой `read_only_hint` (`market_session.is_read_only`). Инструменты расписания сервера помечены не read-only, а без флага `--watch-db` сервер их не публикует, но это единственная защита, пока список не задан явно.
- Обработчики команд — фабрики `build_*_handler()` в модулях предметных пакетов, регистрация и `/help` в `main.py`, флаги окружения в `config.py` (`RESEARCH` как образец булева флага с проверкой в `_validate_config()`).
- В `requirements.txt` нет `python-telegram-bot[job-queue]`, APScheduler не установлен.
- Тесты покрывают только чистые функции (без сети, Telegram и моков `SmartAgent`), см. `tests/conftest.py`.

## Goals / Non-Goals

**Goals:**
- Часы, доставка и команды в боте без новых зависимостей и без нового долгоживущего процесса.
- Сбой любой части (сервер, сеть, Telegram, перезапуск) не теряет сводку молча и не роняет бота.
- Логика планировщика проверяется тестами на простых фейках, как `run_tool_loop`.
- Модель физически не получает инструментов расписания.

**Non-Goals:**
- Управление расписанием естественным языком через модель (обсуждалось и отложено; потребует перехвата вызовов и подтверждения пользователем).
- Пороговые уведомления, фильтр торговых часов, LLM-комментарий к сводке, свой часовой пояс пользователя.
- Ограничение общего числа чатов с опросом (см. «Открытые вопросы»).
- Долгоживущее соединение с сервером или HTTP-режим сервера.

## Decisions

### 1. Планировщик на `asyncio`, без JobQueue

Сервер называет ближайший срок (`next_due_at`); нужен один таймер, который можно перевести на более раннее время. Это ~60 строк на `asyncio` (`asyncio.Event` для «проснись раньше» и ожидание с таймаутом), запускаются в `post_init` приложения и отменяются в `post_shutdown`.

Альтернатива: `application.job_queue.run_once` из PTB. Идиоматичнее, но требует extra `job-queue` (APScheduler), а перестройка срока превращается в удаление и пересоздание задания. Тестировать такую связку на простых фейках сложнее. Отвергнута ради отсутствия новой зависимости и проверяемости.

```
   post_init --> WatchScheduler.run() [asyncio.Task]
        ^                |
        |                v
   schedule_at(t)   wait(min(t - now, 1 ч)) или событие "проснись"
   (из /watch)           |
                         v
                       tick():  run_due -> отправка -> ack
                         |
                         +--> следующий t = next_due_at | пауза повтора | None(только контрольная сверка)
```

### 2. Логика тика отделена от цикла

Функция `run_tick(...)` принимает внедряемые `call_tool` (вызов инструмента сервера), `send` (отправка в чат) и возвращает итог (что делать дальше: время следующего срока, нужна ли немедленная повторная итерация, была ли ошибка). Цикл (`WatchScheduler`) только ждёт и вызывает её. Так всё ветвление (has_more, сбой отправки, «чат недоступен», сбой сервера) проверяется тестами без сна и без Telegram, по образцу `market_tools.run_tool_loop`.

Тик:
1. `watch_run_due` (отдельная сессия сервера, закрывается сразу).
2. Для каждой сводки по порядку: отправить в чат (текст сервера, разбитый по `TELEGRAM_MESSAGE_LIMIT`). Успех: id в список подтверждаемых. `Forbidden` / «chat not found»: запомнить чат для остановки. Иное (сеть, `RetryAfter`, `TimedOut`, прочее): оставить неподтверждённой, отметить «нужен повтор».
3. Для чатов из п. 2 «недоступен» вызвать `watch_stop`.
4. Если есть успешно отправленные, `watch_ack(ids)`.
5. Следующий шаг: `has_more` → сразу ещё тик; нужен повтор → пауза 60 с; иначе `next_due_at` из ответа.

Сбой тика целиком (сервер не запустился, тайм-аут, ошибка протокола): журнал, пауза повтора с ростом 60 → 120 → 240 → ... не более 900 с; успех сбрасывает паузу. Пользователям о фоновых сбоях не пишем.

### 3. Гарантии доставки: не менее одного раза

Порядок «отправить, затем подтвердить» даёт: сбой отправки, сбой `watch_ack` или остановка бота между ними приводят к повторной отправке той же сводки при следующем тике, но не к потере. Побочное следствие (дубль сводки) принимается сознательно. Если сводка из нескольких кусков и отправлен только первый, повтор отправит все: дубль первого куска допустим.

### 4. Расписание после команд без лишних обращений

`/watch` возвращает `next_poll_at` и `next_report_at`: планировщику передаётся `schedule_at(min(их))`, метод переводит срок только на более ранний момент (более поздний не нужен: ближайшее выполнение всё равно наступит раньше) и будит цикл. `/watch_stop` расписание не трогает: лишний тик найдёт, что делать нечего, и получит свежий `next_due_at` (потраченное обращение к серверу дешевле, чем хранить в боте копию расписания).

Контрольная сверка: даже без срока (или со сроком далеко) цикл просыпается не реже раза в час (`RECHECK_SECONDS`), вызывает `run_due` и выравнивает срок по ответу. Это страхует от прыжков системных часов и рассинхрона, стоит ≈1 запуску сервера в час.

### 5. Запуск сервера: один процесс на обращение, отдельно от модели

`mcp_integration/watch_session.py` (только механика MCP, как `market_session.py`): функция вызова одного инструмента открывает `stdio_client` на `uv run --directory <MCP_MOEX_DIR> mcp-moex --watch-db <абсолютный путь>`, делает `initialize()`, `call_tool()`, закрывает всё. Тайм-аут `PRICE_WATCH_TIMEOUT_SECONDS` (по умолчанию 90) охватывает весь цикл. Команда собирается списком аргументов, без shell.

- Путь к файлу хранилища передаётся АБСОЛЮТНЫМ (`os.path.abspath` при загрузке конфигурации): `uv run --directory` меняет рабочий каталог процесса, и относительный путь (`data/...` по умолчанию) указал бы внутрь каталога `mcp-moex`, а не бота.
- Результат: словарь из `structured_content`. `is_error` превращается в `WatchToolError(текст сервера)`; текст уже написан для чтения и показывается пользователю как есть.
- `anyio` может завернуть исключение из тела контекстов в `ExceptionGroup` и обойти перехват по классам; вызов разворачивает группу с одним исключением и поднимает исходное (та же причина, что в `SmartAgent._tool_completion_async`).
- Две сессии на тик (`run_due`, потом `ack`), а не одна: сессия не должна висеть открытой, пока бот отправляет сообщения в Telegram. Цена ≈0,75 с на запуск, тик редкий.

Альтернатива: один долгоживущий процесс сервера по HTTP. Отвергнута: второй режим клиента, супервизор и состояние соединения ради экономии секунды раз в несколько минут; `mcp-integration` прямо требует не удерживать процесс между обращениями.

### 6. Защита модели: список разрешённых инструментов

В `market_session.py` добавляется явный перечень (`search_securities`, `get_current_price`, `get_price_history`), и `MarketTools` отдаёт модели инструмент, только если он в нём И помечен read-only. Основная защита остаётся на сервере (сессия smart-агента запускается без `--watch-db`, и инструментов расписания в ней нет), перечень второй рубеж на случай изменения конфигурации или появления новых read-only инструментов, с предупреждением в журнале о пропущенных. Новый инструмент сервера для модели теперь требует явного добавления в перечень: это желаемое трение.

### 7. Команды и разбор

Пакет `src/price_watch/`:

```
parse.py      чистый разбор: аргументы -> (тикеры, poll, report) | ошибка формы
texts.py      чистые тексты: ответ /watch, /watch_status, подсказка, времена по МСК
scheduler.py  run_tick() и WatchScheduler (цикл, schedule_at)
commands.py   CommandHandler-ы (/watch, /watch_status, /watch_report, /watch_stop), build_*
```

Разбор `/watch`: слова после команды (запятые как разделители), два последних слова должны соответствовать `^\d+[mhdмчд]$` (без учёта регистра), русские единицы переводятся в латинские, остальное тикеры. Бот проверяет только форму: диапазоны, число тикеров и существование бумаги проверяет сервер, и его отказ передаётся пользователю как есть, так правила остаются в одном месте.

Обработчики: `CommandHandler(..., filters=filters.ChatType.PRIVATE)`. Планировщик хранится в `application.bot_data`, доступен обработчикам через `context.application`, глобального состояния нет. Ошибки переводятся в русские сообщения отдельными `except` по образцу `mcp_integration/tools_command.py` (`FileNotFoundError`, `TimeoutError`, `WatchToolError`, последний рубеж с `logger.exception`).

Времена в ответах берутся из ISO-строк сервера (`+03:00`) и форматируются как `ДД.ММ ЧЧ:ММ (МСК)` без пересчёта в пояс пользователя (Telegram его не сообщает).

### 8. Конфигурация и включение

`config.py`: `PRICE_WATCH` (булев флаг по образцу `RESEARCH`, по умолчанию включён, проверка в `_validate_config()`), `PRICE_WATCH_DB` (по умолчанию `data/price_watch/watch.sqlite3`, приводится к абсолютному пути), `PRICE_WATCH_TIMEOUT_SECONDS` (по умолчанию 90, должно быть положительным), производная `PRICE_WATCH_ACTIVE = PRICE_WATCH and bool(MCP_MOEX_DIR)`. Регистрация в `main.py` и упоминание в `/help` идут по `PRICE_WATCH_ACTIVE`, как исследовательские команды по `RESEARCH_ENABLED`. Отдельный флаг нужен, чтобы оператор мог оставить smart-агенту данные биржи, но не включать бота, пишущего сам.

`main()` собирает приложение с `post_init`/`post_shutdown` только при активной возможности. В `post_init` создаётся задача планировщика; в `post_shutdown` она отменяется и дожидается (отмена посреди тика допустима: выход из `async with` завершает процесс сервера, недоставленное останется неподтверждённым).

### 9. Контракт с сервером (что бот вызывает)

| Вызов | Когда | Что используется из результата |
|---|---|---|
| `watch_set(chat_id, secids, poll_interval, report_interval)` | `/watch` | `secids`, интервалы, `replaced`, `next_poll_at`, `next_report_at`, `first_samples` |
| `watch_status(chat_id)` | `/watch_status` | `active`, тикеры, интервалы, `next_*`, `samples_in_period`, `pending_reports` |
| `watch_get_report(chat_id)` | `/watch_report` | `text` |
| `watch_stop(chat_id)` | `/watch_stop`, чат недоступен | `stopped` |
| `watch_run_due()` | тик | `reports[]` (`report_id`, `chat_id`, `text`), `next_due_at`, `has_more` |
| `watch_ack(report_ids)` | после отправки | ничего (число отмеченных только в журнал) |

`chat_id` всегда берётся из `update.effective_chat.id`, а не из аргументов команды. Бот отправляет `text` сводки без правок, поэтому оговорки сервера (задержка котировок, «не рекомендация») сохраняются.

## Risks / Trade-offs

- [Бот пишет сам, без вопроса: это первый такой случай] → включается только явной командой, `/watch_stop` отключает, `/start` и `/help` говорят об этом прямо, при блокировке бота опрос останавливается; в `CLAUDE.md` фиксируется как осознанное исключение, наравне с историей `/agent`.
- [Дубль сводки при сбое между отправкой и подтверждением] → выбрано «не менее одного раза» вместо потери; редкий побочный эффект.
- [Любой пользователь Telegram может заводить опросы: нагрузка на ISS и диск растёт с числом чатов] → границы на чат (10 тикеров, период от 5 минут) держит сервер; общего лимита чатов нет (у бота нет и списка допущенных пользователей), см. «Открытые вопросы».
- [Слишком длинный `watch_run_due` превысит тайм-аут 90 с при многих чатах] → сервер ограничивает параллелизм и кэширует, тайм-аут настраивается; при срабатывании тик повторяется с паузой, а сводки не теряются.
- [Относительный путь хранилища уехал бы в каталог `mcp-moex`] → путь делается абсолютным при загрузке конфигурации, тест на собранную команду.
- [Сервер старой версии не знает `--watch-db`] → процесс завершается с ошибкой аргументов, пользователь видит «не удалось соединиться с сервером», в журнале причина; оператору нужно обновить `mcp-moex`. Отдельной проверки версии нет.
- [Перечень разрешённых инструментов отсекает новые read-only инструменты сервера] → намеренно; предупреждение в журнале называет пропущенные.
- [Задержка первой сводки после перезапуска на время старта `uv` (≈1 с)] → несущественно.
- [`chat_id` пользователя лежит в файле хранилища] → каталог `data/` в `.gitignore`; данных из диалогов там нет; `/watch_stop` удаляет данные чата.

## Migration Plan

Оператор обновляет `mcp-moex` до версии с `--watch-db`, при необходимости задаёт `PRICE_WATCH_DB`, перезапускает бота. Существующие чаты ничего не замечают: без команды `/watch` данных и сообщений нет. Откат: `PRICE_WATCH=false` и перезапуск (команды пропадают, планировщик не стартует); файл хранилища можно оставить или удалить.

## Open Questions

- Нужен ли общий лимит числа чатов с опросом? Для него серверу понадобится инструмент подсчёта, поэтому решение относится к серверу и может быть принято позже, без изменения команд бота.
