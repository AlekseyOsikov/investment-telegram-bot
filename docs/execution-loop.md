# Execution loop: автономное выполнение пула задач (День 5)

Отчёт по заданию «Execution Loop»: пул задач, автономный цикл «взять задачу → выполнить →
закоммитить → следующая», метрики двух прогонов на облачной модели `sonnet` и итог по локальной
модели. Это оснастка разработки: бот (`src/`) её не использует и от неё не зависит.

Все числа — из логов `docs/execution-loop/log-*.md` (каждый прогон выполнялся **один раз**):
это ориентиры, а не статистика. Что не проверялось, указано в разделе «Что не проверено».

## 1. Что сделано

| Часть | Где |
|---|---|
| Пул из 18 задач (баги, тесты, мини-фичи, рефакторинг, документация) | `tasks/backlog.md`, T01–T18 |
| Усложнённый пул из 8 задач | `tasks/backlog.md`, T19–T26 |
| Критерий «сделано» для каждой задачи (скрипт, код выхода 0 = сделано) | `tasks/check.sh <ID>` |
| Runner: отдельный `claude -p` на задачу, приёмка, откат, вторая попытка, лог, метрики | `scripts/exec_loop.py` |
| Чистые правила runner (разбор пула, промпт, классификация сбоя, метрики) | `scripts/exec_loop_lib.py`, тесты `tests/test_exec_loop_lib.py` (14) |
| Логи прогонов | `docs/execution-loop/log-run1.md`, `log-run2-initial.md`, `log-run2-rerun-T22.md` |

Ветки и теги: `exec-loop-baseline` / `exec-loop-pool` — старт первого пула, `exec-loop-pool2` —
старт второго; результаты — ветки `exec-loop-run1` (T01–T18) и `exec-loop-run2` (T19–T26).

### Как устроен цикл
- На каждую задачу — свежая сессия ассистента с одним и тем же шаблоном промпта; профиль
  (`bug-fix`, `test-writer`, `doc-sync`, `research` из `.claude/agents/`) ассистент выбирает сам,
  человек между задачами ничего не подсказывает.
- Приёмку запускает runner сам (`tasks/check.sh`), не доверяя ответу ассистента. Не прошла —
  изменения откатываются, вторая попытка видит **только вывод приёмки**.
- Баги заранее подсажены в код (воспроизводимо, из тега). Основной пул: 5 багов — 3 с красным
  тестом (T01–T03) и 2 «тихих» (T04, T05: покрывающий assert удалён, нужен регрессионный тест).
  Усложнённый: 2 бага — «тихий» T19 и T20 с красным тестом в другом слое. Для каждой задачи проверено, что приёмка на
  базе красная, а на эталонном решении зелёная.
- Права ассистента заданы флагами runner (`--allowedTools`/`--disallowedTools`): без `git push`,
  без чтения `.env` и `tasks/check.sh`.

### Прогон 2: усложнённый пул (T19–T26)

Первый запуск (`log-run2-initial.md`):

| Метрика | Значение |
|---|---|
| Выполнено задач | 7 из 8 |
| **Подряд без паузы** | **3** (T19–T21) |
| Первый провал | T22; в логе помечен «нерабочий код» |
| С первого раза | 7 из 8 (88 %) |
| Среднее время на задачу | 63 с (от 32 с до 1 мин 17 с) |
| Ходов | 143 суммарно (3–53 на задачу) |
| Стоимость по данным ассистента | $3,10 |

**Причина провала T22 — ошибка оснастки, а не модели.** В `DENIED_TOOLS` runner был шаблон
`Read(./.env.*)`, он закрыл и `.env.example`, который T22 требовала обновить. Ассистент не смог
его открыть, отказался обходить запрет и честно написал, что нужно сделать вручную. Эвристика
runner классифицировала это как «нерабочий код». Шаблон исправлен (запрещён только `.env`), T22
перезапущена на той же ветке (`log-run2-rerun-T22.md`): **выполнена с первой попытки за 62 с**,
30 ходов. После перезапуска: 8 из 8, подряд 8, полный `pytest` на `exec-loop-run2` — 2096 зелёных.

Метрика «подряд без паузы» поэтому приводится в двух вариантах: **3 по исходному запуску** и **8
после исправления оснастки**. Честным считаю первое как «как отработал цикл», второе — «на что
способна модель при исправной оснастке».

- Усложнённый пул потребовал примерно в полтора–два раза больше времени и вдвое-втрое больше
  ходов (самые тяжёлые: T21 — 28 ходов и 8 файлов, T26 — 24 хода и 5 файлов, T22 — 30 ходов и 8
  файлов), но модель не сломалась: ни одной задачи не завершилось провалом по её вине.
- Повторного прогона «после правки правил и профилей» в смысле задания **не было**: ни в одном из
  прогонов `sonnet` не упал по вине модели, поэтому править правила и профили было не по чему.
  Единственная правка — исправление оснастки (шаблон запрета), она описана выше и не относится к
  правилам для ассистента.

## 5. Локальная модель

Прогон пула на локальной модели **не выполнялся**; была только проба связности на T16.

- Связка: Claude Code → Ollama 0.21.0 в Docker через `ANTHROPIC_BASE_URL=http://localhost:11434`,
  `ANTHROPIC_AUTH_TOKEN=ollama`, `ANTHROPIC_API_KEY=` (пустая), модель `qwen3-coder:30b`. Ollama
  отвечает на `/v1/messages`, холодная загрузка 40 с.
- Результат пробы: T16 **не выполнена** — 0 вызовов инструментов, 2 токена вывода, 0 изменённых
  файлов. Причина — размер контекста: системный промпт Claude Code и описания инструментов дают
  17,4–19,8 тыс. токенов входа даже на запросе «ответь одним словом», а контекст контейнера
  `OLLAMA_CONTEXT_LENGTH=16384`. Начало промпта обрезается, модель отвечает пустотой.
- Поэтому пул на локальной модели не запускался: провал был бы про настройку контекста, а не про
  способности модели. Варианты (не выполнены): поднять контекст контейнера до 32768 (по
  `docs/local-llm.md`, на 32k префилл `qwen3-coder` падает до ~88 ток/с, то есть минуты на холодную
  сессию) либо перенести `agent_loop.py` из `780f55d5` (ветка `Adv-Day-04-report`) с коротким
  промптом.
- Сравнение «облако vs локально» в смысле «сколько задач вытянула каждая модель» в этом отчёте
  не дано; данные по способностям локальных моделей — в `docs/local-llm.md` (День 4).

Прогон на `haiku` был начат и отменён по решению владельца после четырёх задач (T01–T04 выполнены
с первой попытки); в сравнение не включён.

## 6. Выводы

1. **Autonomous loop работает на этом проекте.** Благодаря готовым правилам (`CLAUDE.md`,
   `docs/code-style.md`), профилям и проверяемым критериям `sonnet` выполнил 26 задач из 26
   (18 + 8) без вмешательства человека между ними.
2. **Качество критерия «сделано» важнее модели.** Почти все проблемы прогонов лежали в оснастке:
   в приёмках — слишком строгая проверка формулировки (T16), накопление красных тестов между
   задачами, прокси-переменные при импорте `config`; в runner — слишком широкий запрет чтения
   (T22). Каждую я нашёл только на живом или эталонном прогоне.
3. **Эвристика причины провала недостаточна.** «Нерабочий код» была поставлена там, где приёмка
   была недостижима из-за запрета. Классификацию надо проверять по `attempt*.json` и `check*.txt`,
   как и сказано в конце каждого лога.
4. **Пул оказался слишком лёгким для `sonnet`**, чтобы найти границу «сколько подряд». Следующий
   шаг — слабая модель (`haiku`) или заведомо более тяжёлые задачи (неоднозначные требования,
   большие рефакторинги); именно там имеет смысл править правила и профили и сравнивать «до» и
   «после».

## 7. Что не проверено

- Каждый прогон выполнялся один раз; разброс между запусками не оценивался.
- `check.sh` лежит в репозитории: запрет его читать держится на `--disallowedTools` и промпте,
  обход через оболочку теоретически возможен (в логах попыток не найден).
- Приёмки проверяют форму и поведение, но не качество кода и текста целиком; проверка
  «сделано» — необходимое, а не достаточное условие хорошей правки.
- Локальная модель, `haiku`, поведение на более тяжёлых задачах и стабильность результата при
  повторе — не измерялись.
- Стоимость — по данным самого ассистента (`total_cost_usd`), не сверена со счётом провайдера.

## 8. Как повторить

```bash
# основной пул
.venv/bin/python scripts/exec_loop.py --branch exec-loop-runN --model sonnet
# усложнённый пул
.venv/bin/python scripts/exec_loop.py --branch exec-loop-runM --from exec-loop-pool2 \
    --tasks T19-T26 --model sonnet
# только посмотреть промпты, ничего не запуская
.venv/bin/python scripts/exec_loop.py --dry-run --tasks T04
```

Рабочая копия должна быть чистой; запускать можно только на ветке `exec-loop-*`. Результаты —
`reports/exec_loop/<ветка>/` (не коммитится): `log.md`, `results.json`, вывод каждой попытки.
