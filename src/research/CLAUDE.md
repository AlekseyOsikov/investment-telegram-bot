# research/ — технические режимы исследования API

Корневые правила (домен, безопасность, конфигурация) — в `/CLAUDE.md`. Эти режимы не
участвуют в обычном потоке сообщений и включаются флагом `RESEARCH` (см. корневой файл).

## Модули

- `_shared.py` — общий каркас: `run_scenario`/`api_error_to_message` (перехват ошибок OpenAI SDK
  → русское сообщение), `extract_usage`/`sum_usage`/`format_scenario_stats`,
  `content_or_reasoning_fallback`, `build_cancel_handler`. Изменения обработки ошибок API или
  статистики вноси сюда, а не в три режима по отдельности; специфику режима (сценарии,
  форматирование, кнопки) оставляй в его модуле.
- `constraints.py` (`/research_constraints`), `reasoning.py` (`/research_reasoning`),
  `temperature.py` (`/research_temperature`) — идут через `main_client`/`MAIN_MODEL`. Тексты и
  ошибки параметризованы `MAIN_CLIENT_LABEL`/`MAIN_API_KEY_ENV_VAR` — не возвращай
  захардкоженное «DeepSeek».
- `models.py` (`/research_models`) — сравнение 4 моделей DeepSeek/Kimi; от `MAIN_CLIENT` не
  зависит, не использует `run_scenario`/`api_error_to_message` (сообщения провайдер-нейтральны,
  статистика шире), но использует остальное из `_shared.py`.
- `chunking_stats.py` (`/research_chunking_stats`, обычный `CommandHandler`) и
  `chunking_compare.py` (`/research_chunking_compare`, `ConversationHandler` с одним циклическим
  состоянием до `/cancel`) — только ЧИТАЮТ индекс из `rag/`; без индекса отвечают понятным
  сообщением, а не падают. Compare показывает топ-`RAG_COMPARE_TOP_K` чанков каждой стратегии
  ОТДЕЛЬНЫМ сообщением на стратегию: оценка, заголовок, метаданные, текст (отделён от метаданных
  строкой `--------`). См. `src/rag/CLAUDE.md`.
- `rag_compare.py` + `rag_compare_eval.py` — `/research_rag_compare`
  `/research_rag_compare_stop` и `/research_rag_compare_report [номер]`: сравнение ответов `/smart_agent` с выключенным и
  включённым слоем `rag` на контрольных вопросах из файла оператора (спека — `openspec/specs/rag-answer-comparison/`
  после архивации изменения `add-rag-compare-command`, до того —
  `openspec/changes/add-rag-compare-command/`). Правила и тексты — в чистом
  `rag_compare_eval.py` (тесты `tests/test_rag_compare_eval.py`), обращения к агенту/LLM/диску и
  Telegram — в `rag_compare.py`.

## `/research_rag_compare`

- **Фоновый прогон**, а не обработчик, ждущий результат: обновления PTB обрабатываются
  последовательно, и обработчик на несколько минут заблокировал бы бота для всех. Обработчик
  проверяет набор и индекс (синхронно), ставит флаг «прогон идёт», создаёт `asyncio`-задачу (ссылка
  хранится в модуле) и отвечает; одновременно ОДИН прогон на весь бот, повторный запуск получает
  прогресс. Флаг снимается в `finally`. Вопросы идут последовательно, каждый вызов агента и
  оценщика — в `asyncio.to_thread`. Прогресс — одно редактируемое сообщение, обновляемое на каждом
  ЭТАПЕ вопроса (ответ без RAG → оценка → ответ с RAG → оценка): рабочий поток зовёт `on_stage`, а
  `_ProgressReporter` планирует правку в цикле событий (`run_coroutine_threadsafe`), отбрасывает
  устаревшие правки по номеру и после итога игнорирует новые (доживающий поток остановленного
  прогона не должен перезаписать итоговый текст); ошибки редактирования прогон не прерывают.
- **Быстрый отказ.** Зависший провайдер раньше давал до 12 минут на вопрос (60 с × 3 попытки SDK × 4
  вызова). Теперь у вопроса бюджет `RAG_COMPARE_QUESTION_TIMEOUT_SECONDS` (120 с; обычный вопрос
  15–25 с), таймаут каждого обращения — `min(REQUEST_TIMEOUT_SECONDS, остаток бюджета)`, клиент —
  `main_client.with_options(max_retries=0)` (для ответа агента клиент и таймаут передаются в
  `SmartAgent` параметрами конструктора). Бюджет исчерпан — оставшиеся этапы получают причину
  «превышен лимит времени вопроса» без обращений. Цена: разовый сетевой сбой не повторяется.
  **Таймаут клиента НЕ ограничивает общее время**: это пауза между чтениями, а DeepSeek под
  нагрузкой держит соединение и шлёт пустые строки keep-alive — вопрос 1 в живом прогоне занял 595 с
  при `timeout=60` (и, по-видимому, поэтому первый вопрос в боте «висел» минутами). Поэтому
  каждое обращение (ответ агента целиком и оценщик) идёт через `ev.call_with_deadline` — поток с
  ожиданием по часам; по истечении — `DeadlineExceeded`, поток-сирота доживает сам, результат
  отбрасывается. Не заменяй это обычным `timeout=`.
- **Остановка.** Вопрос «проваленный» (`question_failed`): сбой провайдера/оценщика или таймаут
  ответа либо оценки (сбой ПОИСКА — нет). `RAG_COMPARE_MAX_CONSECUTIVE_FAILURES` (3) подряд — прогон
  останавливается сам (успешный вопрос сбрасывает счёт). `/research_rag_compare_stop` отменяет
  фоновую задачу (`task.cancel()`), не дожидаясь конца вопроса: задача ловит `CancelledError`,
  делает `uncancel()`, сохраняет ЧАСТИЧНЫЙ отчёт (`status=stopped`, `stop_reason`, `planned`),
  присылает частичный итог и снимает флаг — новый запуск возможен сразу. Рабочий поток с начатым
  вызовом остановить нельзя: он доживает не дольше своего предела по часам, результат отбрасывается
  (агенты изолированы), а `threading.Event` отмены не даёт ему начать следующий этап. Повторная команда во время остановки/завершения отвечает «уже запрошена/
  завершается», без прогона — «не идёт».
- **Изоляция.** Каждый ответ строит СВЕЖИЙ `SmartAgent` во временном каталоге (пустая память,
  профиль без полей, `mcp_*_dir=""`, `cbr_enabled=False`); режимы отличаются только
  `set_layer_enabled("rag", ...)`; настройки поиска — из `config.py`, как в рабочем режиме, и
  записываются в отчёт. Память и профили реальных чатов не затрагиваются; кэш агентов командного
  слоя не используется.
- **Оценка вслепую по чек-листу.** `judge()` — отдельный вызов `main_client` (`json_object`,
  `temperature=0`, `thinking` отключён — иначе на reasoning-моделях лимит токенов целиком уходил на
  скрытые размышления и `content` приходил пустым; один повтор с удвоенным лимитом при обрезанном
  JSON или пустом ответе) на КАЖДЫЙ ответ отдельно:
  вопрос, пронумерованные ожидаемые факты, ответ; режим в запросе не упоминается. Покрытие = доля
  найденных фактов; противоречия — отдельный счётчик. Оценщик — та же модель, что отвечает:
  смещение возможно, поэтому отчёт хранит сырые ответы (`/research_rag_compare_report <номер>`).
- **Метрики поиска.** `fired` (хоть один фрагмент прошёл порог), `hit` (заголовок фрагмента
  начинается с ожидаемого префикса из набора). Перед прогоном заголовки документов индекса
  сверяются с ожидаемыми префиксами (`index_store.list_titles`): вопросы с «источника нет в
  индексе» помечаются и не считаются слабостью поиска. Индекс не построен — прогон не стартует.
  Сбой поиска в режиме с RAG (`rag_context.FAILURE_WARNING`) исключает вопрос из сравнения.
- **Исключение из расчёта**: нет оценённых ответов в обоих режимах или сбой поиска — вопрос не
  входит в средние и счётчики лучше/равно/хуже, а сводка называет причину; режим без единого
  оценённого ответа — «сравнение невозможно».
- **Отчёты**: `RAG_COMPARE_REPORT_DIR` (`data/rag_eval/`, `<UTC-время>.json`, запись через
  временный файл + `os.replace`); «последний» — файл с максимальным именем; повреждённый файл даёт
  сообщение, а не исключение. Отчёт общий на бот и не содержит данных пользователей. Набор вопросов
  — файл `RAG_COMPARE_QUESTIONS_FILE` (по умолчанию `data/rag_eval/questions.json`, поля `question`,
  `kind`, `facts`, `sources` — префиксы заголовков документов индекса; формат — в README). Он НЕ
  коммитится: вопросы и факты привязаны к корпусу оператора, а корпус в репозиторий не входит;
  не клади его (и калибровочные запросы `data/rag_eval/calibration_queries.txt`) под контроль
  версий и не копируй в артефакты OpenSpec и документацию текст документов, их названия и ники
  авторов — в примерах используй вымышленные. Без файла команда отвечает, где его создать; при
  смене корпуса проверяй, что документы набора проиндексированы.
- Прогон тратит ≈40 вызовов LLM (≈3,5 минуты) и использует Ollama в режиме с RAG; запустить его
  может любой пользователь при `RESEARCH=true` — как и остальные research-команды.

## `/research_constraints`

`ConversationHandler` на 4 состояния (вопрос → один из 4 сценариев кнопками → для 3 и 4 ещё
параметр текстом). Найдено эмпирически на DeepSeek (на Kimi не проверялось — не выдавай за
универсальное свойство API):
- Сценарий 2 (формат ответа): `json_schema` не поддерживается (400) — используй
  `{"type": "json_object"}`, поля описывай текстом; не возвращай `json_schema`.
- Сценарий 3 (`max_tokens`): значение от пользователя уходит в API как есть (ограничение на
  стороне API, не постобработкой). На reasoning-моделях лимит может целиком уйти на
  размышления, `content` пуст при `finish_reason == "length"` — `content_or_reasoning_fallback`
  подставляет обрезанный `reasoning_content`; сохраняй.
- Сценарий 4 (`stop`): до `CONSTRAINTS_MAX_STOP_WORDS` (4) слов через запятую.

Обозначения сообщений (сохраняй): 👉 — ждёт выбора/ввода; 📊 — результат сценария; 📈 —
статистика (`finish_reason`, токены) отдельным сообщением после результата (кроме ошибки API).

## `/research_temperature`, `/research_models`

- `temperature`: 2 состояния, нейтральный промпт, `thinking` отключён
  (`extra_body={"thinking": {"type": "disabled"}}`). Сценарии 1–4 — фиксированные 0 / 0.7 / 1.2 / 2;
  сценарий 5 — параллельно 1–4 (`ThreadPoolExecutor`) + сравнение через `main_client` по
  точности, креативности, разнообразию.
- `models`: `MODEL_CATALOG` — список `{"id", "label", "client", ...цены}`, у каждой модели свой
  клиент; `call_model()` принимает `client` и `model_id` явно. Идентификаторы моделей приходят из
  `providers/*_client.py` (из `.env`); при замене меняй элемент каталога, а не `MAIN_MODEL`.
  `thinking` НЕ отключается. Статистика включает время и стоимость (цены в каталоге
  иллюстративные, не официальные). Сценарий 5: параллельно 1–4, затем сравнение ОДНИМ запросом
  через `main_client`/`MAIN_MODEL` (не через модель каталога) по качеству, скорости,
  ресурсоёмкости; статистика передаётся модели в самом запросе.
