# price_watch/ — опрос цен и сводки по расписанию (`/watch*`)

Корневые правила — в `/CLAUDE.md`. Спека — `openspec/specs/price-watch/spec.md`, обоснования —
`openspec/changes/archive/*add-price-watch-commands/design.md`. Активно при
`PRICE_WATCH_ACTIVE` (= `PRICE_WATCH and bool(MCP_MOEX_DIR)`); иначе команды не регистрируются и
не упоминаются в `/help`/`/start`. Не привязано к `RESEARCH`. Использует ТОЛЬКО `mcp-moex` в
режиме `--watch-db` (у `mcp-bybit`/`atomno-mcp-cbr-rates` такого режима нет).

Конфигурация: `PRICE_WATCH` (флаг, по умолчанию `true`; отдельный флаг нужен, чтобы оператор мог
оставить smart-агенту данные биржи, но не включать бота, который пишет сам), `PRICE_WATCH_DB`
(файл SQLite сервера, путь абсолютный), `PRICE_WATCH_TIMEOUT_SECONDS` (90, >0; больше
`MCP_TIMEOUT_SECONDS`, потому что плановый вызов опрашивает биржу по всем чатам разом).
Разбор свободного текста `/watch` — `WATCH_PARSER_MODEL` (имя модели в Ollama; пусто — выключено)
и `WATCH_PARSER_TIMEOUT_SECONDS` (>0).

Команды: `/watch <тикеры> <период опроса> <период сводки>` (пример `/watch SBER GAZP 15m 1h`),
`/watch_status`, `/watch_report`, `/watch_stop`. При строгом синтаксисе LLM не участвует; при
заданном `WATCH_PARSER_MODEL` свободный текст `/watch` разбирает локальная модель-парсер
(`nl_parse.py`), но подготовка сводки по-прежнему без LLM (её собирает сервер).

## Разделение ответственности

СЕРВЕР `mcp-moex` хранит опросы, замеры и сводки в SQLite, опрашивает ISS по вызову клиента,
считает агрегаты и собирает текст сводки (шаблон без LLM). Он «пассивен»: время не измеряет,
ничего не отправляет. БОТ — команды, часы и доставка.

```
/watch -> watch_set(chat_id, тикеры, периоды) -> сервер (SQLite)
WatchScheduler: ждёт next_due_at (не дольше часа) -> тик:
    watch_run_due -> сводки + next_due_at
    отправка в чат -> watch_ack(id доставленных)   [ТОЛЬКО после успешной отправки]
```

## Модули

- `parse.py` — чистый разбор аргументов: тикеры (пробелы/запятые), два последних слова —
  периоды (`m/h/d` или `м/ч/д`). Проверяет только ФОРМУ; границы, число тикеров и существование
  бумаги — на сервере.
- `nl_parse.py` — разбор свободного текста `/watch` локальной моделью-парсером: самодостаточная
  копия промпта/guard из `finetuning/watch_parser/` (без импорта `finetuning/`), чистые функции
  (промпт, guard, `extract_json`, `to_watch_request`) + тонкий нативный вызов `/api/chat` с
  жадными параметрами eval. `src/` не зависит от `finetuning/` — правки там переносятся сюда вручную.
- `texts.py` — чистые тексты по ответам сервера, `friendly_tool_error` (сырой дамп валидатора
  схемы → русская фраза). Текст СВОДКИ собирает сервер.
- `scheduler.py` — `run_tick()` (вызов сервера и отправка внедряются) и `WatchScheduler`
  (`asyncio`, без JobQueue); `start_scheduler`/`stop_scheduler` — хуки `post_init`/`post_stop`.
- `commands.py` — обработчики (только личные чаты; `chat_id` из `update.effective_chat.id`, не из
  аргументов), `build_price_watch_handlers()`. Обращения к серверу — `mcp_integration/watch_session.py`.

## Что сохранять

- **Один процесс сервера на обращение** (`call_watch_tool`), два обращения за тик
  (`watch_run_due`, затем `watch_ack`) — не держать сессию открытой на время отправки.
- **Доставка «не менее одного раза»**: сначала отправка, потом подтверждение. Сбой отправки
  оставляет сводку неподтверждённой; следующие сводки ЭТОГО чата в тике не отправляются
  (порядок), другие чаты не страдают. «Бот заблокирован»/«chat not found»
  (`is_chat_unreachable`) → `watch_stop` для чата.
- **Планировщик**: `run_tick()` не знает про Telegram и MCP. Первый тик — сразу при запуске;
  ожидание не дольше `RECHECK_SECONDS` (час); сбой — пауза 60 с, удвоение до 900 с, сброс после
  успеха; пользователям о фоновых сбоях не пишем. `/watch` вызывает
  `schedule_at(min(next_poll_at, next_report_at))` — только на более РАННИЙ срок; во время
  идущего тика учитывается по его итогам.
- **Модель инструментов расписания не видит**: сервер для `/smart_agent` запускается БЕЗ
  `--watch-db` + `MODEL_TOOL_ALLOWLIST`; инструменты расписания помечены НЕ read-only — «read-only»
  в проекте значит «можно отдавать модели».
- **Серверный отказ показывается как есть** (`WatchToolError`). Текст «опрос не задан» написан
  для модели, поэтому `/watch_report` для пустого чата уточняет состояние через `watch_status` и
  отвечает своими словами.
- **Текст сводки — без правок**: оговорки сервера (задержка 15 минут, «не рекомендация») должны
  доезжать до пользователя.
