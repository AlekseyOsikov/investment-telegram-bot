# agents/ — `/agent`, `/agent_compare`, `/smart_agent`

Корневые правила (домен, безопасность, конфигурация) — в `/CLAUDE.md`. Слой `tools` у
`/smart_agent` (инструменты рыночных данных) — в `src/mcp_integration/CLAUDE.md`. Спека
автоматики задач — `openspec/specs/smart-agent-task-automation/spec.md`.

Агенты используют `main_client`/`MAIN_MODEL`/`SYSTEM_PROMPT`; исключения OpenAI SDK в `ask()`
не перехватывают — перевод в русское сообщение делает командный слой (как `handle_message`).

## Карта модулей

- `agent.py` (`Agent`) — история по именованным веткам в `AGENT_HISTORY_DIR/<chat_id>.json`;
  `context_strategies.py` — 4 стратегии контекста (`STRATEGIES`); `agent_command.py` — `/agent`,
  `/agent_reset`, `/agent_history`, `/agent_mode`, `/agent_context`, `/agent_checkpoint`,
  `/agent_branch`, `/agent_switch_branch`.
- `active_mode.py` — трекер `{chat_id: "agent"|"compare"|"smart_agent"}` в памяти процесса:
  `/agent`, `/agent_compare`, `/smart_agent` попарно взаимоисключающи. Отдельный модуль, чтобы
  не было цикла импорта.
- `compare_command.py` — `/agent_compare`, `/agent_compare_report`, `/agent_compare_reset`.
- `smart_agent.py` (`SmartAgent`) — владение состоянием, диск, вызовы LLM; правила вынесены в
  `memory_state.py` (константы слоёв/полей профиля, чистый разбор и сборка JSON-файла памяти,
  миграция старых форматов; `smart_agent.py` их реэкспортирует), `task_state.py` (автомат), `invariants.py` (инварианты), `market_tools.py` (тексты и цикл слоя
  `tools`), `rag_context.py` (правила и тексты слоя `rag`, второй этап отбора), `rag_search.py`
  (конвейер поиска слоя `rag`), `context_builder.py`
  (чистая сборка контекста из слоёв: порядок, сообщения профиля и памяти), `rag_rewrite.py`
  (переписывание вопроса в поисковый запрос: промпт, нормализация ответа, слияние кандидатов). Принцип разделения везде один: правила и тексты — в отдельном модуле, владение
  состоянием и вызовы LLM — в `SmartAgent`/`Agent`.
- `smart_agent_command.py` — `/smart_agent`, `/smart_agent_profile*`, `/smart_agent_remember|forget|
  long_show`, `/smart_agent_task_*`, `/smart_agent_invariant_*`, `/smart_agent_show|toggle|reset`;
  21 `build_smart_agent_*` в `main.py`.

Тесты: `tests/test_task_state.py` (чистые функции автомата, без моков) — новые правила автомата
покрывай здесь, а не моками `SmartAgent`.

Конфигурация `/agent` (`config.py`): `AGENT_CONTEXT_STRATEGY` (`summary` по умолчанию | `sliding_window`
| `sticky_facts` | `branching`) — стратегия по умолчанию для НОВЫХ чатов и миграции старых файлов;
пользователь сам переключает свою `/agent_context`, выбор хранится в JSON истории, а не в `.env`.
`AGENT_ENABLED_STRATEGIES` (по умолчанию все 4; непустой, по `_SUPPORTED_AGENT_STRATEGIES`, обязан
включать `AGENT_CONTEXT_STRATEGY`) — решение оператора, какие стратегии предлагаются КНОПКАМИ
(`_strategy_keyboard()`, `agent_context_callback()` отклоняет отключённую); поведение `Agent` не
ограничивает — чат с ранее сохранённой, затем скрытой стратегией продолжает работать по ней.
`AGENT_STRATEGY_LABELS` — единственное место с подписями стратегий. `AGENT_CONTEXT_RECENT_PAIRS`/
`AGENT_SUMMARY_CHUNK_PAIRS`/`AGENT_SUMMARY_MAX_TOKENS`, `AGENT_FACTS_MAX_TOKENS` — параметры
стратегий; у `/smart_agent` свои независимые переменные `AGENT_MEMORY_*`.

## `/agent`: управление контекстом

В LLM уходит результат ОДНОЙ из 4 стратегий (`Agent._strategy`, per-chat, переключается
`/agent_context` среди `AGENT_ENABLED_STRATEGIES`). Это не нарушает запрет на runtime-смену
модели/провайдера/промпта: стратегия влияет только на сборку контекста.

**Хранение.** `Agent._branches: {имя: {"messages", "facts", "facts_processed_pairs", "summary",
"summarized_pairs"}}` + `_active_branch` (по умолчанию `"main"`). Сообщения ветки хранятся целиком.
`facts`/`summary` и их счётчики — тоже PER-BRANCH (доступ через `@property` `_facts` и т.д.).
Новая ветка (`create_branch`) стартует с ПУСТЫМИ facts/summary, а не наследует — иначе счётчики
превысили бы число сообщений; не подставляй состояние ветки-источника.

**Стратегии:**
- `sliding_window` — последние `AGENT_CONTEXT_RECENT_PAIRS` пар (остальное только из контекста,
  не с диска).
- `sticky_facts` — словарь фактов, обновляемый JSON-вызовом LLM (`_update_facts`,
  `AGENT_FACTS_SYSTEM_PROMPT`) ДВАЖДЫ за ход: `before_turn()` догоняет бэклог прошлых ходов,
  `after_turn()` учитывает только что полученную пару. Двойной вызов намеренный; при пустом
  бэклоге `_update_facts` ничего не делает. Уходит весь бэклог ещё не учтённых пар; счётчик
  `facts_processed_pairs` растёт ТОЛЬКО при успехе (неудачная пара остаётся в бэклоге). Защита от
  обрезанного JSON: правило промпта (≤~20 ключей) и один повтор с удвоенным `max_tokens` при
  `JSONDecodeError`; при неудаче facts остаются прежними, `ask()` не падает. `json_object`
  проверен на DeepSeek, не на Kimi.
- `branching` — вся история активной ветки. `create_checkpoint(name)` запоминает длину;
  `create_branch(checkpoint, name)` создаёт ОДНУ ветку (несколько — повторными вызовами);
  `switch_branch(name)` НЕ сбрасывает facts/summary (у каждой ветки свои). Команды
  checkpoint/branch/switch разрешены только при стратегии branching
  (`_require_branching_strategy()` в `agent_command.py`; сам `Agent` не проверяет). Вне Branching
  понятие ветки пользователю не показывается (`/agent_mode`).
- `summary` (по умолчанию, `AGENT_CONTEXT_STRATEGY`, а также для файлов старого доветочного
  формата, `_load_state()`) — инкрементальный rollup: `summary` + «свежий хвост» = всё, что ещё не
  свёрнуто. `AGENT_CONTEXT_RECENT_PAIRS` — минимальный хвост; при накоплении сверх него ещё
  `AGENT_SUMMARY_CHUNK_PAIRS` пар сворачиваются вместе со старой сводкой
  (`AGENT_SUMMARY_SYSTEM_PROMPT`). Обновляется только в `after_turn()`.

`set_strategy()` не трогает summary/facts и счётчики (накапливаются, пока активна их стратегия).
Сбой сворачивания/обновления facts не должен ронять уже полученный ответ — `_maybe_update_summary`/
`_update_facts` единственные места в `Agent`, где ловятся исключения SDK.

`/agent_history` печатает историю активной ветки как есть (не summary/facts), режет по
`TELEGRAM_MESSAGE_LIMIT`; `/agent_reset` очищает все ветки, чекпоинты, facts, summary, но НЕ выбранную
стратегию.

## `/agent_compare`

Инструмент тестирования: три ФИКСИРОВАННЫЕ стратегии (Sliding Window, Sticky Facts, Branching —
без summary), у каждой свой `Agent` и файл `<chat_id>_compare_<стратегия>.json`, кэш
`_compare_agents`. Вопрос идёт во все три параллельно (`ThreadPoolExecutor`), вывод в
ФИКСИРОВАННОМ порядке (`COMPARE_STRATEGIES`) отдельными сообщениями с префиксом и строкой токенов;
сбой одной не мешает показать другие (`api_error_to_message`). `/agent_compare_report` сравнивает
последние ответы по качеству/устойчивости/токенам (`AGENT_COMPARE_REPORT_SYSTEM_PROMPT`), работает
только в режиме сравнения; `/agent_compare_reset` — независимо от режима.

## `/smart_agent`: память

Файл `AGENT_MEMORY_DIR/<chat_id>.json` (отдельно от `AGENT_HISTORY_DIR`). Всё — в разрезе профиля.

- `short_term` — сырые сообщения, пишется АВТОМАТИЧЕСКИ на каждый `ask()`; на диске без лимита, в
  LLM — последние `AGENT_MEMORY_SHORT_TERM_PAIRS` пар.
- `working` — одна задача-автомат (см. ниже). Пишется явно (`/smart_agent_task_*`) и автоматически
  техническим вызовом `update_task_state` после каждого ответа.
- `long_term` — факты `{"text","source","created_at"}`: явно `/smart_agent_remember` ДОСЛОВНО
  (`source: "user"`) и автоматически (`"auto"`: факты из диалога и итог задачи). При превышении
  `AGENT_MEMORY_LONG_TERM_MAX_FACTS` вытесняется самый старый, но СНАЧАЛА автоматический и никогда
  только что добавленный (`_append_fact`) — иначе автоизвлечение вымоет ручные факты.
- Геттеры/мутаторы требуют активного профиля (без него — пустое значение/`False`);
  `_require_active_profile()` в командном слое отвечает подсказкой `/smart_agent_profile`.
- **Чувствительные данные**: слои не фильтруют вход, защита держится на двух вещах — предупреждения
  в текстах команд, где пишет пользователь (`/smart_agent_remember|task_set|task_start`, анкета,
  `/smart_agent_profile_set`), и запрет извлекать номера счетов/карт, паспортные данные и денежные
  суммы в промптах `AGENT_TASK_STATE_SYSTEM_PROMPT`/`AGENT_TASK_START_SYSTEM_PROMPT`. Сохраняй оба.
- `get_last_context_messages()` — ровно те сообщения, что ушли в LLM (для `/smart_agent_show`).
- `enabled_layers` (на весь чат, не per-profile; все `True`; `_load_state()` стартует с «все
  включены» и накладывает сохранённое): `profile`, `invariants`, `short_term`, `working`,
  `long_term`, `tools`, `rag`, `task_autostart`; переключатель `/smart_agent_toggle
  <profile|invariants|short|working|long|tools|rag|autostart>` БЕЗ удаления данных — инструмент
  проверки влияния слоя. `task_autostart` НЕ слой контекста — управляет только вызовом `_maybe_start_task()`.
  Выключение `working` замораживает автомат целиком. `/smart_agent_reset` очищает три слоя
  активного профиля (не профиль, `meta`, инварианты, другие профили, `enabled_layers`).
- Порядок сборки контекста: инварианты → профиль → инструменты → материалы (`rag`, только правила) →
  долговременная → задача → краткосрочный диалог (от общего/стабильного к свежему).

## `/smart_agent`: справочные материалы (слой `rag`)

Спеки — `openspec/specs/smart-agent-rag/spec.md` и `rag-query-rewrite/spec.md`; обоснования и
калибровка порога — `openspec/changes/archive/*add-smart-agent-rag/design.md` и
`*add-rag-rerank-and-rewrite/design.md`. Использует индекс `rag/` (см. `src/rag/CLAUDE.md`).
Правила и тексты — `rag_context.py` и `rag_rewrite.py` (чистые модули, тесты
`tests/test_rag_context.py`, `tests/test_rag_rewrite.py`); конвейер поиска (переписывание,
эмбеддинг, кандидаты, отбор; `RagSearchConfig`, `retrieve()`) — `rag_search.py` (тесты
`tests/test_rag_search.py`, внешние вызовы подставляются параметрами); состояние чата
(`_last_rag_*`) и вход — `SmartAgent._retrieve_materials()`.

- **Один поиск на вопрос, до ветвления на пути ответа** (в `ask()`, до `_market_tools_mode()` и до
  запуска MCP-процессов): [переписывание вопроса, если настроено] → эмбеддинг поискового текста
  (`embed_texts(..., budget_seconds=RAG_SEARCH_TIMEOUT_SECONDS)`) →
  `index_store.search(RAG_SMART_AGENT_STRATEGY, ..., RAG_CANDIDATES)` → второй этап
  `rag_context.select_chunks()` (порог `RAG_MIN_SCORE` по КАЖДОМУ кандидату, относительный порог,
  отсев коротких чанков и дубликатов, предел чанков на документ, не более `RAG_TOP_K`). Результат
  (`Materials`) одинаково идёт в `_plain_completion` и в `_run_tool_loop`: фрагменты присутствуют во
  всех обращениях цикла. Порядок и нейтральные значения шагов — в `config.py` и
  `select_chunks()`; при `RAG_CANDIDATES=RAG_TOP_K` и нейтральных шагах поведение прежнее.
- **Переписывание** (`REWRITE_PROVIDER` пуст — выключено): служебный вызов `_rewrite_query()`
  (клиент и модель — `providers/rewrite_client.py`; `temperature=0`, без автоповторов SDK, предел
  ПО ЧАСАМ `REWRITE_TIMEOUT_SECONDS` в потоке-демоне — таймаут HTTP-клиента не ограничивает
  общее время, как показал живой прогон; `thinking` отключён у `deepseek`/`kimi`). Модель видит
  ТОЛЬКО текст вопроса в тегах `<вопрос>` (данные, не инструкция) и неизменный промпт из
  `rag_rewrite.py`: не память, не профиль, не инварианты, не фрагменты. Сбой, таймаут, пустой или
  непригодный ответ (отказ, иероглифы — локальные модели иногда отвечают по-китайски, длиннее
  `MAX_QUERY_CHARS`) — поиск по исходному вопросу, причина в `SearchInfo.rewrite_reason`, пользователю
  не показывается.
- **История диалога в переписывании** (`REWRITE_HISTORY_QUESTIONS`, 0 — выключено; спека —
  `rag-query-rewrite`, «История диалога в переписывании»): `SmartAgent._history_for_rewrite()` берёт
  из `short_term` АКТИВНОГО профиля ТОЛЬКО реплики с ролью `user` (`rag_rewrite.history_questions`:
  последние N, от старых к новым, каждая усечена до `HISTORY_QUESTION_MAX_CHARS`) и вызывается ДО
  дописывания текущей пары — текущий вопрос в выборку не попадает. История пуста, если она
  выключена настройкой, выключен слой `short_term`, диалог пуст (первый вопрос, очистка памяти) или
  нет активного профиля. Промпт: базовый `REWRITE_SYSTEM_PROMPT` НЕ меняется (без истории запрос к
  модели побайтно прежний, есть регресс-тест), с историей к нему добавляется `HISTORY_RULES`
  (история — данные; использовать только для неполного вопроса; самодостаточный переписывать без
  неё) и блок `<история>` перед `<вопрос>`. Откат при сбое — по ИСХОДНОМУ вопросу БЕЗ истории
  (`SearchInfo.history_used` = 0). В `_retrieve_materials`/`search_materials` необязательный
  `history`: None — из памяти агента, список — как есть (сравнение режимов на изолированных
  агентах). `/smart_agent_show` показывает только ЧИСЛО прошлых вопросов в переписывании. Переписанный запрос — ТОЛЬКО в поиск: в запрос основной модели, `short_term` и
  строки источников идёт исходный вопрос. `REWRITE_SEARCH_MODE=both` (по умолчанию) ищет и по
  исходному вопросу, и по переписанному (одним запросом к серверу эмбеддингов) и объединяет
  кандидатов по лучшей оценке (`rag_rewrite.merge_candidates`): `rewritten` на сравнении режимов
  оказался хуже — переписанный запрос уходит от формулировки документа, и часть чанков не проходит
  порог.
- **Этап задачи может отключить поиск** (спеки `smart-agent-rag`, `smart-agent-task-automation`;
  обоснования — `openspec/changes/*add-stage-aware-rag-and-dialog-runner/design.md`). На сборе
  вводных и приёмке реплики пользователя — ответы на вопросы бота, а не вопросы к корпусу; поиск там
  пуст, и при выключенных `tools` режим «не знаю» остановил бы сам этап. Поэтому у `TaskStage` есть
  булев `rag_search` (`False` у `planning` и `validation` сценариев `portfolio`/`review`; у `asset`,
  `execution` и `done` — `True`); `task_state.search_allowed(task)` учитывает его только для
  АКТИВНОЙ задачи (нет задачи, пауза, `done` — поиск по общим правилам), а `SmartAgent.
  _search_skipped_by_stage()` — ещё и активный профиль, включённый слой `working` и включённый `rag`
  с построенным индексом. Пропуск делается в `ask()` ДО `_retrieve_materials()`: `Materials(
  skipped_by_stage=True)` — пустой и `searched=False`, поэтому нет эмбеддинга и переписывания, «не
  знаю», правила цитат и повтора; модель вызывается всегда; в служебном сообщении
  `rag_context.STAGE_SKIP_NOTE` (`SmartAgentAnswer.stage_skip_note`), в `/smart_agent_show` статус
  `STATUS_SKIPPED`. Признак — свойство записи реестра сценариев, как `gate`: пользователь и оператор
  его не меняют, на переходы и гейты он не влияет. Решение берётся по этапу ДО текущего хода (технический вызов автомата идёт
  после ответа). Реальный вопрос к корпусу посреди `planning`/`validation` отвечается без
  материалов — осознанный компромисс (трёхзначный режим не делали). Признак `rag_search` и режим
  «не знаю» — НЕЗАВИСИМЫЕ условия: первый решает, искать ли на этапе, второй — можно ли ответить
  без модели; пока задача АКТИВНА (`SmartAgent._task_active()`: профиль, слой `working`, задача есть,
  не пауза, не `done`), отказ без модели не применяется на ЛЮБОМ этапе (см. «Цитаты и „не знаю“»;
  причина — живой прогон `scripts/dialog_eval.py`: на `execution` при выключенных `tools` отказ
  получали «предложи, что поменять» и «принимаю», задача не доходила до `done`). «Источники
  или явная строка» на каждом ходу уже обеспечивают `NO_MATERIALS_NOTE`, `ABSTAIN_TEXT`,
  `FAILURE_WARNING`, `UNVERIFIED_NOTE` и `STAGE_SKIP_NOTE`.
- **Правила — system, фрагменты — последнее `user`-сообщение.** `build_rules_message()` (данные, не
  инструкции; образовательный материал, не рекомендация и не гарантия; НЕ ослабляет `SYSTEM_PROMPT`;
  инварианты приоритетнее) добавляется только когда фрагменты есть; `build_user_message()` ставит
  блок фрагментов ПЕРЕД отделённым вопросом. Оговорки в тексте правил не убирать (тест проверяет).
- **Цитаты и «не знаю»** (спека `smart-agent-rag`; обоснования —
  `openspec/changes/*add-rag-citations-and-abstain/design.md`). `build_rules_message()` требует
  закончить ответ блоком `Цитаты:` со строками `[n] «дословный отрывок»` (n — номер в блоке
  материалов, ≤ `MAX_CITATIONS`, ≤ `MAX_QUOTE_CHARS`; оговорка о неослаблении `SYSTEM_PROMPT`
  сохраняется и тестируется). После ответа `ask()` вызывает `rag_context.build_citation_result()`:
  `parse_citations` отделяет хвост, `verify_citation` проверяет цитату как подстроку текста фрагмента
  (регистр, пробелы, `ё/е`, кавычки и тире нормализуются; `…` делит цитату на части в порядке
  следования; вся цитата ≥ `MIN_QUOTE_CHARS`, часть ≥ `MIN_PART_CHARS`). Источники
  (`SmartAgentAnswer.rag_sources`) — ВСЕ поданные фрагменты с `chunk_id`, проверенные цитаты
  (`SmartAgentAnswer.citations`) показываются под своим фрагментом, фрагмент без цитат — без них;
  «раздел» = `chunk_index` + `chunk_id` (заголовка раздела в индексе нет). Без проверенных цитат —
  ОДИН повтор `_citation_retry()` (без инструментов, на черновике; +1 к `llm_calls`); не помог —
  те же фрагменты без цитат и `UNVERIFIED_NOTE`. Ответ без блока цитат уходит и в чат, и в
  `short_term`. `Materials.searched` отличает «ничего не нашлось» от «слой выключен / индекса нет /
  сбой поиска»: при `searched` и пустой выдаче `rag_context.should_abstain()` (tools не могут
  участвовать: `_market_tools_mode() != STATUS_OK`, и задача НЕ активна — `task_active` по состоянию до
  хода) даёт ответ `ABSTAIN_TEXT` без вызова модели и MCP (`abstained`, `llm_calls=0`, пара пишется
  в `short_term`); при `STATUS_OK` ИЛИ активной задаче модель вызывается с
  `build_no_materials_message()` и пометкой `NO_MATERIALS_NOTE`. Побочный эффект: при включённом
  `rag` и выключенных `tools` БЕЗ активной задачи реплики без близких материалов («привет») тоже
  получают отказ — слой отключается `/smart_agent_toggle rag`.
- **В `short_term` пишется исходный вопрос без чанков**; тексты чанков на диск не попадают. Блок
  фрагментов хранится только в памяти (`_last_rag_block`) — последнее `user`-сообщение в
  `get_last_context_messages()` не входит. Служебные вызовы LLM (автомат, детектор, ревизор)
  материалов не получают.
- **Молчаливый пропуск**: слой выключен или индекс выбранной стратегии не построен — пустой результат
  без предупреждения. **Сбой поиска** (Ollama недоступна/бюджет исчерпан, повреждённый индекс) не
  роняет ответ: пустой результат + `rag_context.FAILURE_WARNING` в `SmartAgentAnswer.warnings`;
  причина — в `_last_rag_failure` для `/smart_agent_show`; следующий вопрос пробует снова.
- **Видимость**: строки `📚 <документ> — фрагмент N (id …), близость X` и под ними проверенные
  цитаты (`rag_context.format_answer_service_lines`) идут в служебное сообщение после ответа; `/smart_agent_show` — статус слоя (`get_rag_status()`: выключен /
  индекс не построен / включён / недоступен), поисковый запрос и итог отбора
  (`get_last_rag_search()` → `rag_context.describe_search()`: переписанный запрос или причина отката,
  кандидатов найдено / отобрано, отброшено по причинам) и блок материалов последнего вопроса. Итог
  поиска — только в памяти агента, на диск не пишется.
- Порог зависит от связки «модель эмбеддингов + стратегия + чанкинг + переписывание» — при смене
  повторить калибровку (`scripts/rag_calibrate.py`, с переписыванием — `--rewrite`; результаты — в
  `design.md` изменения, раздел «Калибровка»). Первый
  вопрос после простоя Ollama может не уложиться в бюджет (холодный старт) — ответ без материалов.

Конфигурация (значения по умолчанию — в `config.py`): `AGENT_TASK_STATE_*` и `AGENT_TASK_START_*`
— ДВА промпта технического вызова (когда задачи нет, нужен лишь короткий детектор старта — не
гонять полный разбор на каждый разовый вопрос); `AGENT_MEMORY_MAX_INVARIANTS`,
`AGENT_INVARIANT_MAX_CHARS`, `AGENT_INVARIANTS_*` — слой инвариантов. Все системные промпты
технических вызовов в `.env` не выносятся.

## `/smart_agent`: профили

`_profiles: {имя: {"meta", "short_term", "working", "long_term", "invariants"}}` + `_active_profile`;
тот же принцип, что ветки Branching: `switch_profile` переключает диалог, задачу, факты и инварианты
целиком; новый профиль стартует с ПУСТЫМИ слоями.

- `meta` (`PROFILE_FIELDS`: `style`, `experience_level`, `format`, `risk_tolerance`, `horizon`,
  `interests`, `excluded_topics`) — качественные предпочтения подачи, НИКОГДА не финансовые/личные
  данные (новое поле сверяй с доменными правилами). Заполняется ТОЛЬКО явно пользователем: анкета
  (по вопросу на поле, «пропустить») или `/smart_agent_profile_set`; никакая LLM-эвристика не
  решает за пользователя.
- `context_builder.profile_meta_message()` — отдельное системное сообщение; ЯВНО ограничивает влияние профиля
  стилем/форматом/объёмом и не отменяет предупреждения `SYSTEM_PROMPT` (например,
  `risk_tolerance: агрессивный` не повод убрать дисклеймеры). Профиль не должен переопределять
  `SYSTEM_PROMPT`, провайдера, модель.
- Нет активного профиля → пикер вместо цикла вопросов: при входе в `/smart_agent`
  (`PROFILE_PICK`/`WAITING_PROFILE_NAME`/`WAITING_PROFILE_FIELD` → `WAITING_QUESTION`); после
  `/smart_agent_profile_delete` активного (`delete_profile` ставит `active_profile = None`); и если
  профиль удалён посреди диалога — `smart_agent_receive_question` проверяет ДО `ask()` (защитный
  `RuntimeError` в `ask()` — для ошибки программиста, не для штатного сценария).
- `/smart_agent_profile` — ОТДЕЛЬНЫЙ `ConversationHandler`, работает в любой момент, ведёт в
  `ConversationHandler.END`. Анкеты делят код (`_handle_new_profile_name`/
  `_handle_profile_field_answer`, состояние в `context.user_data`), но кнопки с РАЗНЫМИ префиксами:
  `sa_start:` (пикер `/smart_agent`) и `sa_manage:` (`/smart_agent_profile`/`_delete`) — иначе
  `ConversationHandler` одного пикера перехватит кнопки другого.
  `smart_agent_manage_pick_callback` — ещё и entry point своего handler-а (кнопки вне диалога).
- **Порядок регистрации в `main.py` ВАЖЕН**: `build_smart_agent_profile_conversation_handler()`
  ПЕРЕД `build_smart_agent_conversation_handler()` — анкета профиля первой перехватывает обычный
  текст, иначе ответ на вопрос анкеты уйдёт агенту как вопрос пользователя.
- Миграция: файлы до профилей (плоские `short_term`/`working`/`long_term`) заворачиваются в профиль
  `"Профиль по умолчанию"` и он СРАЗУ активен; файлы без ключа `invariants` получают пустой список
  (`invariants.sanitize_list`).

## `/smart_agent`: инварианты

Жёсткие ограничения пользователя («без криптовалют», «доля акций ≤ 40%»). НЕ четвёртый слой
памяти: `long_term` — ЗНАНИЕ, `meta` — ПРЕДПОЧТЕНИЕ подачи, инвариант — ЗАПРЕТ, подкреплённый
проверкой кодом. Список `{"text","category","created_at"}` в профиле; категория
(`strategy|instruments|risk|process|other`) — префикс до двоеточия (`invariants.parse_input`).

- **Пишется ТОЛЬКО явными командами** (`/smart_agent_invariant_add|remove`); автоизвлечение не
  добавлять — по тому же правилу, что и для `meta`.
- **Лимит БЕЗ вытеснения**: при `AGENT_MEMORY_MAX_INVARIANTS` добавление отклоняется
  (`invariants.ADD_LIMIT`) — запрет не должен теряться незаметно.
- **Уровень 1 — контекст любого ответа.** `invariants.build_context_message()` идёт ПЕРВЫМ после
  `SYSTEM_PROMPT`: нумерованный список; приоритет выше профиля и просьбы; проверять МОЛЧА (без
  анонса «проверю на инварианты» — он читается как отдельный шаг работы); при конфликте —
  отказать, назвать НОМЕР и формулировку, предложить альтернативу; при настойчивости не уступать,
  снять можно только `/smart_agent_invariant_remove`; инвариант НЕ ослабляет предупреждения
  `SYSTEM_PROMPT` (оговорку, как в `_profile_meta_message`, не убирать — иначе слой станет
  пользовательским системным промптом).
- **Уровень 2 — проверка результата задачи КОДОМ.** Когда на этапе `validation` появляется ещё НЕ
  проверенный результат (`task_state.needs_invariant_check`: `result_payload` против снимка
  `INVARIANTS_CHECKED_KEY`), `SmartAgent._check_invariants()` делает отдельный вызов-ревизор
  (`AGENT_INVARIANTS_SYSTEM_PROMPT`, `json_object`, один повтор с удвоенным лимитом). Ревизору
  уходит только артефакт (`result_payload`), не диалог. При `verdict: "violated"` с хотя бы одним
  существующим номером код откатывает задачу (`task_state.apply_invariant_violations`, через
  `_roll_back`): результат СОХРАНЯЕТСЯ, `verdict` снимается, `awaiting_correction`, вперёд — только
  после НОВОГО результата. Претензии — `INVARIANT_VIOLATIONS_KEY` (вне `data`), снимаются при
  переписывании обязательного ключа этапа. Привязка к результату, а не к факту перехода: иначе
  задача, переведённая на проверку вручную, уезжала бы в `done` непроверенной. Проверка идёт ДО
  приёмки пользователем.
- Ревизор НЕ считает нарушением упоминание запрещённого в пояснении («криптовалюты исключены») и
  долю 0% — только реальное включение в решение (правила 2–3 промпта).
- Смещение к пропускам: `violated` без валидных номеров, ошибка вызова и неразобранный JSON = «нарушений
  нет» (`_call_json_with_retry`) — служебная проверка не должна ни ронять отправленный ответ, ни
  стопорить задачу; инварианты всё равно в контексте ответа.
- Видимость: «⛔ Результат нарушает инварианты…» печатается ВМЕСТО «✅ Этап: …» (переход назад),
  уходит в контекст следующего ответа, строку состояния и `/smart_agent_task_show`; список —
  `/smart_agent_invariant_show` и блок `/smart_agent_show`.
- `/smart_agent_toggle invariants` — единственный слой, выключение которого снимает и проверку
  ревизором; после каждого ответа печатается предупреждение, пока инварианты заданы, но слой
  выключен (`_task_service_lines`). `/smart_agent_reset` инварианты НЕ очищает.

## `/smart_agent`: конечный автомат задачи (`task_state.py`)

`working` = `{"task_type","goal","stage","step","expected_action","paused","paused_at",
"awaiting_correction","data","processed_pairs","created_at"}` или `None`.

**Имена этапов инженерные, означают шаги ИНВЕСТИЦИОННОГО процесса** (сохраняй оговорку в текстах и
докстрингах): `planning` — профилирование (сбор вводных, подтверждение сводки); `execution` —
ФОРМИРОВАНИЕ ПРЕДЛОЖЕНИЯ, а НЕ исполнение сделок (бот не исполняет у брокера); `validation` —
ПРИЁМКА результата пользователем, не машинная проверка (машинная — ревизор инвариантов); `done` —
зафиксировано. Пользователю этапы подписаны по смыслу («формирование портфеля», «разбор»,
«предложение изменений»).

Все сценарии — на одном скелете `planning` → `execution` → `validation` → `done` (откат
`validation` → `execution`); различаются ключами `data`, гейтом на `planning`, текстами:

| Сценарий | `planning` собирает | Гейт вводных | `execution` заполняет |
|---|---|---|---|
| `portfolio` | `goal_type`, `horizon`, `risk`, `constraints`, затем `brief`/`brief_verdict` | да | `allocation` (доли в %) |
| `asset` | `asset`, `horizon`, `role_in_portfolio` | нет | `analysis` |
| `review` | `current_allocation` (только доли), `concern`, `constraints`, затем `brief`/`brief_verdict` | да | `proposed_changes` |

Новый сценарий — одна запись в `SCENARIOS` без изменений логики; гейт — свойство записи
(`TaskStage.gate`). У `asset` гейта нет намеренно (справочный разбор, не рекомендация по структуре);
при добавлении сценария решай по тому, является ли результат рекомендацией. **Денежные суммы не
собираются ни на одном этапе** — только качественные параметры и доли в %.

Правила (сохранять):
- **Условие перехода проверяет КОД, а не модель**: обязательные ключи `data` этапа
  (`required_keys`, `missing_keys`) + значение ключа-гейта (`gate_satisfied`, `_forward_target`).
  Тот же список недостающего уходит в контекст ответа, чтобы отказ на «переходи уже» совпадал с
  реальностью. Контекст называет и СЛЕДУЮЩИЙ этап (`next_forward_stage`) и запрещает выдумывать
  названия этапов и анонсировать служебные проверки бота — всё, что модель говорит о порядке работы,
  должно совпадать с реестром.
- **ГЕЙТ — решение ЧЕЛОВЕКА.** (1) `planning` → `execution` у `portfolio`/`review`:
  `brief_verdict == "confirmed"` — сначала сводка вводных (`brief`), потом прямое подтверждение.
  Отказ (`corrected`) — гейт сбрасывается НА МЕСТЕ (`_reset_gate`: `brief`/`brief_verdict` удалены,
  `awaiting_correction`, этап тот же) + строка «🔁 Вводные не подтверждены». (2) `validation` →
  `done`: `verdict == "accepted"`; `changes_requested` — откат назад.
- **Откат в этап с гейтом снимает его гейт** (`_roll_back` чистит `sequential_keys` и ключ гейта
  целевого этапа) — иначе задача уехала бы по устаревшему согласию.
- **ВПЕРЁД автомат двигается САМ, как только ключи собраны; поле `"stage"` из ответа модели не
  влияет** (раньше модель ставила `verdict: accepted` и оставляла прежний `stage` — состояние
  залипало). Не возвращай «модель решает, пора ли дальше».
- **НАЗАД — единственный переход по явному сигналу**: с `validation` — `verdict`
  (`changes_requested`), с прочих — более ранний допустимый `"stage"`. `_roll_back` снимает ключи
  этапов ПОСЛЕ целевого, но НЕ целевого, и ставит `awaiting_correction` (блокирует движение вперёд
  до правки хотя бы одного ключа этапа). Пара «не чистим ответы + флаг» — сохранять; ручной
  `/smart_agent_task_stage` назад идёт через тот же `_roll_back`.
- **Принимаются только ключи ТЕКУЩЕГО ЭТАПА** (`normalize_data_updates`): иначе модель изобретала бы
  имена параметров (условие не выполнилось бы) и можно было бы перепрыгнуть этап (вернуть
  `allocation` + `verdict: accepted` → `done` без приёмки и ревизора). Фильтр — по этапу, не по
  сценарию. На РУЧНУЮ запись (`/smart_agent_task_set`) не распространяется. Ключи-гейты —
  закрытые значения (`CLOSED_VALUE_KEYS`: `verdict` ∈ `accepted|changes_requested`, `brief_verdict`
  ∈ `confirmed|corrected`) и принимаются ТОЛЬКО В ПОРЯДКЕ (`sequential_keys`): нельзя подтвердить
  сводку до её проговаривания.
- **Кто двигает автомат**: технический вызов LLM после КАЖДОГО ответа (`update_task_state`,
  `json_object`, один повтор с удвоенным `max_tokens`). Командный слой СНАЧАЛА отправляет ответ
  пользователю, потом делает вызов (`_task_service_lines`). Сбой не трогает состояние и
  `processed_pairs` — пары копятся в бэклоге.
- **Старт**: явно (`/smart_agent_task_start`, заменяет задачу) или автоматически по намерению —
  ТОЛЬКО когда активной задачи нет (укороченный детектор `_maybe_start_task`). Завершённая (`done`)
  задача не блокирует автостарт: новая занимает слот. `/smart_agent_toggle autostart` отключает
  только автообнаружение.
- **Пауза** — флаг `paused`, ортогонален этапу; на паузе технический вызов не делается,
  основная модель не продолжает задачу. `/smart_agent_task_resume` печатает сводку
  (`describe_state`) целиком из состояния, без LLM.
- **`data` живёт до конца задачи, а не этапа** (блок «Уже собрано», сводка после паузы, откат,
  итог). МЕЖДУ задачами ничего не наследуется (`new_task()` с пустым `data`, `finish_task`
  обнуляет). Переживает задачу только один компактный факт в `long_term`.
- **Завершение**: при `stage="done"` итог переносится ОДНИМ фактом (`archive_fact`,
  `source: "auto"`), не по факту на ключ (лимит фактов). Слот автоматически не чистится —
  `data` продолжает уходить в контекст («новых шагов по ней не предлагай»), пока нет
  `/smart_agent_task_done`.
- **Наблюдаемость**: после каждого ответа — строка состояния (`state_line`); строки событий
  (старт, смена этапа, сброс подтверждения, отклонение, архивирование) — только когда событие
  было. Всё, что автомат НЕ сделал из предложенного моделью, — `StateChange.rejected`, печатается
  «⛔ Автомат отклонил: …» (причины на русском) и копится в короткой истории (`transitions`,
  `TRANSITIONS_MAX = 10`, `record_transition`; с пометкой автор) — это диагностика, не журнал
  аудита: не превращай в полный лог, не выноси лимит в `.env`.
- **`/smart_agent_task_stage`** (`manual_transition_block`): граф переходов соблюдается; заполненность
  обычных ключей НЕ проверяется (иначе застрявшую задачу не сдвинуть) — при переводе вперёд с
  несобранным печатается предупреждение; ГЕЙТ текущего этапа соблюдается (это решение человека,
  обход обнулил бы его смысл) — отказ называет ключ и путь: ответить в диалоге или
  `/smart_agent_task_set <ключ-гейта> <значение>`. Назад гейт не мешает никогда.
